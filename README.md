# Автономная док-станция для беспилотных авиационных систем

Репозиторий содержит документацию и впоследствии будет содержать программное обеспечение автономной док-станции и совместно разрабатываемой бортовой интеграции для нескольких зарегистрированных и закреплённых БАС, при этом одна физическая зона принимает и обслуживает только один выбранный аппарат за цикл.

> **Текущий статус: предварительное проектирование. Каждый технический документ имеет собственную редакцию и статус; специальные спецификации не считаются согласованными автоматически.**
>
> На данном этапе зафиксирована концепция системы и предварительная программная архитектура. Модель квадрокоптера, автопилот, аккумулятор, протоколы связи, зарядная мощность, конкретные датчики и исполнительные механизмы пока не выбраны. Документы не являются готовым проектом для изготовления или эксплуатации.

## 1. Назначение

Док-станция должна обеспечивать автономное обслуживание совместимого квадрокоптера после выполнения инспекционной миссии:

1. Обнаружение и идентификация возвращающегося аппарата.
2. Подготовка станции и оценка метеоусловий.
3. Открытие защитной крышки.
4. Точная посадка с использованием штатного автопилота БАС и внешней системы позиционирования.
5. Подтверждение посадки и безопасного состояния аппарата.
6. Закрытие защитной крышки, если это допускают конструкция и состояние аппарата.
7. Получение материалов с внутреннего накопителя БАС.
8. Проверка целостности и локальное сохранение материалов.
9. Защищённая передача материалов на удалённый сервер.
10. Беспроводная зарядка аккумулятора.
11. Передача результатов инспекции специалисту.
12. Получение следующего задания и подготовка к повторному вылету.
13. Самоочистка площадки после освобождения её квадрокоптером.

## 2. Исходные требования

| Параметр | Исходное требование | Статус / уточнение |
|---|---|---|
| Температурный диапазон окружающей среды | −30…+50 °C | ЗАДАНО; условия для каждого узла уточнить |
| Время зарядки | До 2 часов | ЗАДАНО; уточнить батарею и начальный/конечный заряд |
| Автономность | 5–6 циклов без физического вмешательства | ЗАДАНО; автоматический переход к следующей разрешённой миссии |
| КПД беспроводной зарядки | Не менее 70 % | ЗАДАНО; уточнить метод и точки измерения |
| Самоочистка | Предусмотрена | ЗАДАНО; конструкция не выбрана |
| Удалённый контроль | Предусмотрен | ЗАДАНО; серверный интерфейс не выбран |
| Метеостанция | На корпусе станции | ЗАДАНО; допустимый выносной кронштейн требует проверки |
| Бортовая интеграция | Совместно со станцией | СОГЛАСОВАНО; состав зависит от выбранного БАС |
| Количество БАС | Несколько зарегистрированных БАС; один выбранный аппарат на физический цикл | СОГЛАСОВАНО; состав поддерживаемых конфигураций и механизм распознавания определяются отдельно |
| Крышка при обслуживании | Закрыта после безопасной посадки | СОГЛАСОВАНО; конструктивную безопасность нужно проверить |
| Проверка специалистом | Не обязательна перед каждым циклом | СОГЛАСОВАНО; следующий вылет при наличии разрешённого задания и выполнении проверок |

## 4. Роли участников разработки

- **Владелец проекта / технический руководитель:** определяет требования, согласовывает решения, организует аппаратные испытания и принимает результаты.
- **ChatGPT:** основной ИИ-помощник проекта: поддерживает архитектуру и документацию, реализует небольшие функции по согласованным контрактам, готовит тесты, анализирует diff и фактические результаты проверок. Работает в `main` по `docs/AI_WORK_RULES.md`.
- **Испытания:** фактическую работоспособность подтверждают тесты и проверки на оборудовании. Ответ ИИ не является доказательством работоспособности.

## 5. Главный принцип проекта

**Документация в этом репозитории — единый источник согласованных требований и решений.**

Ни один ИИ или разработчик не должен молча менять архитектуру, интерфейсы, ограничения безопасности или уже согласованное поведение.

Если в документации обнаружено противоречие или недостаток, нужно:

1. Описать проблему.
2. Объяснить последствия.
3. Предложить варианты.
4. Дождаться согласования владельца проекта.
5. Только после согласования обновить документацию и код.

## 6. Структура репозитория

- `docs/` — техническая документация и правила разработки.
- `src/` — исходный код программных компонентов (пока не определена окончательная структура).
- `hardware/` — электрические схемы, подключения, спецификации и документация оборудования.
- `tests/` — автоматизированные тесты, сценарии и протоколы испытаний.

## 7. Статусы и зрелость сведений

В документации отдельно фиксируются три независимые характеристики.

**Статус требования или решения:**
- ЗАДАНО;
- СОГЛАСОВАНО;
- ПРЕДЛОЖЕНИЕ;
- ТРЕБУЕТ УТОЧНЕНИЯ;
- ОТКЛОНЕНО.

**Статус реализации:**
- НЕ НАЧАТО;
- В РАЗРАБОТКЕ;
- РЕАЛИЗОВАНО;
- НЕ РЕАЛИЗОВАНО;
- ЗАБЛОКИРОВАНО.

**Статус проверки:**
- НЕ ПРОВЕРЕНО;
- ПРОВЕРЕНО — ПРОЙДЕНО;
- ПРОВЕРЕНО — НЕ ПРОЙДЕНО;
- ПРОВЕРЕНО — ЧАСТИЧНО.

Например: «требование СОГЛАСОВАНО; модуль РЕАЛИЗОВАНО; испытание НЕ ПРОВЕРЕНО».

Подробные определения приведены в `docs/00_DOCUMENT_CONTROL.md`. Статус «СОГЛАСОВАНО» нельзя присваивать решению только потому, что оно предложено ИИ или внесено в документ.

## 8. Правила внесения изменений

- Предпочтительно вносить изменения небольшими логически завершёнными порциями.
- Не смешивать документационные изменения, новые функции и исправления несвязанных ошибок в одном изменении.
- Текущая рабочая ветка проекта — `main`; обычные изменения вносятся непосредственно в неё небольшими логически завершёнными коммитами.
- Отдельную ветку использовать только для специально согласованного рискованного эксперимента или изолированной работы; необходимость такой ветки предварительно согласовать с владельцем проекта.
- Pull Request не является стандартным способом внесения обычных изменений в рамках текущего рабочего процесса.
- Не хранить пароли, токены, приватные ключи, сертификаты, реальные персональные данные и секреты в репозитории.
- Не считать успешную компиляцию доказательством безопасности.
- Перед изменением существующего файла сначала изучить его актуальную версию в репозитории.

Подробные правила приведены в [AI_WORK_RULES.md](docs/AI_WORK_RULES.md).
