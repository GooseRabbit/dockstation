# Конфигурация доски GitHub Projects DockStation

**Статус:** предложение по настройке; сама доска GitHub Projects ещё не создана.  
**Редакция:** 0.1.  
**Дата:** 2026-11-02.

## 1. Назначение

Документ фиксирует предлагаемую конфигурацию доски для планирования и контроля работ по DockStation.

Доска должна показывать не только факт выполнения задачи, но и степень её технической проверки. Подготовка спецификации, написание кода, автоматические тесты и испытания на реальном оборудовании — разные результаты.

## 2. Общие параметры проекта

| Параметр | Предлагаемое значение |
|---|---|
| Название | DockStation — разработка |
| Источник задач | GitHub Issues репозитория `GooseRabbit/dockstation` |
| Основной вид | Board, группировка по полю Status |
| Дополнительный вид | Table, все задачи |
| Связь с исходным кодом | Ссылки на файлы, коммиты и результаты тестов |
| Рабочая ветка | `main` |
| Pull Request | Не используется как обязательный этап обычного рабочего процесса |

Видимость проекта (public/private) владелец выбирает при создании с учётом желаемой открытости планов разработки.

## 3. Поле Status

Использовать одно основное поле статуса со следующими значениями и порядком:

| Статус | Когда устанавливать |
|---|---|
| Запланировано | Задача внесена в план, работа ещё не начата |
| Проектирование | Готовится спецификация, схема или техническое решение |
| Архитектурная проверка | Результат передан на проверку владельцу проекта |
| Готово к реализации | Требования и интерфейсы достаточно определены для написания кода или изготовления узла |
| Разработка | Выполняется программная или аппаратная реализация |
| Проверка | Идут автоматические, имитационные, стендовые или интеграционные испытания |
| Принято | Критерии приёмки выполнены, результаты и документация зафиксированы |
| Заблокировано | Продолжение невозможно без решения, данных, компонента или устранения зависимости |

«Принято» не означает готовность всей станции к эксплуатации. Это статус конкретной задачи или модуля в пределах согласованных критериев приёмки.

## 4. Дополнительные поля

Рекомендуется добавить следующие поля:

| Поле | Тип | Значения / назначение |
|---|---|---|
| Тип задачи | Single select | Спецификация; Программная реализация; Аппаратная разработка; Испытание; Документация; Исследование; Исправление |
| Модуль | Text | Название компонента из `docs/18_MODULE_REGISTER.md` |
| Приоритет | Single select | Критический; Высокий; Обычный; Низкий |
| Этап проверки | Single select | Не проводилась; Анализ документации; Автоматические тесты; Имитация; Стендовые испытания; Интеграционные испытания; Испытания с БАС; Климатические/ресурсные испытания |
| Требования | Text | REQ-ID, относящиеся к задаче |
| Отказы | Text | FAIL-ID, которые необходимо учесть |
| Документация | Text | Ссылки на спецификации и протоколы |

Не следует дублировать все сведения из Issue в дополнительных полях. Полное описание задачи и критерии приёмки хранятся в Issue.

## 5. Рекомендуемые представления (Views)

### 5.1. Основная доска — «Рабочий процесс»

- Layout: Board.
- Group by: Status.
- Показывать: название задачи, приоритет, тип задачи, модуль, этап проверки.
- Использовать для ежедневного понимания текущего положения работ.

### 5.2. Таблица — «Все задачи»

- Layout: Table.
- Показывать все открытые и закрытые задачи.
- Колонки: Status, Title, Тип задачи, Модуль, Приоритет, Этап проверки, Требования, Отказы.
- Использовать для поиска задач и проверки связей с документацией.

### 5.3. Представление — «Заблокировано»

- Layout: Table или Board.
- Фильтр: Status = Заблокировано.
- Показывать причину блокировки и необходимое решение.

### 5.4. Представление — «Проверка»

- Layout: Table или Board.
- Фильтр: Status = Проверка.
- Показывать этап проверки, критерии приёмки и ссылки на результаты.

## 6. Правила ведения карточек

1. Одна карточка должна описывать одну логически завершённую задачу.
2. Большой модуль разбивать на спецификацию, реализацию, тестирование и отдельные аппаратные работы, если это действительно разные результаты.
3. В каждой задаче указывать цель, контекст, разрешённый объём изменений и критерии приёмки.
4. Связывать задачу с REQ-ID и FAIL-ID, когда они применимы.
5. В карточке не ставить статус «Принято» только потому, что код написан или компилируется.
6. Результаты проверки подтверждать конкретными командами, логами или протоколами.
7. Если данных недостаточно, карточка должна оставаться в «Проектировании» или «Заблокировано», а открытые вопросы — быть явно записаны.
8. Не создавать отдельные карточки для каждого мелкого технического действия, если они относятся к одной проверяемой задаче.

## 7. Начальный набор задач

Ниже — рекомендуемые первые карточки. Их следует создавать как GitHub Issues и добавлять в доску после её создания.

| Название | Тип задачи | Модуль | Начальный статус |
|---|---|---|---|
| Подготовить спецификацию StationStateManager | Спецификация | StationStateManager | Проектирование |
| Проверить и согласовать модель состояний станции | Архитектурная проверка | StationStateManager | Запланировано |
| Определить границы и контракт SafetyManager | Спецификация | SafetyManager | Запланировано |
| Уточнить вычислительную архитектуру станции без выбора преждевременного стека | Исследование | Системная архитектура | Запланировано |
| Проработать механический модуль крышки | Аппаратная разработка | LidManager | Проектирование |
| Восстановить реестр оборудования и карточки компонентов | Документация | Аппаратная документация | Запланировано |

Начальные статусы являются планом работ, а не свидетельством начала реализации.

## 8. Автоматизация

На первом этапе не включать автоматические правила, которые самостоятельно переводят задачу в «Принято» по факту закрытия Issue или коммита.

Переходы статусов лучше выполнять осознанно, чтобы не путать:
- готовность спецификации;
- готовность к реализации;
- успешность автоматических тестов;
- прохождение аппаратных испытаний;
- окончательную приёмку результата.

Автоматизацию можно добавить позже, когда процесс будет проверен на практике.

## 9. Ограничение текущей настройки

Этот документ описывает конфигурацию доски, но не является самой доской GitHub Projects. На дату редакции доска не создана: для этого требуется операция создания Project и настройки его полей в интерфейсе GitHub либо через API с соответствующими правами.

Перед созданием следует сверить доступность полей и представлений в текущем интерфейсе GitHub Projects и при необходимости адаптировать конфигурацию без изменения принципов учёта статусов проекта.
