# Пофункциональный план реализации ConfigurationManager

**Связанная спецификация:** `docs/27_CONFIGURATION_MANAGER.md`.  
**Статус:** рабочий план — требует согласования.  
**Редакция:** 0.10.  
**Дата:** 2026-11-10.

## 1. Принцип

ConfigurationManager реализуется последовательно, одной функцией за задачу. Каждая задача включает минимальные необходимые типы/интерфейсы, тесты и обновление документации.

Первая версия read-only: загрузить сохранённую запись, декодировать, проверить и предоставить snapshot. Изменение параметров, миграции и восстановление не входят.

## 2. Правила задач

1. Работать в main по docs/AI_WORK_RULES.md и получать актуальную версию main перед началом.
2. Читать спецификацию, этот план, интерфейсные контракты и существующие тесты.
3. Реализовывать только одну функцию/задачу.
4. Не переписывать модуль целиком и не менять несвязанные файлы.
5. Не придумывать параметры, модели устройств, диапазоны, единицы, тайм-ауты или формат хранения.
6. Не подставлять значения по умолчанию вместо отсутствующих обязательных данных.
7. Использовать fake-порты в unit/contract-тестах; не обращаться к реальному оборудованию.
8. Добавлять позитивные, негативные и граничные тесты.
9. До коммита проверить список изменённых файлов и полный diff; фактические результаты тестов указывать отдельно.

## 4. Первый вертикальный срез

Порядок: CFG-F00 → CFG-F01 → CFG-F02 → CFG-F03 → CFG-F04 → CFG-F05 → CFG-F06 → CFG-F07 → CFG-F08.

CFG-F00 реализована как контрактные типы и абстрактные read-only порты. CFG-F01 реализована как изолированная проверка с явным набором поддерживаемых версий. CFG-F02 реализована как изолированная проверка наличия обязательных полей по явному набору сегментированных путей. CFG-F03 реализована как изолированная проверка точного типа, скалярных допустимых значений и числовых границ по явному набору правил. CFG-F04 реализована как изолированная проверка прямых парных отношений по явной политике; условные зависимости и составные выражения пока не поддерживаются. CFG-F05 объединяет F01-F04, сохраняет WARNING и связывает результат с точной версией/ревизией кандидата; для неё есть 26-проверочный контрактный тест с подменами. CFG-F06 создаёт getter-only snapshot только после VALID и точного совпадения идентификаторов; отдельный unit-тест содержит 24 проверки. CFG-F07 реализована как read-only оркестрация SettingsRepository → ConfigurationDecoderPort → F05 → F06; 30-проверочный contract harness использует fake-порты и подмены F05/F06. CFG-F08 реализована как stateless getter от выбранного вызывающим слоем текущего ConfigurationLoadResult: 19-проверочный unit-тест проверяет точную ревизию, наличие snapshot, соответствие metadata и fail-closed поведение для статусов/issues; глобальное активное состояние не вводится. Production-политики версий, обязательных полей, значений и зависимостей не утверждены. Проверка единиц отложена до появления метаданных. Тестовые идентификаторы и пути служат только тестовыми данными. Если для последующих правил нет утверждённого перечня параметров или критерия, не выдумывать его ради теста. Выделить недостающие требования и оставить эту часть явно незавершённой.

## 5. Сквозные ограничения

- DiagnosticsManager использует snapshot и статус ConfigurationManager, но не повторяет CFG-F01…CFG-F05.
- StationStateManager получает подтверждение через доверенную границу, а не из event payload.
- VALID относится к конкретной ревизии.
- Ошибка обязательной проверки не допускает публикацию частичного snapshot.
- Отсутствие необязательного оборудования не означает FAIL и не означает PASS его работоспособности.
- ConfigurationManager не выдаёт разрешения на физические операции.
- Реальные адаптеры подключаются после выбора хранилища и платформы.

## 6. Сквозные тесты

1. Чтение → декодирование → проверки пройдены → snapshot соответствует ревизии записи.
2. Нет записи → NOT_FOUND, snapshot отсутствует.
3. Хранилище недоступно → UNAVAILABLE.
4. Ошибка чтения → READ_ERROR.
5. Ошибка декодирования → DECODE_ERROR.
6. Неподдерживаемая версия → UNSUPPORTED_VERSION.
7. Нет обязательного параметра → INVALID.
8. Ошибка обязательного правила не создаёт snapshot.
9. Новый результат не наследует VALID предыдущей ревизии.
10. Секретные значения не попадают в диагностические сообщения.

Host-тесты не доказывают атомарность физического хранилища, сохранность при отключении питания или аппаратную интеграцию.

## 7. Вне первого этапа

- save_configuration() и apply_configuration_change();
- авторизация и аудит изменения параметров;
- миграция схем;
- резервное копирование, откат и восстановление;
- выбор JSON/YAML/бинарного формата или конкретной СУБД;
- реализация для ESP32, Orange Pi или другой платы.

Эти задачи оформляются отдельно после согласования требований.

## 8. Критерии готовности задачи

1. Реализован только заявленный контракт.
2. Отсутствующие данные и ошибки различаются явно.
3. Нет скрытых значений по умолчанию.
4. Snapshot создаётся только после обязательной проверки.
5. Добавлены позитивные, негативные и граничные тесты.
6. Тесты фактически запущены, команда и результат зафиксированы.
7. Полный diff проверен до коммита.
