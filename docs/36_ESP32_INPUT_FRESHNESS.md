# ESP32: свежесть safety-входов и устаревшие данные

**Статус:** программный механизм реализован; аппаратные интервалы требуют измерения и утверждения.  
**Редакция:** 1.0.  
**Дата:** 2026-11-18.  
**Связанные документы:** `docs/33_ESP32_HARDWARE_PROFILE.md`, `docs/35_ESP32_APPLICATION_LOGIC.md`.

## 1. Назначение

Документ определяет, как ESP32 отличает актуальное показание safety-входа от отсутствующего или устаревшего. Свежесть — отдельная характеристика от значения сигнала: `false` означает измеренное неактивное состояние, а не отсутствие измерения.

Механизм не выполняет GPIO-чтение и не выбирает частоту опроса. Он проверяет только timestamp, который передал вызывающий слой.

## 2. Контролируемые классы входов

| Класс | Состав | Использование |
|---|---|---|
| Положение крышки | OPEN/CLOSED/TRANSITIONING/UNKNOWN от debounced limit-switch tracker | Разрешение команд крышки и операций с закрытой крышкой |
| Motion feedback | platform, cleaning, drive | Запрет конфликтующих движений |
| Safety stop | активен/неактивен | Запрет обычных команд при активном или неизвестном состоянии |
| Workspace | известна ли зона и свободна ли она | Разрешение StartCleaning |

Motion feedback рассматривается как единый согласованный набор. Если в одном обновлении отсутствует хотя бы одно из трёх значений, весь набор считается неизвестным; частичное обновление не должно освежать остальные значения.

## 3. Timestamp и правила свежести

Каждый набор входов получает timestamp монотонного времени ESP32 в миллисекундах:
- timestamp задаётся в момент получения нового измерения;
- timestamp должен происходить из одного monotonic clock domain внутри текущей загрузки ESP32;
- нельзя передавать время Repka, UTC, время получения сообщения или время пересылки старого кэшированного значения;
- после перезапуска ESP32 все входы начинают как неизвестные; старые timestamp не переносятся.

Для каждого класса отдельно задаётся максимальный возраст:
- `lid_position_max_age_ms`;
- `motion_feedback_max_age_ms`;
- `safety_stop_max_age_ms`;
- `workspace_max_age_ms`.

**Нулевое значение означает, что доверять этому классу входов нельзя.** Значения по умолчанию равны нулю намеренно. Реальные окна нельзя назначить без знания периода опроса, debounce, задержки датчика и требуемого времени реакции. Они должны быть подтверждены после выбора платы и схемы, а затем проверены измерениями.

Граница включительная: возраст, равный max age, ещё свежий. Первое значение возраста больше max age уже считается устаревшим. Если текущее monotonic время меньше timestamp измерения, измерение считается недействительным.

Изменение конфигурации свежести аннулирует все сохранённые измерения и очищает pending-команду. Источники должны передать новые данные.

## 4. Поведение команд

Обычные команды не разрешаются на основании устаревших входов:
- stale safety-stop → `REJECTED / SAFETY_STOP_STALE`;
- stale motion feedback → `REJECTED / MOTION_FEEDBACK_STALE`;
- stale lid position → `REJECTED / LID_POSITION_STALE`;
- stale workspace при StartCleaning → `REJECTED / WORKSPACE_STATE_STALE`.

Если измерение никогда не поступало, остаётся причина UNKNOWN (например, `SAFETY_STOP_STATE_UNKNOWN` или `MOTION_STATE_UNKNOWN`). Так диагностика различает «не получали» и «получали, но давно».

StopMotion и StopCleaning остаются доступными даже при stale/unknown safety-входах. Это разрешение команды, а не доказательство физического останова: исполнительный слой и аппаратный emergency-stop ещё не реализованы.

Свежий новый sample восстанавливает возможность оценки команды, но pending-команда автоматически не возобновляется и не переисполняется.

## 5. Телеметрия

Логическая телеметрия использует:
- `UNKNOWN` + `SensorQualityStatus::Unknown` — измерение не поступало или источник сообщил неизвестное состояние;
- `STALE` + `SensorQualityStatus::Stale` — ранее измеренное значение превысило свой max age;
- `NOT_CONFIGURED` + `SensorQualityStatus::NotConfigured` — вход не включён в подтверждённую конфигурацию;
- фактическое значение + `SensorQualityStatus::Ok` — значение получено и ещё свежее.

`measured_at` в сообщении ControllerLink остаётся строкой времени формирования телеметрии. Проверка свежести опирается на отдельный monotonic timestamp, не на эту строку.

## 6. Текущая реализация и ограничения

Реализованы:
- отдельные timestamps и max-age для четырёх классов входов;
- fail-closed при нулевом окне, превышении max-age и регрессии времени;
- сброс сохранённых измерений при изменении конфигурации;
- stale reason codes для обычных команд;
- различение UNKNOWN и STALE в телеметрии;
- host tests на точной границе max-age, превышении на 1 мс, восстановлении, независимых окнах классов и stop-командах.

Пока не реализованы:
- реальные GPIO reads;
- физический sampling loop;
- проверка аппаратной частоты опроса и jitter;
- обнаружение обрыва/короткого замыкания по электрическим признакам;
- отдельная freshness policy для DHT22; DHT22 GPIO acquisition и bounded sampling loop реализованы, но физические GPIO/датчики ещё не проверены;
- аппаратное аварийное отключение и физические interlocks.

Механизм доверяет timestamp вызывающего слоя. Если будущий GPIO adapter повторно передаст старое кэшированное значение с новым timestamp, freshness tracker не сможет распознать подмену. Поэтому hardware adapter обязан формировать timestamp только после успешного физического чтения и сообщать ошибку чтения как отсутствие sample.

## 7. Что требуется перед аппаратной приёмкой

1. Зафиксировать период опроса каждого входа и debounce.
2. Определить max-age из измеренной частоты и требований времени реакции; не копировать значения из host tests.
3. Проверить задержку и jitter при штатной нагрузке, TLS обмене и reconnect.
4. Инжектировать обрыв, stuck-at, дребезг, пропуск чтений и перезапуск контроллера.
5. Убедиться, что каждый stale/unknown сценарий блокирует обычные команды и отображается отдельно.
6. Подтвердить аппаратную реакцию на safety-stop независимым от программного ControllerLink способом.

До выполнения этих пунктов freshness policy является программным защитным барьером, но не сертификатом функциональной безопасности.
