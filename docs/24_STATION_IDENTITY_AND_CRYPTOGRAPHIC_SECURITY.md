# Идентичность станции и криптографическая защита

**Статус:** техническая спецификация идентичности и доступа; правила изоляции OwnerSpace заданы владельцем проекта, конкретные криптографические параметры остаются предложениями до согласования.  
**Редакция:** 0.3.  
**Дата:** 2026-11-11.

## 1. Назначение

Документ детализирует постоянный идентификатор физической док-станции (Station ID), её криптографическую идентичность, первичную регистрацию, пространства владения частных владельцев и организаций (OwnerSpace), членство пользователей, станционные полномочия, изоляцию данных, защиту каналов связи, управление ключами и проверку удалённых команд.

Это дополнение к:
- `docs/07_DATA_TRANSFER_AND_SECURITY.md` — общая информационная безопасность и передача материалов;
- `docs/23_OPERATOR_APPLICATION.md` — пользовательское приложение;
- `docs/06_INTERFACES_AND_DATA_CONTRACTS.md` — контракты обмена;
- `docs/02_REQUIREMENTS.md` — требования;
- `docs/11_TESTING_AND_ACCEPTANCE.md` — испытания.

**Важно:** внесение технического предложения в этот документ не означает его согласования. Реальные криптографические параметры и аппаратные средства должны быть проверены с учётом выбранных контроллеров, ОС, библиотек и модели угроз.

## 2. Термины и разделение идентификаторов

Необходимо различать следующие сущности:

| Сущность | Назначение | Изменяемость |
|---|---|---|
| Station ID | Постоянный машинный идентификатор физической станции в системе | Не меняется после регистрации; не переиспользуется |
| Inventory number | Человекочитаемый инвентарный номер, например `DS-001`, назначаемый организации/оператором | Может назначаться и изменяться администратором по политике учёта; не является криптографической идентичностью |
| Hardware serial | Заводской серийный номер корпуса/изделия/основного узла, если присвоен изготовителем | Определяется изготовителем; не заменяет Station ID |
| Device key | Индивидуальная криптографическая пара ключей станции | Может быть заменена только контролируемой процедурой |
| Device certificate | Сертификат, связывающий публичный ключ с зарегистрированной станцией | Может быть перевыпущен или отозван |
| Display name | Читаемое имя станции, например «Док № 04» | Может изменяться уполномоченным пользователем |
| Network address | IP, MAC, SSID, имя хоста и другие сетевые признаки | Могут изменяться; не являются удостоверением личности |
| OwnerSpace (tenant) | Пространство владения одного частного владельца или одной организации; граница доступа к принадлежащему ему парку станций и данным | Может иметь несколько пользователей и станций; одна станция имеет только одного текущего владельца OwnerSpace |
| OwnerSpaceMembership | Связь индивидуальной учётной записи пользователя с OwnerSpace, ролью и состоянием членства | Создаётся/отзывается уполномоченным администратором; пользователь может состоять в нескольких OwnerSpace |
| StationAccessGrant | Явное право пользователя на конкретную станцию и набор ресурсов/операций, включая срок делегирования | Ограничивается конкретными Station ID и полномочиями; может быть отозвано или истечь |
| Station ownership record | Доверенная запись соответствия Station ID единственному текущему OwnerSpace | Меняется только процедурой передачи владения; Station ID не меняется |

Station ID является открытым идентификатором, а не секретом, паролем, токеном или доказательством права доступа. Знание Station ID не должно позволять зарегистрировать станцию, войти в неё или получить управление. Наличие Station ID в запросе также не подтверждает принадлежность станции пользователю или его OwnerSpace.

MAC-адрес, IP-адрес, SSID, географическое положение и отображаемое имя нельзя использовать как единственный идентификатор или как доказательство подлинности станции.

## 3. Предлагаемый формат Station ID

### 3.1. Рекомендация

Предлагается использовать UUID версии 4 по RFC 9562:
- 128-битное значение;
- генерируется криптографически стойким генератором случайных чисел;
- отображается в стандартном текстовом формате UUID;
- не содержит серийного номера, MAC-адреса, координат или других персональных/производственных данных;
- не зависит от системных часов станции.

UUIDv4 выбран как простой случайный постоянный идентификатор, а не как средство аутентификации. Регистратор всё равно обязан проверять уникальность по ограничению уникальности в реестре.

Пример формата (только иллюстрация, не реальный ID): `7f0d2e91-6a13-4f8c-9c42-8d7a1b3e5f60`.

### 3.2. Правила жизненного цикла

1. Station ID назначается один раз при первичной регистрации.
2. После регистрации ID неизменяем.
3. Изменяемое имя станции хранится отдельно.
4. Человекочитаемый Inventory number может назначаться администратором при регистрации или позднее; его уникальность проверяется в пределах организации/пространства учёта.
5. Изменение Inventory number или display_name не меняет Station ID и не требует перевыпуска сертификата.
6. При передаче станции новому владельцу меняются связи с пользователями и права, но не Station ID.
7. При выводе станции из эксплуатации запись переводится в статус RETIRED/DECOMMISSIONED.
8. Выведенный Station ID никогда не выдаётся другой станции.
9. Повторная регистрация уже известной аппаратной или криптографической идентичности не создаёт новую станцию автоматически: требуется процедура восстановления/передачи/замены контроллера.
10. Удаление учётной записи пользователя или отвязка пользователя от станции не удаляет Station ID и не меняет криптографическую идентичность станции.

### 3.3. Генерация и проверка уникальности

UUID должен формироваться генератором криптографически стойких случайных чисел, предоставленным ОС или доверенной криптографической библиотекой. Запрещено использовать простой PRNG, счётчик, MAC-адрес или комбинацию времени с серийным номером.

Реестр станций должен накладывать уникальное ограничение на Station ID. При конфликте регистрация останавливается, существующая запись не перезаписывается. Конфликт должен журналироваться и передаваться на ручную проверку.

## 4. Криптографическая идентичность станции

Station ID и криптографическая идентичность должны существовать независимо.

### 4.1. Ключевая пара

Предлагаемый порядок:
1. При первом доверенном вводе станция создаёт индивидуальную пару ключей.
2. Приватный ключ по возможности создаётся и хранится внутри TPM, secure element или другого аппаратного хранилища ключей.
3. Приватный ключ не передаётся серверу, операторскому приложению, установщику или другой станции.
4. Серверу/центру регистрации передаётся открытый ключ или запрос на выдачу сертификата.
5. После успешной регистрации публичный ключ связывается с Station ID в реестре.

Если выбранный контроллер не имеет TPM/secure element, допускается временное проектное решение с индивидуальным ключом, созданным криптографически стойким генератором и защищённым средствами ОС/правами доступа/шифрованием хранилища. Такой вариант должен быть явно отмечен как менее стойкий к физическому извлечению накопителя. Нельзя незаметно подменять индивидуальные ключи одним общим ключом для всех станций.

### 4.2. Сертификаты и доверие

Для сетевого взаимодействия рекомендуется управляемая инфраструктура сертификатов (PKI):
- собственный корневой центр сертификации хранится отдельно и используется ограниченно;
- для выпуска сертификатов используются промежуточные/операционные полномочия;
- каждой станции выдаётся индивидуальный сертификат;
- сертификат содержит идентификатор или ссылку на зарегистрированную аппаратную идентичность;
- предусматриваются срок действия, перевыпуск, ротация и отзыв;
- тестовые и эксплуатационные удостоверяющие центры/сертификаты разделяются.

Сертификат подтверждает связь публичного ключа с зарегистрированным субъектом, но проверка сертификата не заменяет проверку прав конкретного пользователя или команды.

### 4.3. Замена контроллера или ключа

При замене вычислительного модуля/контроллера:
- старый сертификат отзывается или помечается недействительным;
- выполняется контролируемое сервисное подтверждение физической станции;
- новый ключ генерируется на новом модуле;
- Station ID сохраняется только если по учётным и физическим данным это та же станция;
- событие замены и новая криптографическая идентичность попадают в аудит.

При полной замене физического изделия создаётся новая запись станции и новый Station ID. Точные критерии «ремонт той же станции» и «новая станция» требуется определить в регламенте обслуживания.

## 5. Первичная регистрация (provisioning)

### 5.1. Штатная онлайн-процедура

Предлагаемая последовательность:
1. Станция запускается в ограниченном режиме первичной регистрации; обычные управляющие команды и опасные физические операции недоступны.
2. Уполномоченный установщик физически активирует режим регистрации предусмотренным способом (например, сервисная кнопка/перемычка/ключ обслуживания).
3. Станция создаёт индивидуальную пару ключей и формирует запрос регистрации с публичным ключом, аппаратными сведениями, случайным challenge/nonce и версией ПО.
4. Оператор подтверждает регистрацию в доверенном сервисе, указывает/проверяет заводской серийный номер и при необходимости назначает Inventory number (например, DS-001).
5. Реестр выделяет уникальный Station ID и проверяет отсутствие конфликтов по Station ID, серийному номеру и ключу.
6. Сервис регистрации связывает публичный ключ с Station ID и выдаёт индивидуальный сертификат/учётные данные устройства.
7. Станция проверяет подлинность ответа регистратора и сохраняет Station ID, сертификат и доверенные корни.
8. Регистрация фиксируется в аудите; станция выходит из ограниченного режима только после подтверждения завершения регистрации и локальной проверки конфигурации.

QR-код или напечатанный Station ID может использоваться для удобства поиска и привязки, но не является самостоятельным доказательством подлинности или права регистрации. Нельзя использовать общий пароль по умолчанию или один bootstrap-секрет для всего парка станций.

### 5.2. Офлайн-регистрация

Офлайн-регистрация должна быть предусмотрена, но не должна ослаблять защиту:
- предпочтительный вариант — заранее выданный сервером одноразовый регистрационный ваучер/пакет с ограниченным сроком и областью действия;
- регистрация сохраняется как PENDING_SYNC до сверки с центральным реестром;
- при последующей синхронизации уникальность Station ID, серийного номера и открытого ключа проверяется повторно;
- конфликт не приводит к автоматической перезаписи другой станции; станция помещается в режим разрешения конфликта;
- ваучер после использования становится недействительным.

Создание Station ID вручную без проверки глобального реестра допускается только как временный офлайн-процесс с последующей обязательной синхронизацией и проверкой. Постоянный общий bootstrap-пароль запрещён.

### 5.3. Привязка пользователя и назначение полномочий

Пользователь привязывается к станции только после того, как:
- станция прошла криптографическую регистрацию и имеет запись в доверенном реестре;
- пользователь аутентифицирован индивидуальной учётной записью;
- пользователь состоит в OwnerSpace — владельце этой станции либо имеет действующее точечное делегирование;
- инициатор имеет право управлять соответствующим членством/делегированием;
- станция подтверждена через доверенный канал или процедуру физического сопряжения.

Ввод одного только Station ID, сканирование QR-кода или знание сетевого адреса не создаёт права доступа. Запись членства должна фиксировать user_id, owner_space_id, роль, инициатора, время, статус и основание. Запись станционного права должна дополнительно фиксировать station_id, перечень разрешений, срок действия и состояние отзыва.

### 5.4. Владение станцией и его передача

1. Каждая зарегистрированная станция связана ровно с одним текущим OwnerSpace — частным владельцем или организацией.
2. Одно OwnerSpace может владеть множеством станций; один пользователь может состоять в нескольких OwnerSpace под своей индивидуальной учётной записью.
3. Первичное назначение OwnerSpace выполняется уполномоченной процедурой после регистрации станции и проверки права владельца. Нельзя назначить владельца только введением публичного Station ID.
4. Передача станции требует полномочий текущего владельца и подтверждения нового владельца. Простая смена display_name, Inventory number или пользователя не является передачей владения.
5. При завершении передачи меняется запись OwnerSpace для Station ID; постоянный Station ID сохраняется. Все привязки, делегирования, сессии и токены прежнего OwnerSpace, предоставлявшие доступ к этой станции, отзываются. Пользователи нового OwnerSpace получают права только через новые назначения.
6. Передача и отзыв прежнего доступа журналируются. Права на исторические данные и материалы обрабатываются отдельно по утверждённой процедуре; автоматическое наследование доступа прежних пользователей запрещено.

## 6. Криптографическая защита каналов

### 6.1. Общая политика

Все каналы управления, мониторинга, администрирования, передачи файлов и видео должны защищать конфиденциальность, целостность и подлинность стороны/сторон. Требование одинаково для:
- станция — сервер;
- операторское приложение — сервер;
- операторское приложение — станция по Wi-Fi;
- операторское приложение — станция по Ethernet/USB/service port или иному проводному интерфейсу;
- БАС — станция;
- удалённый видеопоток.

Предпочтительный IP-транспорт — TLS 1.3 по действующей редакции RFC 9846. Поддержка TLS должна подтверждаться выбранными библиотеками и ОС. Отключение проверки цепочки доверия/имени узла/назначения сертификата запрещено.

TLS защищает канал между узлами, но не заменяет авторизацию команд, локальные межблокировки, шифрование данных на накопителе и управление ключами.

Нельзя автоматически переходить на HTTP, незашифрованный TCP, открытый WebSocket или другой незашифрованный режим при ошибке TLS. Если выбранный компонент не поддерживает согласованный защищённый протокол, соединение отклоняется до отдельного инженерного решения.

### 6.2. Режимы соединения

| Канал | Минимальное требование |
|---|---|
| Станция — сервер | TLS 1.3; взаимная аутентификация станции индивидуальным сертификатом (mTLS) |
| Приложение — сервер | TLS 1.3; аутентификация пользователя и проверка прав на стороне сервиса |
| Приложение — станция напрямую | TLS 1.3; приложение проверяет сертификат станции, станция независимо аутентифицирует пользователя и проверяет его права |
| БАС — станция | Взаимная аутентификация и защищённый канал; конкретный протокол зависит от выбранного БАС и радиоинтерфейса |
| Камера/видеопоток | Защищённый транспорт и отдельная авторизация на просмотр; не выдавать открытый RTSP/поток в незащищённую сеть |
| Проводной сервисный интерфейс | Те же проверки аутентификации и полномочий; физический кабель не создаёт административный доступ |

Wi-Fi WPA2/WPA3 и сегментация сети рассматриваются как дополнительные сетевые меры, но не заменяют прикладную криптографическую защиту.

### 6.3. TLS-совместимость и алгоритмы

На этапе выбора библиотек следует проверить:
- поддержку RFC 9846;
- проверку цепочки сертификатов и статуса отзыва;
- надёжную генерацию случайных чисел;
- обновление криптографической библиотеки;
- запрет устаревших протоколов и небезопасных наборов шифров;
- безопасное хранение ключей;
- корректную обработку ошибки сертификата и истечения срока действия.

Конкретные наборы шифров и алгоритмы сертификатов не фиксируются до выбора вычислителей и библиотек. Не следует самостоятельно изобретать криптографические протоколы или заменять проверенные реализации самописным шифрованием.

### 6.4. Внутренний канал Repka Pi 5 — ESP32 (DEC-066, предложение)

Для короткого внутреннего UART Repka—ESP32 предлагается использовать стандартный TLS 1.3 поверх существующего полнодуплексного байтового потока, а не разрабатывать собственный криптографический формат. Это локальный профиль пары контроллеров; он не заменяет mTLS станции—сервер и не меняет общую модель Station ID.

**Предлагаемый профиль:**
- Repka выступает TLS client и инициирует соединение; ESP32 — TLS server.
- Версия — только TLS 1.3 по действующей редакции RFC 9846. Запрещены downgrade/fallback к TLS 1.2 и любой открытый режим при ошибке handshake.
- Для первой пары предлагается внешний случайный PSK длиной 32 байта (256 бит), уникальный для связки конкретных Repka + ESP32. PSK должен поступать из криптографически стойкого генератора случайных чисел; пароль, PIN, серийный номер, Station ID или строка конфигурации не являются допустимым источником ключа.
- Для обмена ключами предлагается только TLS 1.3 PSK с эфемерным (EC)DHE (psk_dhe_ke / PSK-ephemeral). Чистый PSK-only режим не разрешать: он не обеспечивает forward secrecy для трафика. Первая проверяемая комбинация — TLS_AES_128_GCM_SHA256 и общая поддерживаемая эфемерная группа (начальный кандидат — secp256r1); окончательный allow-list утверждается только после interop и аппаратной проверки выбранного SoC.
- PSK identity — непрозрачный случайный идентификатор конкретного ключевого набора. Он не должен раскрывать Station ID, серийный номер, имя владельца или иные читаемые сведения; сама identity не доказывает знание PSK.
- Стороны аутентифицируют друг друга владением одним индивидуальным PSK в TLS handshake. Обычные поля controller_id/controller_instance_id остаются проверяемым логическим контекстом после защищённого handshake, а не самостоятельным средством аутентификации.
- Сертификаты X.509 и проверка срока действия сертификата для этого внутреннего point-to-point профиля не требуются. Это снимает зависимость установления локального защищённого канала от RTC/синхронизации часов, но не отменяет требования к случайности и безопасному жизненному циклу PSK.

**Почему не самописное шифрование:** TLS 1.3 уже определяет handshake, вывод сессионных ключей, аутентификацию записей, sequence protection и обработку ошибок. Сочетание PSK с эфемерным (EC)DHE позволяет сохранить forward secrecy при использовании внешнего общего секрета. Применение PSK-only режима теряет это свойство; TLS 1.3 0-RTT имеет отдельные риски повторного воспроизведения. Поэтому на первом этапе отключить early data/0-RTT, session tickets и возобновление сессии: при каждом восстановлении UART-канала выполнять полный новый PSK-DHE handshake. RFC 9846 прямо различает PSK-only и PSK с (EC)DHE и описывает риски replay для 0-RTT.

**Разделение уровней:**
1. Физический UART остаётся DEC-062: 3,3 В, full duplex, исходный профиль 115200 8N1.
2. TLS-стек получает и отправляет сырые байты UART через custom send/receive callbacks. На этой границе обрабатываются частичные чтения/записи, backpressure, тайм-ауты и сброс канала.
3. TLS record layer шифрует и аутентифицирует трафик. Дополнительный самописный внешний encryption frame не вводится.
4. Только plaintext application data, возвращённые TLS после успешного handshake и проверки записей, передаются в ControllerFrameStreamDecoder; затем работают существующие ControllerCodec и ControllerLinkSession.
5. Следовательно, ControllerFrameStreamDecoder больше не подключается напрямую к сырым байтам GPIO UART: он получает байты уже из TLS read(). Формат ControllerCodec v1 остаётся внутренним прикладным форматом и не считается криптографической защитой.

В качестве библиотек-кандидатов: Mbed TLS из ESP-IDF на ESP32 (TLS 1.3 полноценно поддерживается начиная с Mbed TLS 3.6.0; требуется включить и проверить TLS 1.3 и PSK-ephemeral режим для точного target) и OpenSSL 3.x на Repka. Mbed TLS предоставляет пользовательские send/receive callbacks; OpenSSL BIO pair позволяет управлять TLS I/O поверх нестандартного транспорта. Совместимость конкретных версий, PSK callbacks, cipher/group allow-list и поведение при частичных UART I/O обязательны к отдельной interop-проверке. Пока точные ESP32 SoC и ESP-IDF не подтверждены, ни версия ESP-IDF, ни конкретные API/настройки прошивки окончательно не фиксируются.

**Хранение ключа:**
- Для Linux — отдельный credential-файл, например /etc/dockstation/credentials/repka-esp32.psk, не в JSON-конфигурации и не в репозитории; каталог доступен только root и группе сервиса, файл — root-owned и читаем только процессом dockstation. Права ОС снижают риск случайного чтения, но не защищают от физического извлечения незашифрованного системного накопителя или компрометации root.
- На ESP32 — отдельная запись NVS. Для production требуется проверить связку Flash Encryption + NVS Encryption, поскольку NVS Encryption использует ключи, защищённые Flash Encryption. Secure Boot должен ограничивать запуск неподписанного кода; конкретные режимы зависят от точного SoC и ESP-IDF.
- Общий PSK для нескольких станций/ESP32 запрещён. Нельзя включать PSK в исходники, sdkconfig, обычные backup, crash dump или логи. Секреты не выводятся в диагностические снимки и не передаются через обычные API.
- PSK генерируется и устанавливается только в отдельной физически контролируемой процедуре provisioning. Использование USB как сервисного интерфейса само по себе не делает его доверенным: режим первичной выдачи, подтверждение присутствия уполномоченного специалиста, временный канал доставки и очистка промежуточных копий ещё требуется спроектировать. Никакой сетевой/открытый fallback provisioning не допускается.
- Для замены ESP32, компрометации, сброса или ремонта предусматривается выпуск нового pair-specific PSK, отзыв старого и запись действия в аудит. PSK local link не является Device Key/сертификатом станции для сервера и не переиспользуется в mTLS или иных каналах.

**Поведение при отказе:** до завершения TLS handshake и проверки PSK никакие ControllerCodec сообщения не передаются в прикладную сессию. Неверный PSK/identity, несовместимая версия, отказ проверки AEAD tag, потеря UART или фатальная ошибка TLS закрывают защищённую сессию; остаток буферов и ControllerLinkSession сбрасываются, затем допускается только новый полный handshake. Открытый режим, обход проверки, «debug plaintext» и автоматическое понижение протокола запрещены. При недоступности защищённого канала удалённый обмен и будущие удалённые команды блокируются; локальные аппаратные межблокировки и безопасное автономное поведение ESP32 продолжают работать независимо от Repka.

**Команды и повторы:** TLS защищает записи и аутентифицирует канал, но не выдаёт права на опасное действие. Первый этап остаётся read-only: HELLO/HELLO_ACK/HEARTBEAT/REQUEST_SNAPSHOT/TELEMETRY_SNAPSHOT/ERROR. При последующем добавлении команд обязательны отдельная проверка полномочий, Station ID/target binding, command_id, срок действия, sequence/nonce, проверка локального SafetyManager и дедупликация на уровне приложения по §8.2. Потеря ответа после отправки команды не означает, что действие не произошло; для потенциально опасной операции требуется OUTCOME_UNKNOWN и сверка, а не слепой повтор.

**Проверки до реализации/приёмки:** interop TLS 1.3 PSK-DHE OpenSSL ↔ Mbed TLS; отказ при неверном/отсутствующем PSK и identity; принудительное отсутствие TLS 1.2/PSK-only/0-RTT/session resumption; отказ при изменённой/обрезанной записи; разрыв во время handshake и чтения/записи; проверка, что до handshake complete plaintext не доходит до ControllerCodec; отсутствие секретов в логах/файлах конфигурации; проверка прав на credential storage; измерение heap peak, handshake time и устойчивости на точном ESP32 при UART 115200. Host-тесты и interop не заменяют физические испытания UART и безопасного хранения ключа на готовой плате.

## 7. Пароли, пользователи и сессии

### 7.1. Хранение паролей

Пароли пользователей:
- не хранятся в открытом виде;
- не шифруются обратимым способом для последующего восстановления;
- хранятся как результат специализированной медленной функции хеширования паролей с индивидуальной случайной солью;
- не передаются по незашифрованному каналу;
- не попадают в логи, диагностические отчёты, crash dump по возможности и резервные выгрузки в открытом виде.

Рекомендуемая функция для первой реализации — Argon2id по RFC 9106. Соль должна быть уникальной для каждой записи и генерироваться криптографически стойким генератором. Параметры памяти/итераций/параллелизма выбираются нагрузочным тестом на сервере/целевой платформе, а затем версионируются; не копировать параметры из примера RFC без измерения на целевом оборудовании.

При каждой успешной аутентификации следует иметь возможность определять устаревшие параметры хеширования и безопасно повышать их при следующей смене пароля/успешной проверке.

### 7.2. Политика учётных записей

Предусмотреть:
- индивидуальную учётную запись для каждого человека;
- отсутствие совместно используемых учётных записей операторов;
- поддержку нескольких пользователей в одном OwnerSpace;
- возможность членства одной индивидуальной учётной записи в нескольких OwnerSpace;
- отдельное хранение членства OwnerSpace и прав на конкретные станции;
- ограничение частоты попыток входа и защиту от перебора;
- блокировку/временную задержку по политике после серии ошибок;
- проверку пароля на распространённость/компрометацию при задании или смене;
- поддержку менеджеров паролей и вставки пароля;
- многофакторную аутентификацию как минимум для администраторов удалённого доступа — рекомендуемое требование;
- принудительный отзыв сессий при блокировке пользователя, смене пароля, отзыве роли или отвязке от станции.

Минимальная длина и требования к паролям должны быть установлены отдельной парольной политикой с учётом применимого профиля безопасности. Не вводить искусственные требования вроде обязательной комбинации трёх классов символов без обоснования.

### 7.3. Сессии и токены

Сессии должны быть ограничены сроком жизни и областью полномочий, включая OwnerSpace, целевые Station ID и допустимые операции. Токены не должны передаваться в URL или сохраняться в открытых логах. При блокировке пользователя, отзыве членства OwnerSpace, станционного grant, смене владельца станции или изменении полномочий затронутый доступ прекращается, включая уже активные сессии и токены. Изменение полномочий должно немедленно учитываться серверной проверкой; нельзя полагаться только на срок жизни ранее выданного токена. Обновление/продление токена должно предусматривать ротацию и обнаружение повторного использования. Это немедленное прекращение относится к запросам, проверяемым центральным сервером, и к подключённым получателям отзыва. Станция, полностью отключённая от сервера, не может узнать об отзыве в момент его выполнения; для неё ранее выданный локальный grant ограничивается заранее установленным коротким сроком автономного действия и прекращает действовать по истечении этого срока или при получении подписанного отзыва.

## 8. Multi-tenant авторизация, удалённые команды и защита от повторов

### 8.1. Проверка области владения и доступа к ресурсам

На серверной стороне проверка доступа обязательна при каждом API-запросе, а не только при входе пользователя или при построении списка станций.

Для каждого запроса сервер обязан:
1. Получить пользователя из проверенной активной сессии, а не из полей тела/параметров клиентского запроса.
2. По Station ID определить фактический OwnerSpace станции из доверенного реестра.
3. Проверить действующее членство пользователя в этом OwnerSpace либо точечный делегированный StationAccessGrant.
4. Проверить право на конкретную станцию, ресурс и операцию, а также срок и область делегирования.
5. Отказать по умолчанию, если запись отсутствует, принадлежность не определена, право неизвестно/отозвано/просрочено или проверка не завершилась успешно.

Эта проверка обязательна для списков станций, карточек, телеметрии, истории измерений, журналов, конфигурации, миссий, файлов и метаданных, камеры/видеопотока, подписок и push-событий, команд и результатов команд, экспорта и диагностических отчётов. Каждый дочерний объект должен быть связан с родительской станцией и наследовать её границу доступа. Фильтрация только на клиенте запрещена.

Клиентские owner_space_id, user_id, role и permissions не являются доказательством полномочий. Сервер определяет личность пользователя по сессии, а владельца станции и права — по собственным доверенным записям. Подстановка чужого Station ID не должна раскрывать существование станции, её владельца, имя, состояние или другие метаданные. Техническая роль администратора серверной платформы сама по себе не означает неограниченное право читать данные владельцев.

Прямое локальное подключение к станции обязано соблюдать ту же модель полномочий. При отсутствии сервера допускается использовать только ранее полученные подписанные grants с ограниченными областью и сроком действия. Grant должен быть привязан к пользователю, конкретному Station ID и набору разрешений; станция проверяет подпись доверенного издателя и срок. Если станция не может подтвердить действительность права, доступ к защищённым данным и командам отклоняется. Отзыв на полностью отключённую станцию доставить мгновенно невозможно, поэтому автономный срок и набор разрешённых офлайн-операций должны быть минимальными и явно заданы. Физический кабель, локальная Wi-Fi-сеть или знание адреса не создают привилегии.

### 8.2. Проверка удалённых команд и защита от повторов

Каждая управляющая команда должна быть связана с конкретной станцией и иметь как минимум:
- command_id — уникальный идентификатор команды;
- station_id — целевая станция;
- actor_id / user_id — инициатор;
- operation_id — идентификатор длительной операции, если создаётся;
- command_type и параметры;
- issued_at и expires_at;
- nonce или монотонный sequence number;
- идентификатор сессии/контекста авторизации;
- версию контракта.

Станция обязана самостоятельно проверить:
1. Подлинность канала/отправителя и действительность учётных данных.
2. Совпадение station_id с собственной постоянной идентичностью.
3. Полномочия пользователя на данный тип команды и данную станцию.
4. Срок действия команды и защиту от повторного использования nonce/sequence/command_id.
5. Допустимость команды по текущему состоянию и локальным правилам SafetyManager.
6. Отсутствие конфликта с уже выполняемой операцией.

Приложение не может само объявить команду разрешённой только потому, что пользователь видит кнопку. Поля user_id/role в сообщении клиента являются контекстом, но не самостоятельным доказательством полномочий: они должны подтверждаться доверенным сервером/станцией.

Команды, поставленные в очередь на сервере, должны оставаться привязанными к Station ID и иметь ограниченный срок действия. Станция не должна исполнять устаревшую команду после длительного отсутствия связи. Для потенциально опасных команд потеря ответа означает OUTCOME_UNKNOWN до сверки, а не повод автоматически повторить действие.

## 9. Защита данных на накопителях и обновлений

Предусмотреть:
- шифрование локального накопителя станции или чувствительных областей хранения;
- защиту ключей шифрования отдельно от данных, с использованием TPM/secure element, если доступно;
- невозможность получить приватный ключ станции простым извлечением накопителя, насколько это позволяет выбранная аппаратная платформа;
- шифрование резервных копий и секретной конфигурации;
- раздельное хранение эксплуатационных, тестовых и резервных ключей;
- цифровую подпись обновлений ПО/прошивок и проверку подписи до установки;
- отказ от установки повреждённого, неподписанного или подписанного недоверенным ключом пакета;
- журналирование установки, версии, результата и источника обновления.

Шифрование накопителя защищает данные при потере/извлечении носителя, но не заменяет контроль доступа работающей ОС и защиту устройства от физической компрометации.

## 10. Управление жизненным циклом ключей

Необходимо описать и протестировать:
- генерацию ключей;
- регистрацию публичной части;
- хранение закрытых ключей;
- выпуск и установку сертификата;
- плановую ротацию;
- отзыв при компрометации;
- замену контроллера;
- сброс к заводскому состоянию;
- передачу станции другому владельцу;
- вывод станции из эксплуатации;
- безопасное уничтожение/аннулирование ключей.

Один общий приватный ключ или общий пароль для всего парка станций запрещён. Ключи не должны храниться в Git, в исходном коде, в примерах конфигурации или в обычных логах.

## 11. Отказ и восстановление доверия

Если сертификат отозван, просрочен, не соответствует Station ID или не проходит проверку цепочки, защищённая сессия не устанавливается. Нельзя отключать проверку сертификата для обхода отказа.

Восстановление должно выполняться через документированный физически подтверждённый сервисный процесс с аудитом. Сервисный режим не является скрытым backdoor и не должен предоставлять безусловный доступ к опасным исполнительным операциям.

При подозрении на компрометацию:
1. Отозвать учётные данные устройства/сертификат.
2. Заблокировать удалённый доступ к станции до повторной регистрации.
3. Отозвать сессии операторов, если скомпрометированы пользовательские учётные данные.
4. Зафиксировать инцидент.
5. Выполнить сервисную проверку и повторное provisioning.

## 14. Нормативные и технические источники

- [RFC 9562 — Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562.html): формат UUID и генерация UUIDv4.
- [RFC 9846 — The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/rfc/rfc9846.html): актуализированная спецификация TLS 1.3, опубликована в июле 2026 г.; заменяет RFC 8446.

Эти источники не являются доказательством соответствия проекта конкретному стандарту. Применимость формальных требований и законодательства должна быть проверена отдельно.

## 15. Правило согласования

Владелец проекта отдельно согласует:
- формат и процедуру назначения Station ID;
- онлайн- и офлайн-provisioning;
- PKI и аппаратную защиту ключей;
- TLS/mTLS и политику сертификатов;
- парольную политику и MFA;
- шифрование накопителя;
- подпись обновлений.

Требование изоляции OwnerSpace, проверки доступа на каждом запросе, запрета доступа к чужой станции по одному Station ID и отзыва прежнего доступа при передаче станции является обязательным требованием проекта (DEC-055), а не криптографическим предложением.

До согласования конкретные криптографические решения из приведённого списка имеют статус ПРЕДЛОЖЕНИЕ. Разработчикам запрещено превращать эти рекомендации в окончательные криптографические параметры или заменять их упрощённой схемой без согласования.
