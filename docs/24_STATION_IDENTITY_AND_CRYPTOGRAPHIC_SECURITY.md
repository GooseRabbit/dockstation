# Идентичность станции и криптографическая защита

**Статус:** предварительная техническая спецификация; предложения требуют согласования владельца проекта.  
**Редакция:** 0.1.  
**Дата:** 2026-11-03.

## 1. Назначение

Документ детализирует постоянный идентификатор физической док-станции (Station ID), её криптографическую идентичность, первичную регистрацию, привязку к учётным записям, защиту каналов связи, управление ключами и проверку удалённых команд.

Это дополнение к:
- `docs/07_DATA_TRANSFER_AND_SECURITY.md` — общая информационная безопасность и передача материалов;
- `docs/23_OPERATOR_APPLICATION.md` — пользовательское приложение;
- `docs/06_INTERFACES_AND_DATA_CONTRACTS.md` — контракты обмена;
- `docs/02_REQUIREMENTS.md` — требования;
- `docs/11_TESTING_AND_ACCEPTANCE.md` — испытания.

**Важно:** внесение технического предложения в этот документ не означает его согласования. Реальные криптографические параметры и аппаратные средства должны быть проверены с учётом выбранных контроллеров, ОС, библиотек и модели угроз.

## 2. Термины и разделение идентификаторов

Необходимо различать следующие сущности:

| Сущность | Назначение | Изменяемость |
|---|---|---|
| Station ID | Постоянный логический идентификатор физической станции в системе | Не меняется после регистрации; не переиспользуется |
| Hardware serial | Заводской серийный номер корпуса/изделия/основного узла, если присвоен изготовителем | Определяется изготовителем; не заменяет Station ID |
| Device key | Индивидуальная криптографическая пара ключей станции | Может быть заменена только контролируемой процедурой |
| Device certificate | Сертификат, связывающий публичный ключ с зарегистрированной станцией | Может быть перевыпущен или отозван |
| Display name | Читаемое имя станции, например «Док № 04» | Может изменяться уполномоченным пользователем |
| Network address | IP, MAC, SSID, имя хоста и другие сетевые признаки | Могут изменяться; не являются удостоверением личности |

Station ID является открытым идентификатором, а не секретом, паролем, токеном или доказательством права доступа. Знание Station ID не должно позволять зарегистрировать станцию, войти в неё или получить управление.

MAC-адрес, IP-адрес, SSID, географическое положение и отображаемое имя нельзя использовать как единственный идентификатор или как доказательство подлинности станции.

## 3. Предлагаемый формат Station ID

### 3.1. Рекомендация

Предлагается использовать UUID версии 4 по RFC 9562:
- 128-битное значение;
- генерируется криптографически стойким генератором случайных чисел;
- отображается в стандартном текстовом формате UUID;
- не содержит серийного номера, MAC-адреса, координат или других персональных/производственных данных;
- не зависит от системных часов станции.

UUIDv4 выбран как простой случайный постоянный идентификатор, а не как средство аутентификации. Регистратор всё равно обязан проверять уникальность по ограничению уникальности в реестре.

Пример формата (только иллюстрация, не реальный ID): `7f0d2e91-6a13-4f8c-9c42-8d7a1b3e5f60`.

### 3.2. Правила жизненного цикла

1. Station ID назначается один раз при первичной регистрации.
2. После регистрации ID неизменяем.
3. Изменяемое имя станции хранится отдельно.
4. При передаче станции новому владельцу меняются связи с пользователями и права, но не Station ID.
5. При выводе станции из эксплуатации запись переводится в статус RETIRED/DECOMMISSIONED.
6. Выведенный ID никогда не выдаётся другой станции.
7. Повторная регистрация уже известной аппаратной или криптографической идентичности не создаёт новую станцию автоматически: требуется процедура восстановления/передачи/замены контроллера.
8. Удаление учётной записи пользователя или отвязка пользователя от станции не удаляет Station ID и не меняет криптографическую идентичность станции.

### 3.3. Генерация и проверка уникальности

UUID должен формироваться генератором криптографически стойких случайных чисел, предоставленным ОС или доверенной криптографической библиотекой. Запрещено использовать простой PRNG, счётчик, MAC-адрес или комбинацию времени с серийным номером.

Реестр станций должен накладывать уникальное ограничение на Station ID. При конфликте регистрация останавливается, существующая запись не перезаписывается. Конфликт должен журналироваться и передаваться на ручную проверку.

## 4. Криптографическая идентичность станции

Station ID и криптографическая идентичность должны существовать независимо.

### 4.1. Ключевая пара

Предлагаемый порядок:
1. При первом доверенном вводе станция создаёт индивидуальную пару ключей.
2. Приватный ключ по возможности создаётся и хранится внутри TPM, secure element или другого аппаратного хранилища ключей.
3. Приватный ключ не передаётся серверу, операторскому приложению, установщику или другой станции.
4. Серверу/центру регистрации передаётся открытый ключ или запрос на выдачу сертификата.
5. После успешной регистрации публичный ключ связывается с Station ID в реестре.

Если выбранный контроллер не имеет TPM/secure element, допускается временное проектное решение с индивидуальным ключом, созданным криптографически стойким генератором и защищённым средствами ОС/правами доступа/шифрованием хранилища. Такой вариант должен быть явно отмечен как менее стойкий к физическому извлечению накопителя. Нельзя незаметно подменять индивидуальные ключи одним общим ключом для всех станций.

### 4.2. Сертификаты и доверие

Для сетевого взаимодействия рекомендуется управляемая инфраструктура сертификатов (PKI):
- собственный корневой центр сертификации хранится отдельно и используется ограниченно;
- для выпуска сертификатов используются промежуточные/операционные полномочия;
- каждой станции выдаётся индивидуальный сертификат;
- сертификат содержит идентификатор или ссылку на зарегистрированную аппаратную идентичность;
- предусматриваются срок действия, перевыпуск, ротация и отзыв;
- тестовые и эксплуатационные удостоверяющие центры/сертификаты разделяются.

Сертификат подтверждает связь публичного ключа с зарегистрированным субъектом, но проверка сертификата не заменяет проверку прав конкретного пользователя или команды.

### 4.3. Замена контроллера или ключа

При замене вычислительного модуля/контроллера:
- старый сертификат отзывается или помечается недействительным;
- выполняется контролируемое сервисное подтверждение физической станции;
- новый ключ генерируется на новом модуле;
- Station ID сохраняется только если по учётным и физическим данным это та же станция;
- событие замены и новая криптографическая идентичность попадают в аудит.

При полной замене физического изделия создаётся новая запись станции и новый Station ID. Точные критерии «ремонт той же станции» и «новая станция» требуется определить в регламенте обслуживания.

## 5. Первичная регистрация (provisioning)

### 5.1. Штатная онлайн-процедура

Предлагаемая последовательность:
1. Станция запускается в ограниченном режиме первичной регистрации; обычные управляющие команды и опасные физические операции недоступны.
2. Уполномоченный установщик физически активирует режим регистрации предусмотренным способом (например, сервисная кнопка/перемычка/ключ обслуживания).
3. Станция создаёт индивидуальную пару ключей и формирует запрос регистрации с публичным ключом, аппаратными сведениями, случайным challenge/nonce и версией ПО.
4. Оператор подтверждает регистрацию в доверенном сервисе и указывает/проверяет заводской серийный номер.
5. Реестр выделяет уникальный Station ID и проверяет отсутствие конфликтов по Station ID, серийному номеру и ключу.
6. Сервис регистрации связывает публичный ключ с Station ID и выдаёт индивидуальный сертификат/учётные данные устройства.
7. Станция проверяет подлинность ответа регистратора и сохраняет Station ID, сертификат и доверенные корни.
8. Регистрация фиксируется в аудите; станция выходит из ограниченного режима только после подтверждения завершения регистрации и локальной проверки конфигурации.

QR-код или напечатанный Station ID может использоваться для удобства поиска и привязки, но не является самостоятельным доказательством подлинности или права регистрации. Нельзя использовать общий пароль по умолчанию или один bootstrap-секрет для всего парка станций.

### 5.2. Офлайн-регистрация

Офлайн-регистрация должна быть предусмотрена, но не должна ослаблять защиту:
- предпочтительный вариант — заранее выданный сервером одноразовый регистрационный ваучер/пакет с ограниченным сроком и областью действия;
- регистрация сохраняется как PENDING_SYNC до сверки с центральным реестром;
- при последующей синхронизации уникальность Station ID, серийного номера и открытого ключа проверяется повторно;
- конфликт не приводит к автоматической перезаписи другой станции; станция помещается в режим разрешения конфликта;
- ваучер после использования становится недействительным.

Создание Station ID вручную без проверки глобального реестра допускается только как временный офлайн-процесс с последующей обязательной синхронизацией и проверкой. Постоянный общий bootstrap-пароль запрещён.

### 5.3. Привязка пользователя

Пользователь должен привязываться к станции после того, как:
- станция прошла криптографическую регистрацию;
- оператор аутентифицирован;
- оператор имеет право управлять связями пользователей/станций;
- станция подтверждена через доверенный канал или процедуру физического сопряжения.

Ввод одного только Station ID не должен создавать связь пользователя со станцией. Привязка должна фиксировать user_id, station_id, роль/разрешения, кто выполнил операцию, время и статус.

## 6. Криптографическая защита каналов

### 6.1. Общая политика

Все каналы управления, мониторинга, администрирования, передачи файлов и видео должны защищать конфиденциальность, целостность и подлинность стороны/сторон. Требование одинаково для:
- станция — сервер;
- операторское приложение — сервер;
- операторское приложение — станция по Wi-Fi;
- операторское приложение — станция по Ethernet/USB/service port или иному проводному интерфейсу;
- БАС — станция;
- удалённый видеопоток.

Предпочтительный IP-транспорт — TLS 1.3 по действующей редакции RFC 9846. Поддержка TLS должна подтверждаться выбранными библиотеками и ОС. Отключение проверки цепочки доверия/имени узла/назначения сертификата запрещено.

TLS защищает канал между узлами, но не заменяет авторизацию команд, локальные межблокировки, шифрование данных на накопителе и управление ключами.

Нельзя автоматически переходить на HTTP, незашифрованный TCP, открытый WebSocket или другой незашифрованный режим при ошибке TLS. Если выбранный компонент не поддерживает согласованный защищённый протокол, соединение отклоняется до отдельного инженерного решения.

### 6.2. Режимы соединения

| Канал | Минимальное требование |
|---|---|
| Станция — сервер | TLS 1.3; взаимная аутентификация станции индивидуальным сертификатом (mTLS) |
| Приложение — сервер | TLS 1.3; аутентификация пользователя и проверка прав на стороне сервиса |
| Приложение — станция напрямую | TLS 1.3; приложение проверяет сертификат станции, станция независимо аутентифицирует пользователя и проверяет его права |
| БАС — станция | Взаимная аутентификация и защищённый канал; конкретный протокол зависит от выбранного БАС и радиоинтерфейса |
| Камера/видеопоток | Защищённый транспорт и отдельная авторизация на просмотр; не выдавать открытый RTSP/поток в незащищённую сеть |
| Проводной сервисный интерфейс | Те же проверки аутентификации и полномочий; физический кабель не создаёт административный доступ |

Wi-Fi WPA2/WPA3 и сегментация сети рассматриваются как дополнительные сетевые меры, но не заменяют прикладную криптографическую защиту.

### 6.3. TLS-совместимость и алгоритмы

На этапе выбора библиотек следует проверить:
- поддержку RFC 9846;
- проверку цепочки сертификатов и статуса отзыва;
- надёжную генерацию случайных чисел;
- обновление криптографической библиотеки;
- запрет устаревших протоколов и небезопасных наборов шифров;
- безопасное хранение ключей;
- корректную обработку ошибки сертификата и истечения срока действия.

Конкретные наборы шифров и алгоритмы сертификатов не фиксируются до выбора вычислителей и библиотек. Не следует самостоятельно изобретать криптографические протоколы или заменять проверенные реализации самописным шифрованием.

## 7. Пароли, пользователи и сессии

### 7.1. Хранение паролей

Пароли пользователей:
- не хранятся в открытом виде;
- не шифруются обратимым способом для последующего восстановления;
- хранятся как результат специализированной медленной функции хеширования паролей с индивидуальной случайной солью;
- не передаются по незашифрованному каналу;
- не попадают в логи, диагностические отчёты, crash dump по возможности и резервные выгрузки в открытом виде.

Рекомендуемая функция для первой реализации — Argon2id по RFC 9106. Соль должна быть уникальной для каждой записи и генерироваться криптографически стойким генератором. Параметры памяти/итераций/параллелизма выбираются нагрузочным тестом на сервере/целевой платформе, а затем версионируются; не копировать параметры из примера RFC без измерения на целевом оборудовании.

При каждой успешной аутентификации следует иметь возможность определять устаревшие параметры хеширования и безопасно повышать их при следующей смене пароля/успешной проверке.

### 7.2. Политика учётных записей

Предусмотреть:
- индивидуальную учётную запись для каждого человека;
- отсутствие совместно используемых учётных записей операторов;
- ограничение частоты попыток входа и защиту от перебора;
- блокировку/временную задержку по политике после серии ошибок;
- проверку пароля на распространённость/компрометацию при задании или смене;
- поддержку менеджеров паролей и вставки пароля;
- многофакторную аутентификацию как минимум для администраторов удалённого доступа — рекомендуемое требование;
- принудительный отзыв сессий при блокировке пользователя, смене пароля, отзыве роли или отвязке от станции.

Минимальная длина и требования к паролям должны быть установлены отдельной парольной политикой с учётом применимого профиля безопасности. Не вводить искусственные требования вроде обязательной комбинации трёх классов символов без обоснования.

### 7.3. Сессии и токены

Сессии должны быть ограничены сроком жизни и областью полномочий. Токены не должны передаваться в URL или сохраняться в открытых логах. При отзыве пользователя или привязки доступ к конкретной станции прекращается, включая уже активные сессии. Обновление/продление токена должно предусматривать ротацию и обнаружение повторного использования.

## 8. Защита удалённых команд и повторов

Каждая управляющая команда должна быть связана с конкретной станцией и иметь как минимум:
- command_id — уникальный идентификатор команды;
- station_id — целевая станция;
- actor_id / user_id — инициатор;
- operation_id — идентификатор длительной операции, если создаётся;
- command_type и параметры;
- issued_at и expires_at;
- nonce или монотонный sequence number;
- идентификатор сессии/контекста авторизации;
- версию контракта.

Станция обязана самостоятельно проверить:
1. Подлинность канала/отправителя и действительность учётных данных.
2. Совпадение station_id с собственной постоянной идентичностью.
3. Полномочия пользователя на данный тип команды и данную станцию.
4. Срок действия команды и защиту от повторного использования nonce/sequence/command_id.
5. Допустимость команды по текущему состоянию и локальным правилам SafetyManager.
6. Отсутствие конфликта с уже выполняемой операцией.

Приложение не может само объявить команду разрешённой только потому, что пользователь видит кнопку. Поля user_id/role в сообщении клиента являются контекстом, но не самостоятельным доказательством полномочий: они должны подтверждаться доверенным сервером/станцией.

Команды, поставленные в очередь на сервере, должны оставаться привязанными к Station ID и иметь ограниченный срок действия. Станция не должна исполнять устаревшую команду после длительного отсутствия связи. Для потенциально опасных команд потеря ответа означает OUTCOME_UNKNOWN до сверки, а не повод автоматически повторить действие.

## 9. Защита данных на накопителях и обновлений

Предусмотреть:
- шифрование локального накопителя станции или чувствительных областей хранения;
- защиту ключей шифрования отдельно от данных, с использованием TPM/secure element, если доступно;
- невозможность получить приватный ключ станции простым извлечением накопителя, насколько это позволяет выбранная аппаратная платформа;
- шифрование резервных копий и секретной конфигурации;
- раздельное хранение эксплуатационных, тестовых и резервных ключей;
- цифровую подпись обновлений ПО/прошивок и проверку подписи до установки;
- отказ от установки повреждённого, неподписанного или подписанного недоверенным ключом пакета;
- журналирование установки, версии, результата и источника обновления.

Шифрование накопителя защищает данные при потере/извлечении носителя, но не заменяет контроль доступа работающей ОС и защиту устройства от физической компрометации.

## 10. Управление жизненным циклом ключей

Необходимо описать и протестировать:
- генерацию ключей;
- регистрацию публичной части;
- хранение закрытых ключей;
- выпуск и установку сертификата;
- плановую ротацию;
- отзыв при компрометации;
- замену контроллера;
- сброс к заводскому состоянию;
- передачу станции другому владельцу;
- вывод станции из эксплуатации;
- безопасное уничтожение/аннулирование ключей.

Один общий приватный ключ или общий пароль для всего парка станций запрещён. Ключи не должны храниться в Git, в исходном коде, в примерах конфигурации или в обычных логах.

## 11. Отказ и восстановление доверия

Если сертификат отозван, просрочен, не соответствует Station ID или не проходит проверку цепочки, защищённая сессия не устанавливается. Нельзя отключать проверку сертификата для обхода отказа.

Восстановление должно выполняться через документированный физически подтверждённый сервисный процесс с аудитом. Сервисный режим не является скрытым backdoor и не должен предоставлять безусловный доступ к опасным исполнительным операциям.

При подозрении на компрометацию:
1. Отозвать учётные данные устройства/сертификат.
2. Заблокировать удалённый доступ к станции до повторной регистрации.
3. Отозвать сессии операторов, если скомпрометированы пользовательские учётные данные.
4. Зафиксировать инцидент.
5. Выполнить сервисную проверку и повторное provisioning.

| Область | Проектное состояние |
|---|---|
| Station ID как постоянный уникальный идентификатор | Требование задано; формат UUIDv4 — предложение |

| Argon2id для хранения паролей | Предложение; параметры не выбраны |

## 14. Нормативные и технические источники

- [RFC 9562 — Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562.html): формат UUID и генерация UUIDv4.
- [RFC 9846 — The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/rfc/rfc9846.html): актуализированная спецификация TLS 1.3, опубликована в июле 2026 г.; заменяет RFC 8446.
- [RFC 9106 — Argon2 Memory-Hard Function](https://www.rfc-editor.org/rfc/rfc9106.html): Argon2id и рекомендации по выбору параметров.
- [NIST SP 800-63B-4 — Authentication and Authenticator Management](https://pages.nist.gov/800-63-4/sp800-63b.html): рекомендации по защите паролей и аутентификации.

Эти источники не являются доказательством соответствия проекта конкретному стандарту. Применимость формальных требований и законодательства должна быть проверена отдельно.
