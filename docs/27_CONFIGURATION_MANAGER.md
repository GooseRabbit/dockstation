# Спецификация менеджера конфигурации станции (ConfigurationManager)

**Предлагаемое имя программного компонента:** `ConfigurationManager`.  
**Статус:** ЧЕРНОВИК — логические границы согласованы, детальные контракты требуют проверки владельца проекта.  
**Редакция:** 0.1.  
**Дата:** 2026-11-07.  
**Основание:** DEC-054.

> Документ описывает логические обязанности и предварительные контракты. Он не выбирает формат хранения, накопитель, ОС, язык программирования, вычислительную платформу или криптографический алгоритм.

## 1. Назначение

ConfigurationManager получает сохранённую конфигурацию станции, декодирует её через отдельную абстракцию, проверяет и только затем предоставляет остальным компонентам как рабочую.

Он отвечает на вопрос: **«Какая конфигурация сохранена и прошла ли она обязательные проверки?»** Он не решает, безопасно ли выполнять физическое действие: это отдельная ответственность SafetyManager и соответствующего исполнителя.

## 2. Согласованное разделение ответственности

| Компонент | Ответственность |
|---|---|
| ConfigurationManager | Получение, декодирование и содержательная проверка конфигурации; предоставление проверенного снимка |
| DiagnosticsManager | Проверка доступности служб и оборудования по проверенному снимку; сбор диагностического отчёта |
| StationStateManager | Глобальное состояние и переходы; использование достоверного результата проверки конфигурации и самодиагностики |
| SafetyManager | Независимое решение ALLOW / DENY / UNKNOWN для конкретной операции |
| SettingsRepository | Логическая граница доступа к сохранённой записи |
| ConfigurationDecoderPort | Логическая граница преобразования записи в типизированного кандидата |

Это логические границы. Их размещение в одном процессе, разных процессах или на разных вычислительных устройствах не утверждено.

## 3. Обязанности и ограничения

ConfigurationManager должен:
1. Получать сохранённую конфигурацию через SettingsRepository.
2. Различать отсутствие записи, недоступность хранилища и ошибку чтения.
3. Декодировать запись без предположения о конкретном формате.
4. Проверять поддержку версии схемы.
5. Проверять наличие обязательных параметров.
6. Проверять типы, перечислимые значения, диапазоны и единицы только там, где критерии утверждены.
7. Проверять согласованность взаимосвязанных параметров по утверждённым правилам.
8. Формировать проверенный снимок только после успешного прохождения всех обязательных проверок.
9. Предоставлять результат и ревизию снимка через явные интерфейсы.

Не должен:
- подставлять значения по умолчанию вместо отсутствующих обязательных параметров;
- считать ноль или пустую строку заменой отсутствующих данных;
- объявлять неподтверждённое оборудование установленным или исправным;
- выдавать частично проверенный снимок как рабочий;
- переносить результат VALID на другую ревизию;
- управлять физическими устройствами или выдавать разрешения на опасные операции;
- изменять и сохранять настройки в первой read-only версии.

## 4. Логические зависимости

### 4.1. SettingsRepository

Предоставляет сохранённую запись и метаданные. Контракт различает: запись найдена; запись отсутствует; хранилище недоступно; ошибка чтения.

Порт не определяет файл, базу данных, энергонезависимую память или другой носитель и не задаёт транзакционный механизм конкретного хранилища.

### 4.2. ConfigurationDecoderPort

Преобразует сохранённую запись в типизированного кандидата `ConfigurationCandidate`. Декодер различает успешное декодирование, повреждённую или некорректную запись и неподдерживаемую версию схемы. Успешное декодирование не означает, что параметры допустимы или согласованы: это проверяет ConfigurationManager.

### 4.3. Нейтральное представление декодированных данных

Чтобы не выбирать формат хранения, декодер предоставляет данные как типизированное дерево `ConfigurationDocumentView`. Оно поддерживает значения `Null`, `Boolean`, `SignedInteger`, `UnsignedInteger`, `Number`, `String`, `Object`, `Array` и `Opaque`. Объект состоит из именованных полей; массив сохраняет порядок элементов. Значение `Opaque` сохраняет непроинтерпретированный фрагмент байтов, когда декодер не должен угадывать его смысл. `Unknown` означает незаданный/неизвестный тип узла, а не допустимую подмену значения.

Неизвестные поля остаются в дереве и не отбрасываются молча. Это только представление в памяти после декодирования. Оно не задаёт JSON/YAML/бинарную сериализацию, правила кодирования, файловую структуру или схему конкретных параметров.

Типы с суффиксом `View`, `std::string_view` и списки через указатель/размер не владеют памятью. Декодер и вызывающий слой обязаны обеспечить, чтобы буферы, строки, массивы и объекты оставались действительными всё время использования кандидата, issues и проверенного снимка. Адаптер не должен освобождать или менять опубликованные данные, пока их используют потребители.

### 4.4. Потребители

StationStateManager получает доверенное подтверждение успешной проверки для текущей ревизии. DiagnosticsManager получает проверенный снимок для формирования плана диагностики. Потребители не читают сохранённую запись в обход ConfigurationManager и не повторяют его проверки.

## 5. Версия схемы и ревизия конфигурации

- `schema_version` определяет структуру и правила интерпретации сохранённых данных.
- `configuration_revision` идентифицирует конкретную редакцию параметров.

Набор поддерживаемых версий передаётся CFG-F01 явно через
`ConfigurationSchemaVersionSetView`. В коде нет встроенного значения версии:
пока владелец проекта не утвердил базовую версию схемы, production-набор не
задаётся. Версия рассматривается как непрозрачный идентификатор, а не как
обязательно числовая строка или SemVer. Сравнение выполняется точно, с учётом
регистра. Идентификатор должен быть непустым и не должен содержать ASCII-пробелы,
управляющие символы или NUL.

Изменение параметров не обязательно меняет версию схемы. Ревизия сама по себе не доказывает корректность. Результат VALID должен относиться к той же ревизии, что и снимок; после замены снимка старое подтверждение не применяется к новой ревизии.

## 6. Предлагаемые результаты

### 6.1. Статусы

| Статус | Значение |
|---|---|
| VALID | Конфигурация получена, декодирована и прошла все обязательные проверки |
| NOT_FOUND | Сохранённая конфигурация отсутствует |
| UNAVAILABLE | Хранилище или обязательная зависимость недоступны |
| READ_ERROR | Ошибка чтения сохранённой записи |
| DECODE_ERROR | Запись невозможно корректно декодировать |
| UNSUPPORTED_VERSION | Версия схемы не поддерживается |
| INVALID | Структура или содержимое не прошло обязательную проверку |
| INTERNAL_ERROR | Внутренняя ошибка обработки |

Статусы не сводятся к Boolean. Результат может содержать известные ревизию и версию схемы, список проблем и предупреждений, а также проверенный снимок. Снимок существует только при VALID.

Для CFG-F01: пустая или некорректная версия кандидата даёт `INVALID`;
корректная версия, отсутствующая в разрешённом наборе, даёт
`UNSUPPORTED_VERSION`; пустой, дублирующийся или некорректный набор политики
даёт `INTERNAL_ERROR`. Тестовые значения версий не являются утверждённым
форматом или перечнем версий проекта.

### 6.2. Проблемы проверки

Каждая проблема содержит машинный reason_code, идентификатор/путь параметра (если применимо), уровень ERROR или WARNING и короткое описание без секретных значений. Любая ошибка ERROR исключает VALID. Предупреждения допустимы только для необязательных параметров, если обязательные проверки пройдены.

### 6.3. ValidatedConfigurationSnapshot

Снимок содержит типизированную конфигурацию, `schema_version`, `configuration_revision` и документированное дерево параметров. Доступ к его полям предоставляется только через операции чтения; прямых сеттеров нет. Обычный потребитель не может создать снимок самостоятельно: конструктор закрыт, а единственная предусмотренная точка создания — CFG-F06 после успешной проверки. Снимок логически неизменяем для получателей. Конкретный состав параметров ещё не утверждён.

## 7. Правила проверки

1. Версия схемы должна быть явно получена и входить в перечень поддерживаемых версий. Неизвестная версия не интерпретируется по догадке.
2. Обязательность параметров задаётся явной политикой CFG-F02, сформированной по утверждённым требованиям и согласованному профилю. Реализация принимает перечень путей явно; полный production-перечень остаётся открытым (CFG-Q02) и не придумывается в коде.
3. Типы, значения, диапазоны и единицы проверяются только при наличии утверждённых критериев.
4. Взаимная согласованность проверяется только по явно определённым правилам.
5. Политика неизвестных дополнительных полей остаётся открытой. Нельзя молча отбрасывать поле, если это может изменить смысл конфигурации.

Отсутствие необязательного оборудования не является отказом, но и не означает, что это оборудование исправно.

## 8. Взаимодействие при запуске

1. ConfigurationManager получает сохранённую запись.
2. Декодирует её и выполняет обязательные проверки.
3. При успехе предоставляет проверенный снимок и VALID.
4. StationStateManager использует доверенное подтверждение результата в контексте запуска.
5. DiagnosticsManager формирует план по проверенному снимку и проверяет службы.
6. StationStateManager получает диагностический отчёт и применяет правила переходов.

Внешний event payload не является доказательством валидности конфигурации. Подтверждение должно поступать через доверенную границу и относиться к используемой ревизии. ConfigurationManager сам не формирует INITIALIZATION_COMPLETED или SELF_TEST_COMPLETED и не выполняет переходы SSM.

## 9. Отказобезопасное поведение

| Ситуация | Результат |
|---|---|
| Запись отсутствует | NOT_FOUND; не создавать фиктивную конфигурацию |
| Хранилище недоступно | UNAVAILABLE |
| Ошибка чтения | READ_ERROR |
| Повреждённая запись | DECODE_ERROR |
| Неизвестная версия | UNSUPPORTED_VERSION |
| Нет обязательного параметра | INVALID |
| Значение не соответствует утверждённому критерию | INVALID |
| Противоречие по утверждённым правилам | INVALID |
| Внутренняя ошибка | INTERNAL_ERROR; частичный снимок не публикуется |

Сохранённый старый снимок не доказывает успешную текущую загрузку. Правила восстановления или отката на прежнюю ревизию требуют отдельного решения. Проверка не запускает приводы, зарядку, крышку и другие физические действия.

## 10. Границы первой версии

Первый срез read-only: получение, декодирование, проверка и предоставление проверенного снимка.

Не входят: редактирование и запись настроек, удалённая настройка, миграция схем, резервное копирование, откат/восстановление, выбор формата хранения и алгоритма проверки целостности.

`save_configuration()` и `apply_configuration_change()` остаются возможными функциями следующего этапа и потребуют отдельного контракта авторизации, атомарной записи и аудита.

## 12. План тестирования

Тесты выполняются на ПК с fake-портами и не доказывают сохранность данных на реальном носителе при потере питания.

Обязательны сценарии:
1. Корректная запись → VALID и проверенный снимок.
2. Нет записи → NOT_FOUND, снимка нет.
3. Хранилище недоступно → UNAVAILABLE.
4. Ошибка чтения → READ_ERROR.
5. Повреждённая запись → DECODE_ERROR.
6. Поддерживаемая и неподдерживаемая версия схемы.
7. Нет обязательного параметра → INVALID.
8. Недопустимые значения и утверждённые противоречия → INVALID.
9. Ошибка любой обязательной проверки исключает создание снимка.
10. Результат VALID и снимок относятся к одной ревизии.
11. Необязательное оборудование не объявляется исправным автоматически.
12. Предупреждения не скрывают ошибки ERROR; секреты не выводятся в диагностике.

### 27.9. Проверка типов и значений (CFG-F03)

CFG-F03 получает явный `ConfigurationValueRuleSetView`. Каждое правило содержит сегментированный путь, ожидаемый точный тип, необязательные числовые минимум/максимум того же типа и/или точный список допустимых скалярных значений. Правила не встроены в ConfigurationManager: вызывающий слой передаёт их явно. Пустая, противоречивая или неоднозначная политика возвращает `INTERNAL_ERROR`.

Проверка различает отсутствующее поле, неразрешимый/неоднозначный путь, несовпадение типа, выход за нижнюю/верхнюю границу и значение вне явного перечня. Числа с плавающей точкой должны быть конечными. Неявного преобразования между signed, unsigned и Number нет. Буфер issues заполняется только после подсчёта полного числа проблем; недостаточный буфер не приводит к выдаче частичного результата.

Нейтральное дерево пока не содержит метаданных единиц измерения. Поэтому CFG-F03 не преобразует и не проверяет единицы. Их представление и правила согласования остаются открытым требованием. Production-диапазоны и перечисления не задаются этой функцией и не придумываются реализацией.


### 27.10. Проверка взаимной согласованности (CFG-F04)

CFG-F04 получает явный ConfigurationConsistencyRuleSetView. Одно правило задаёт два сегментированных пути, общий ожидаемый скалярный тип и операцию сравнения: Equal, NotEqual, LessThan, LessThanOrEqual, GreaterThan или GreaterThanOrEqual. Оба поля должны существовать и соответствовать указанному типу. Равенство/неравенство разрешено для Null, Boolean, SignedInteger, UnsignedInteger, Number и String; порядковые операции — только для числовых типов.

Сравнение типов точное: signed, unsigned и Number не приводятся друг к другу. Number сравнивается без допуска; NaN и Inf недопустимы. Object, Array и Opaque не сравниваются. Правила должны иметь диагностическое имя отношения; набор непустой, корректный и без дубликатов.

CFG-F04 проверяет только прямые парные отношения. Условные зависимости и составные выражения не реализованы; производственные зависимости параметров не заданы и не придумываются. Ошибки кандидата возвращают INVALID; повреждённая политика/структура дерева или недостаточный issue buffer возвращает INTERNAL_ERROR. Буфер проблем заполняется только после предварительного подсчёта; усечённый список не возвращается.


### 27.11. Объединённая проверка конфигурации (CFG-F05)

CFG-F05 принимает ConfigurationValidationPolicyView: явные наборы версий, обязательных полей, правил значений и правил согласованности. Каждый набор обязателен и должен быть непустым. Функция не содержит production-настроек.

Порядок строгий: CFG-F01 → CFG-F02 → CFG-F03 → CFG-F04. Если версия схемы отсутствует, некорректна, не поддерживается или политика версий повреждена, CFG-F05 сразу возвращает результат F01; дальнейшая интерпретация документа не выполняется. Остальные этапы запускаются только после успешной проверки версии.

Issues этапов F01-F04 объединяются в один caller-owned buffer и сохраняют порядок этапов. Перед возвратом CFG-F05 записывает в ConfigurationValidationResult validated_schema_version и validated_configuration_revision точного кандидата, к которому относится результат. WARNING сохраняются и не блокируют VALID. Любой INVALID даёт итог INVALID, если не возник INTERNAL_ERROR; INTERNAL_ERROR имеет приоритет, но уже собранные диагностические issues не теряются. Неизвестный статус подвалидатора или некорректная структура его результата закрывает проверку через INTERNAL_ERROR. ERROR в результате VALID либо отсутствие ERROR в результате INVALID/INTERNAL_ERROR также считается нарушением контракта. VALID возможен только при четырёх успешных этапах и отсутствии ERROR.

До запуска проверок вызывающий код обязан предоставить буфер ёмкостью не менее 1 + суммы размеров наборов required_fields, value_rules и consistency_rules. Это worst-case количество issues с одним дополнительным слотом для возможного WARNING от F01. Переполнение при расчёте ёмкости, null или недостаточный буфер приводят к INTERNAL_ERROR до записи в пользовательский буфер. Ошибки версии возвращаются напрямую из F01 и не используют общий буфер; успешный F01 может добавить в общий буфер один WARNING. CFG-F05 не создаёт snapshot и не выполняет загрузку/сохранение.

### 27.12. Создание проверенного снимка (CFG-F06)

`build_validated_configuration_snapshot(candidate, validation)` принимает результат CFG-F05 и создаёт закрытый `ValidatedConfigurationSnapshot` только при `validation.status == Valid`. Результат F05 должен содержать `validated_schema_version` и `validated_configuration_revision`; обе строки точно сравниваются с соответствующими полями кандидата. Пустая версия или ревизия, отсутствие привязки или несовпадение не допускают публикацию снимка и возвращают `InternalError`.

При `Invalid`, `UnsupportedVersion` и `InternalError` snapshot отсутствует, статус и корректный список issues сохраняются. Для `Valid` список может содержать только корректные `Warning`. Наличие `Error`, неизвестной серьёзности/статуса, повреждённого списка или пустого диагностического кода/описания возвращает `InternalError` без snapshot. WARNING остаются доступными потребителю.

CFG-F06 не повторяет CFG-F01…F05 и не исправляет кандидата. Снимок хранит не владеющее памятью представление того же документа; backing storage должен оставаться неизменным и действительным всё время использования snapshot. Никакого конкретного формата хранения, набора параметров или production-политики функция не задаёт.
