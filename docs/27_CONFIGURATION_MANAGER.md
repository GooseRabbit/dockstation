# Спецификация менеджера конфигурации станции (ConfigurationManager)

**Предлагаемое имя программного компонента:** `ConfigurationManager`.  
**Статус:** ЧЕРНОВИК — логические границы согласованы, детальные контракты требуют проверки владельца проекта.  
**Редакция:** 0.1.  
**Дата:** 2026-11-07.  
**Основание:** DEC-054.

> Документ описывает логические обязанности и предварительные контракты. Он не выбирает формат хранения, накопитель, ОС, язык программирования, вычислительную платформу или криптографический алгоритм.

## 1. Назначение

ConfigurationManager получает сохранённую конфигурацию станции, декодирует её через отдельную абстракцию, проверяет и только затем предоставляет остальным компонентам как рабочую.

Он отвечает на вопрос: **«Какая конфигурация сохранена и прошла ли она обязательные проверки?»** Он не решает, безопасно ли выполнять физическое действие: это отдельная ответственность SafetyManager и соответствующего исполнителя.

## 2. Согласованное разделение ответственности

| Компонент | Ответственность |
|---|---|
| ConfigurationManager | Получение, декодирование и содержательная проверка конфигурации; предоставление проверенного снимка |
| DiagnosticsManager | Проверка доступности служб и оборудования по проверенному снимку; сбор диагностического отчёта |
| StationStateManager | Глобальное состояние и переходы; использование достоверного результата проверки конфигурации и самодиагностики |
| SafetyManager | Независимое решение ALLOW / DENY / UNKNOWN для конкретной операции |
| SettingsRepository | Логическая граница доступа к сохранённой записи |
| ConfigurationDecoderPort | Логическая граница преобразования записи в типизированного кандидата |

Это логические границы. Их размещение в одном процессе, разных процессах или на разных вычислительных устройствах не утверждено.

## 3. Обязанности и ограничения

ConfigurationManager должен:
1. Получать сохранённую конфигурацию через SettingsRepository.
2. Различать отсутствие записи, недоступность хранилища и ошибку чтения.
3. Декодировать запись без предположения о конкретном формате.
4. Проверять поддержку версии схемы.
5. Проверять наличие обязательных параметров.
6. Проверять типы, перечислимые значения, диапазоны и единицы только там, где критерии утверждены.
7. Проверять согласованность взаимосвязанных параметров по утверждённым правилам.
8. Формировать проверенный снимок только после успешного прохождения всех обязательных проверок.
9. Предоставлять результат и ревизию снимка через явные интерфейсы.

Не должен:
- подставлять значения по умолчанию вместо отсутствующих обязательных параметров;
- считать ноль или пустую строку заменой отсутствующих данных;
- объявлять неподтверждённое оборудование установленным или исправным;
- выдавать частично проверенный снимок как рабочий;
- переносить результат VALID на другую ревизию;
- управлять физическими устройствами или выдавать разрешения на опасные операции;
- изменять и сохранять настройки в первой read-only версии.

## 4. Логические зависимости

### 4.1. SettingsRepository

Предоставляет сохранённую запись и метаданные. Контракт различает: запись найдена; запись отсутствует; хранилище недоступно; ошибка чтения.

Порт не определяет файл, базу данных, энергонезависимую память или другой носитель и не задаёт транзакционный механизм конкретного хранилища.

### 4.2. ConfigurationDecoderPort

Преобразует запись в типизированного кандидата ConfigurationCandidate. Декодер различает успешное декодирование, повреждённую запись и неподдерживаемую версию схемы. Успешное декодирование не означает, что параметры допустимы или согласованы: это проверяет ConfigurationManager.

### 4.3. Потребители

StationStateManager получает доверенное подтверждение успешной проверки для текущей ревизии. DiagnosticsManager получает проверенный снимок для формирования плана диагностики. Потребители не читают сохранённую запись в обход ConfigurationManager и не повторяют его проверки.

## 5. Версия схемы и ревизия конфигурации

- `schema_version` определяет структуру и правила интерпретации сохранённых данных.
- `configuration_revision` идентифицирует конкретную редакцию параметров.

Изменение параметров не обязательно меняет версию схемы. Ревизия сама по себе не доказывает корректность. Результат VALID должен относиться к той же ревизии, что и снимок; после замены снимка старое подтверждение не применяется к новой ревизии.

## 6. Предлагаемые результаты

### 6.1. Статусы

| Статус | Значение |
|---|---|
| VALID | Конфигурация получена, декодирована и прошла все обязательные проверки |
| NOT_FOUND | Сохранённая конфигурация отсутствует |
| UNAVAILABLE | Хранилище или обязательная зависимость недоступны |
| READ_ERROR | Ошибка чтения сохранённой записи |
| DECODE_ERROR | Запись невозможно корректно декодировать |
| UNSUPPORTED_VERSION | Версия схемы не поддерживается |
| INVALID | Структура или содержимое не прошло обязательную проверку |
| INTERNAL_ERROR | Внутренняя ошибка обработки |

Статусы не сводятся к Boolean. Результат может содержать известные ревизию и версию схемы, список проблем и предупреждений, а также проверенный снимок. Снимок существует только при VALID.

### 6.2. Проблемы проверки

Каждая проблема содержит машинный reason_code, идентификатор/путь параметра (если применимо), уровень ERROR или WARNING и короткое описание без секретных значений. Любая ошибка ERROR исключает VALID. Предупреждения допустимы только для необязательных параметров, если обязательные проверки пройдены.

### 6.3. ValidatedConfigurationSnapshot

Снимок содержит типизированную конфигурацию, schema_version, configuration_revision и сведения для сопоставления с результатом проверки. Он логически неизменяем для получателей. Получатели читают предназначенные им параметры, но не редактируют общий активный снимок. Точная структура ещё не утверждена.

## 7. Правила проверки

1. Версия схемы должна быть явно получена и входить в перечень поддерживаемых версий. Неизвестная версия не интерпретируется по догадке.
2. Обязательность параметров задаётся утверждёнными требованиями и согласованным профилем. Неутверждённый перечень не придумывается в коде.
3. Типы, значения, диапазоны и единицы проверяются только при наличии утверждённых критериев.
4. Взаимная согласованность проверяется только по явно определённым правилам.
5. Политика неизвестных дополнительных полей остаётся открытой. Нельзя молча отбрасывать поле, если это может изменить смысл конфигурации.

Отсутствие необязательного оборудования не является отказом, но и не означает, что это оборудование исправно.

## 8. Взаимодействие при запуске

1. ConfigurationManager получает сохранённую запись.
2. Декодирует её и выполняет обязательные проверки.
3. При успехе предоставляет проверенный снимок и VALID.
4. StationStateManager использует доверенное подтверждение результата в контексте запуска.
5. DiagnosticsManager формирует план по проверенному снимку и проверяет службы.
6. StationStateManager получает диагностический отчёт и применяет правила переходов.

Внешний event payload не является доказательством валидности конфигурации. Подтверждение должно поступать через доверенную границу и относиться к используемой ревизии. ConfigurationManager сам не формирует INITIALIZATION_COMPLETED или SELF_TEST_COMPLETED и не выполняет переходы SSM.

## 9. Отказобезопасное поведение

| Ситуация | Результат |
|---|---|
| Запись отсутствует | NOT_FOUND; не создавать фиктивную конфигурацию |
| Хранилище недоступно | UNAVAILABLE |
| Ошибка чтения | READ_ERROR |
| Повреждённая запись | DECODE_ERROR |
| Неизвестная версия | UNSUPPORTED_VERSION |
| Нет обязательного параметра | INVALID |
| Значение не соответствует утверждённому критерию | INVALID |
| Противоречие по утверждённым правилам | INVALID |
| Внутренняя ошибка | INTERNAL_ERROR; частичный снимок не публикуется |

Сохранённый старый снимок не доказывает успешную текущую загрузку. Правила восстановления или отката на прежнюю ревизию требуют отдельного решения. Проверка не запускает приводы, зарядку, крышку и другие физические действия.

## 10. Границы первой версии

Первый срез read-only: получение, декодирование, проверка и предоставление проверенного снимка.

Не входят: редактирование и запись настроек, удалённая настройка, миграция схем, резервное копирование, откат/восстановление, выбор формата хранения и алгоритма проверки целостности.

`save_configuration()` и `apply_configuration_change()` остаются возможными функциями следующего этапа и потребуют отдельного контракта авторизации, атомарной записи и аудита.

## 12. План тестирования

Тесты выполняются на ПК с fake-портами и не доказывают сохранность данных на реальном носителе при потере питания.

Обязательны сценарии:
1. Корректная запись → VALID и проверенный снимок.
2. Нет записи → NOT_FOUND, снимка нет.
3. Хранилище недоступно → UNAVAILABLE.
4. Ошибка чтения → READ_ERROR.
5. Повреждённая запись → DECODE_ERROR.
6. Поддерживаемая и неподдерживаемая версия схемы.
7. Нет обязательного параметра → INVALID.
8. Недопустимые значения и утверждённые противоречия → INVALID.
9. Ошибка любой обязательной проверки исключает создание снимка.
10. Результат VALID и снимок относятся к одной ревизии.
11. Необязательное оборудование не объявляется исправным автоматически.
12. Предупреждения не скрывают ошибки ERROR; секреты не выводятся в диагностике.

## 14. Критерии готовности спецификации

- [x] Логические границы ConfigurationManager, DiagnosticsManager, StationStateManager и SafetyManager согласованы (DEC-054).

- [ ] Уточнены типы данных и сигнатуры портов.
- [ ] Определён перечень обязательных параметров по утверждённым требованиям.
- [ ] Уточнены коды ошибок и политика неизвестных полей.
- [ ] Согласован пофункциональный план реализации.
- [ ] Проверены связи с SSM и DiagnosticsManager.
