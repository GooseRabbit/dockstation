# Алгоритмы работы док-станции

**Статус:** предварительное описание.  
**Редакция:** 0.2.3.
**Дата актуализации:** 2026-11-03.

## 1. Назначение

Документ описывает последовательность действий станции от включения до повторного ожидания БАС. Алгоритмы являются основой для будущих конечных автоматов и программных задач.

Все временные интервалы, пороги, допуски и команды автопилоту должны быть определены после выбора оборудования. Если значение не указано, его нельзя придумывать в коде.

## 2. Основные состояния станции

| Состояние | Назначение |
|---|---|
| ВЫКЛЮЧЕНА | Станция не выполняет программную работу |
| ЗАПУСК | Инициализация вычислителей и оборудования |
| САМОПРОВЕРКА | Проверка датчиков, приводов, связи и питания |
| ОЖИДАНИЕ | Станция ожидает возвращения закреплённого за ней БАС |
| ОБНАРУЖЕНИЕ | Получено предварительное событие обнаружения |
| АУТЕНТИФИКАЦИЯ | Проверка подлинности станции и БАС |
| АВТОРИЗАЦИЯ | Проверка разрешённых действий данного БАС |
| ПОДГОТОВКА ПРИЁМА | Проверка площадки, погоды и механизмов |
| ОТКРЫТИЕ КРЫШКИ | Управляемое открытие с контролем положения |
| СОПРОВОЖДЕНИЕ ПОСАДКИ | Обработка визуальных измерений и обмен с автопилотом |
| ПОДТВЕРЖДЕНИЕ ПОСАДКИ | Проверка касания, устойчивости и остановки двигателей |
| ЗАКРЫТИЕ КРЫШКИ | Закрытие корпуса после подтверждения безопасной посадки |
| ОБСЛУЖИВАНИЕ В ЗАКРЫТОМ КОРПУСЕ | Зарядка и получение материалов |
| ОЖИДАНИЕ ЗАДАНИЯ | Ожидание/проверка следующей допустимой миссии |
| ПОДГОТОВКА ВЫЛЕТА | Предполётные проверки и проверка погоды |
| ОТКРЫТИЕ ДЛЯ ВЫЛЕТА | Открытие крышки для штатного вылета |
| ВЫЛЕТ | Контроль запуска и освобождения площадки |
| САМООЧИСТКА | Очистка свободной площадки после вылета |
| ОГРАНИЧЕННЫЙ РЕЖИМ | Часть функций запрещена, безопасные функции могут оставаться доступными |
| ОЖИДАНИЕ ВМЕШАТЕЛЬСТВА | Требуется удалённое или физическое решение специалиста |
| ВОССТАНОВЛЕНИЕ | Повторная диагностика после отказа или перезапуска |
| АВАРИЙНОЕ СОСТОЯНИЕ | Выполнение конкретной защитной реакции; автоматический возврат к работе не предполагается |

Состояния станции и состояния отдельных модулей не следует смешивать. Например, зарядка может быть завершена, а передача файлов ещё продолжаться.

Станция может иметь несколько зарегистрированных/закреплённых БАС. Для одного физического цикла выбирается один целевой БАС; одна зона приёма и обслуживания одновременно работает только с одним аппаратом. Обнаружение неизвестного БАС не добавляет его в список разрешённых и не даёт права на приём. Способ обнаружения и аутентификации может различаться между моделями БАС.

Переход из ограниченного режима в штатную работу допускается только после повторной проверки причин ограничения.

### 3.1. Автоматический переход между миссиями

После обслуживания станция не ждёт обязательного подтверждения специалиста после каждой миссии.

Следующее задание может выполняться автоматически только при наличии заранее разрешённой миссии и выполнении всех проверок. Механизм предварительного разрешения миссий, срок действия заданий, допустимые районы/маршруты и ограничения очереди должны быть определены отдельно.

Удалённое наблюдение и право специалиста остановить дальнейшую автоматизацию сохраняются как проектируемые функции.

Команда STOP_AUTOMATION останавливает подготовку следующих автоматических миссий. Сама по себе она не означает возврат или принудительную посадку БАС, который уже находится в полёте.

До допуска следующей миссии проверяются локальный резерв хранения для ожидаемых материалов и настроенный предел числа автоматических циклов без физического осмотра. При недостатке места или достижении предела дальнейший автоматический вылет блокируется с указанием причины.

### 3.2. Приоритетный приём и невозможность приёма

«Приоритетный приём» пока не является готовым алгоритмом и не означает игнорирование физических ограничений. Это отдельный режим, который ещё нужно определить.

Станция должна передать БАС достоверный статус готовности/неготовности и причину. При отказе крышки, занятой площадке, недостоверном позиционировании или недопустимых погодных условиях дальнейшее действие выполняется по заранее согласованному бортовому алгоритму: ожидание, повторный заход, альтернативная площадка или иной поддерживаемый вариант.

Станция не должна молча возвращаться к ожиданию, пока БАС остаётся в воздухе. Для отдельных моделей БАС в дальнейшем может быть разработан дополнительный сценарий передачи альтернативного маршрута/площадки на борт, но он не считается частью текущего согласованного алгоритма и требует отдельного интерфейса.

## 4. Обнаружение и идентификация

### 4.1. Назначение

Станция должна отличать зарегистрированный возвращающийся БАС от случайных радиоустройств и посторонних объектов.

### 4.2. Последовательность

1. Служба обнаружения сканирует предусмотренные для выбранной конфигурации радиоканалы/интерфейсы.
2. При обнаружении подходящего сигнала формируется событие.
3. Станция пытается установить соединение.
4. Выполняется аутентификация устройства по механизму, утверждённому для конкретной модели/конфигурации БАС и станции. До выбора и проверки такого механизма аутентификация считается нереализованной. Bluetooth-имя, MAC-адрес и уровень сигнала не могут заменять аутентификацию.
5. Проверяется, что идентичность БАС присутствует в списке зарегистрированных для этой станции, и что именно этому БАС разрешён текущий цикл.
6. Камера или другой датчик подтверждает физическое присутствие аппарата и, где это реализуемо, его соответствие аутентифицированной сессии.
7. Событие передаётся менеджеру состояний.

Bluetooth-имя, MAC-адрес и сила сигнала могут помогать обнаружению, но не должны быть единственным механизмом авторизации или точного измерения расстояния.

### 4.3. Отказы

- устройство не найдено;
- соединение не установлено;
- аутентификация не пройдена;
- визуальное подтверждение отсутствует;
- сигнал потерян;
- обнаружено несколько устройств;
- данные противоречат друг другу.

Для каждого отказа следует фиксировать код, время, источник и допустимое дальнейшее действие.

## 5. Подготовка к приёму

До открытия крышки проверяются:

- нет ли на площадке постороннего предмета;
- нет ли на площадке другого БАС;
- исправны ли датчики положения крышки;
- исправен ли привод;
- доступно ли питание;
- исправны ли необходимые средства связи;
- доступны ли данные метеостанции;
- не активна ли очистка или зарядка;
- не находится ли станция в аварийном состоянии.

Разрешение на приём не должно автоматически означать разрешение на плановый вылет. Это разные операции и могут иметь разные погодные ограничения.

Если условия штатного приёма не выполнены, станция должна использовать заранее согласованный сценарий: ожидание, повторный заход, альтернативная площадка или иное действие, поддерживаемое автопилотом. Станция не должна импровизировать команды полёта.

## 6. Открытие крышки

1. Получить команду на открытие от менеджера состояний.
2. Проверить разрешение системы безопасности.
3. Проверить отсутствие несовместимых операций.
4. Запустить привод.
5. Контролировать положение и нагрузку.
6. Остановить привод при достижении конечного положения.
7. Подтвердить состояние «открыта».
8. В исключительном сценарии при подозрении на неисправность крышки может потребоваться дополнительное подтверждение уполномоченного оператора перед запросом открытия. Подтверждение не заменяет ALLOW от SafetyManager, достоверную обратную связь и локальные межблокировки; при DENY/UNKNOWN или запрете защитного контура открытие не выполняется.
9. При тайм-ауте, заклинивании или противоречии датчиков остановить движение и зарегистрировать отказ.

Открытие не подтверждается только фактом подачи питания на двигатель.

## 7. Точная посадка

### 7.1. Предварительный вариант

- на посадочной площадке размещается визуальный маркер;
- камера обнаруживает маркер;
- алгоритм оценивает относительное положение и ориентацию;
- оценивается качество измерения;
- данные передаются штатному автопилоту через согласованный протокол;
- автопилот выполняет корректировку траектории;
- станция контролирует качество сопровождения и состояния процесса.

### 7.2. Условия достоверности

Нужно контролировать:

- видимость маркера;
- качество изображения;
- корректность калибровки камеры;
- известные геометрические размеры маркера;
- координатные системы и ориентации;
- задержку измерений и передачи;
- частоту обновления;
- достоверность временной метки;
- допустимую область измерения.

Нельзя подавать в автопилот координаты без понимания системы координат, единиц измерения и направления осей.

### 7.3. Потеря маркера

При потере маркера:

1. Пометить измерение как недействительное.
2. Прекратить выдачу устаревших поправок.
3. Передать автопилоту предусмотренный статус недостоверности/потери сопровождения.
4. Выполнить только заранее согласованную реакцию автопилота.
5. Зарегистрировать событие.

Конкретные команды и безопасный сценарий определяются по документации выбранного автопилота и испытаниям. Не следует придумывать их по названию протокола.

## 8. Подтверждение посадки

Нужно использовать несколько независимых признаков, например:

- сообщение штатного автопилота о посадке;
- состояние DISARMED или эквивалентное;
- датчик присутствия на площадке;
- датчик нагрузки;
- визуальное подтверждение неподвижного аппарата.

Набор признаков определяется после выбора оборудования. Ни один отдельный сигнал не должен автоматически считаться абсолютным доказательством безопасного состояния.

После подтверждения:

1. Запретить операции, несовместимые с присутствием БАС.
2. Проверить отсутствие вращения двигателей по доступным достоверным данным.
3. Убедиться, что аппарат устойчиво находится в посадочном положении.
4. Разрешить дальнейшие операции обслуживания.

Для первой версии принято решение закрывать крышку после посадки и перед обычным обслуживанием внутри корпуса. Это допустимо только после отдельного подтверждения безопасной геометрии, отсутствия контакта с аппаратом и препятствий. Если подтверждение невозможно, крышка остаётся в текущем безопасном положении, штатное закрытое обслуживание не начинается, несовместимые операции блокируются, специалист уведомляется.

Если БАС находится на площадке при открытой крышке и требуется вмешательство, зарядка и обслуживание не начинаются, оператор уведомляется, а автоматическое закрытие не выполняется без повторного подтверждения безопасного положения БАС и зоны крышки. Допустимое время ожидания и действия при осадках определяются отдельной процедурой после выбора конструкции.

## 9. Обслуживание: зарядка и данные

После подтверждения безопасного состояния два процесса могут выполняться параллельно.

### 9.1. Зарядка

1. Проверить положение БАС.
2. Проверить взаимное положение катушек.
3. Получить разрешение BMS и проверить профиль батареи.
4. Проверить температуры.
5. Проверить отсутствие посторонних металлических предметов.
6. Проверить силовую часть.
7. Запустить зарядку.
8. Контролировать ток, напряжение, мощность и температуру.
9. При достижении целевого состояния завершить передачу энергии.
10. При отказе выполнить безопасное отключение и зафиксировать причину.

Нельзя задавать напряжение и ток только по номинальному напряжению аккумулятора. Необходимы спецификация батареи и требования её BMS.

### 9.2. Получение материалов

1. Установить связь с БАС.
2. Аутентифицировать устройства.
3. Запросить манифест файлов.
4. Проверить свободное место.
5. Создать задание передачи.
6. Получать файлы блоками.
7. Проверять блоки и целостность итогового файла.
8. Сохранить локальную копию.
9. Добавить материал в очередь сервера.
10. Получить подтверждение сервера.
11. Зарегистрировать результат.

## 10. Подготовка следующего вылета

Во время штатного обслуживания крышка должна быть закрыта. Перед зарядкой и передачей материалов станция повторно подтверждает закрытое положение, безопасное положение БАС и наличие питания бортовой электроники. Закрытый корпус не должен нарушать связь с БАС, обмен с BMS и зарядку; это подтверждается испытаниями.

Перед вылетом проверяются:

- действующая и неотозванная миссия, адресованная выбранному БАС;
- срок действия миссии и обязательный признак ручного подтверждения (REQUIRED / NOT_REQUIRED / UNKNOWN); UNKNOWN или отсутствующий признак блокирует автоматический вылет;
- разрешение на автоматическое продвижение и отсутствие команды STOP_AUTOMATION;
- локальная квота миссий на случай недоступности сервера: по умолчанию при недоступности сервера вылет запрещён; допускается только явно назначенная действующая квота — заданное число миссий либо до ручного удаления задания;
- выбранный оператором критерий завершения передачи: LOCAL_COMPLETE или SERVER_CONFIRMED; соответствующий статус должен быть подтверждён для обязательных материалов;
- достаточный свободный резерв локального хранилища для ожидаемых материалов следующей миссии;
- не достигнут предел автоматических циклов без физического осмотра;
- заряд аккумулятора;
- отсутствие критических ошибок БАС;
- доступность требуемых материалов или завершённость их копирования — согласно принятой политике;
- наличие заранее загруженного и допустимого задания;
- действительность и разрешённость задания по согласованной политике;
- отсутствие запрета на автоматический переход;
- отсутствие команды остановки автоматических циклов.
- состояние станции;
- погодные условия;
- готовность крышки;
- готовность посадочной/стартовой площадки;
- наличие связи, требуемой для конкретной миссии.

Если сервер недоступен, новый вылет по умолчанию запрещён. Исключение возможно только при наличии явно назначенной локальной квоты заранее разрешённых миссий. Нельзя автоматически разрешать миссию только потому, что аппарат заряжен или задание осталось в локальной очереди.

## 11. Вылет и освобождение площадки

1. Проверить готовность.
2. Открыть крышку.
3. Подтвердить конечное положение.
4. Передать штатному автопилоту согласованное разрешение на старт/вылет.
5. Контролировать состояние аппарата.
6. Подтвердить освобождение площадки.
7. Только после подтверждения разрешить самоочистку.
8. Проверить окончание очистки.
9. Закрыть крышку, если это допускается конструкцией и условиями.
10. Перейти в ожидание.

Если вылет прерван, не состоялся или освобождение площадки не подтверждено, самоочистка не запускается. При неизвестном положении БАС или противоречивых данных крышка автоматически не закрывается; станция выполняет восстановление/ожидание вмешательства и уведомляет оператора. Закрытие допускается только после достоверного подтверждения, что БАС отсутствует в зоне движения и все условия безопасности выполнены. Для S-12 используется контекст AFTER_TAKEOFF, отличный от AFTER_LANDING, без добавления нового глобального состояния.

## 12. Самоочистка

Очистка должна запускаться только при выполнении всех условий:

- БАС отсутствует на площадке;
- крышка и механизм находятся в допустимом положении;
- нет постороннего объекта;
- привод исправен;
- погодные условия допустимы для выбранной технологии очистки;
- система безопасности выдала разрешение.

После запуска контролировать время, положение и нагрузку механизма. При заклинивании или ином отказе остановить привод, зарегистрировать причину и прекратить попытки после установленного числа повторов. Бесконечное повторение запрещено. Если механизм неисправен или безопасность зоны не подтверждена, автоматический цикл не продолжается до предусмотренной проверки/вмешательства. Пропуск очистки возможен только если площадка и крышка находятся в подтверждённом безопасном состоянии и такой переход допускается таблицей автомата.

## 13. Тайм-ауты и повторные попытки

Для каждого процесса должны быть заданы:

- максимальное время ожидания;
- допустимое число повторов;
- интервал между повторами;
- условие окончательного отказа;
- код ошибки;
- допустимый следующий шаг.

Точные числа пока не заданы. Запрещено создавать бесконечные циклы повторения команд.

Тайм-аут подтверждения не равен доказательству того, что физическая операция не выполнилась. Если команда могла быть передана исполнительному модулю, но подтверждение не получено, результат операции считается OUTCOME_UNKNOWN до сверки фактического состояния оборудования. Нельзя автоматически отправлять повторную команду, которая может повторно запустить движение или другую опасную операцию.

Повтор допускается только по явно заданной политике конкретной операции: после проверки её текущего состояния, оценки риска повторного действия и получения необходимых разрешений.

## 14. Восстановление после перезапуска

После внезапного отключения питания станция не должна слепо продолжать последнюю команду.

Она должна:

1. Инициализировать программные компоненты и контроллеры.
2. Загрузить сохранённые параметры и конфигурацию, проверить их версию, целостность и обязательные поля. При отсутствии/повреждении параметров не подставлять молча рабочие значения; зафиксировать причину и применить утверждённую реакцию.
3. Считать сохранённые данные о незавершённых операциях и намерениях.
4. Выполнить стартовую диагностику через DiagnosticsManager; результаты отдельных проверок предоставляет соответствующая служба.
5. Повторно опросить датчики.
6. Определить фактическое положение крышки и механизмов.
7. Определить наличие БАС и сопоставить его с зарегистрированными аппаратами.
8. Проверить состояние зарядного модуля.
9. Проверить целостность незавершённых файлов.
10. Восстановить очередь передачи.
11. Выбрать безопасное состояние по фактическим данным и правилам восстановления.
12. Зарегистрировать факт перезапуска.

Сохранённое программное состояние является записью о ранее известных событиях, а не доказательством текущего положения оборудования. После повторного опроса подсистем необходимо сопоставить сохранённое состояние с фактическими показаниями.

Если состояние датчика неизвестно, данные устарели или источники противоречат друг другу, станция не должна автоматически считать оборудование безопасным или продолжать последнюю физическую операцию. Требуется определить результат незавершённой операции и применить конкретную политику восстановления. Если однозначное безопасное решение отсутствует, затронутые опасные действия остаются заблокированными, а дальнейшее состояние выбирается по утверждённому правилу отказа.

Переходы ЗАПУСК → САМОПРОВЕРКА → ВОССТАНОВЛЕНИЕ должны быть отражены в таблице переходов. Выход из ВОССТАНОВЛЕНИЕ в штатное состояние допускается только после проверки актуальных отчётов подсистем.

Если после перезапуска достоверно подтверждено, что зарегистрированный БАС находится внутри корпуса, крышка закрыта, зона безопасна и состояние обслуживающих подсистем известно, станция может вернуться в ОБСЛУЖИВАНИЕ В ЗАКРЫТОМ КОРПУСЕ. Возобновляются только те независимые процессы, для которых заново подтверждены условия и безопасность; незавершённая физическая операция не продолжается только по сохранённому статусу. Если положение БАС, крышки или состояние подсистем неизвестно/противоречиво, штатное обслуживание не возобновляется, требуется вмешательство.

## 15. Принцип конечного автомата

Менеджер состояний должен централизованно контролировать переходы. Функциональные модули не должны самостоятельно переводить всю станцию в произвольные состояния.

Переход разрешается, если:

- получено событие или команда;
- выполнены условия перехода;
- система безопасности не запретила операцию;
- необходимые данные актуальны;
- все операции, конфликтующие с планируемым переходом, завершены или безопасно отменены; независимые параллельные операции допускаются только там, где это прямо предусмотрено алгоритмом (например, передача материалов и зарядка при закрытом обслуживании).

Для каждой пары «текущее состояние — событие» нужно определить допустимое следующее состояние. Неизвестные переходы запрещаются и журналируются.

Глобальное состояние станции, состояние отдельной операции и фактическое состояние оборудования — разные сущности. Их нельзя подменять друг другом. Например, принятие исполнительным модулем команды закрытия крышки не подтверждает ни начало движения, ни закрытое положение крышки.

Для операции, выполняемой функциональным модулем, различать как минимум следующие этапы:

- REQUESTED — SSM зарегистрировал запрос и operation_id; передача исполнительному модулю ещё не подтверждена;
- ACCEPTED — исполнительный модуль принял запрос к обработке;
- STARTED — исполнительный модуль подтвердил начало действия;
- COMPLETED — действие завершено и требуемый результат подтверждён;
- FAILED — исполнительный модуль сообщил об отказе;
- CANCEL_REQUESTED — запрошена отмена;
- CANCELLED — отмена подтверждена;
- OUTCOME_UNKNOWN — результат нельзя достоверно установить.

Глобальное состояние, обозначающее выполнение физической операции, не должно устанавливаться только по факту отправки или принятия команды. Условие входа и выхода для такого состояния должно указывать требуемое событие и подтверждение.

### 15.1. Обязательная форма записи перехода

Каждый переход, который допускается к реализации, должен быть описан отдельной записью. Минимальные поля:

| Поле | Что фиксируется |
|---|---|
| Transition ID | Уникальный идентификатор правила |
| Текущее состояние | Одно из состояний раздела 2 |
| Событие | Тип события, запускающего проверку |
| Предварительные условия | Все логические условия и требования к актуальности данных |
| Проверка безопасности | Требуемое разрешение/проверка и исполнитель, который её запрашивает |
| Следующее состояние | Одно из состояний раздела 2 либо явное отсутствие перехода |
| Запросы действий | Какие функциональные менеджеры должны получить ActionRequest |
| Требуемый lifecycle | Какой статус операции необходим для входа/выхода из состояния |
| Подтверждение результата | Какой отчёт/измерение подтверждает фактический результат |
| Тайм-аут и отказ | Что происходит при отсутствии ответа, отказе или OUTCOME_UNKNOWN |
| Трассировка | Связанные REQ, FAIL и TEST |

Эта структура является формой будущей матрицы, а не утверждением о конкретных переходах. Правила, для которых не определены условия, подтверждения или отказные ветви, нельзя считать готовыми к реализации.

Независимые операции могут выполняться параллельно, если это явно предусмотрено алгоритмом. Например, во время закрытого обслуживания передача материалов и зарядка могут идти параллельно. SSM должен отслеживать их по разным operation_id; завершение одной операции не должно ошибочно завершать другую или менять общий этап обслуживания раньше выполнения его условий.
