# Программная архитектура

**Статус:** предварительное проектирование.  
**Редакция:** 0.1.

## 1. Цель

Разделить программное обеспечение станции на компоненты с понятными задачами и контролируемыми интерфейсами.

Архитектура не фиксирует окончательный язык программирования, ОС, контроллеры или платы. Эти решения зависят от выбора оборудования.

## 2. Основные принципы

1. Один модуль отвечает за ограниченную область функций.
2. Взаимодействие выполняется через явно описанные интерфейсы.
3. Модуль не должен напрямую управлять чужим оборудованием в обход владельца этого оборудования.
4. Критические защитные функции не должны зависеть от интернет-соединения.
5. Неизвестное состояние не считается безопасным.
6. Входные данные проверяются до использования.
7. Для операций задаются тайм-ауты и обработка ошибок.
8. Секреты и конфигурация отделяются от исходного кода.
9. Логика тестируется без физического оборудования.
10. Аппаратные драйверы можно заменять имитаторами в тестах.

## 3. Пять логических уровней

### Уровень 1. Главная логика

| Модуль | Назначение |
|---|---|
| Управление состоянием станции | Хранит текущее состояние и разрешает переходы |
| Планировщик заданий и маршрутов | Получает, хранит и проверяет миссии |
| Система контроля безопасности | Проверяет запреты, разрешения и критические состояния |

### Уровень 2. Функциональные модули

| Модуль | Назначение |
|---|---|
| Управление метеоданными | Оценка погодных условий |
| Обнаружение и идентификация БАС | Обнаружение и проверка устройства |
| Управление посадкой | Обработка данных позиционирования и взаимодействие с автопилотом |
| Управление крышкой | Открытие, закрытие и контроль механизма |
| Управление зарядкой | Управление зарядным процессом |
| Управление самоочисткой | Управление механизмом очистки |
| Управление данными | Координация получения и отправки материалов |
| Управление электропитанием | Мониторинг и распределение питания |

### Уровень 3. Обработка и хранение данных

| Модуль | Назначение |
|---|---|
| Доступ к накопителю БАС | Работа с согласованным интерфейсом бортового хранилища |
| Передача файлов | Передача файлов и частей файлов |
| Проверка целостности | Контрольные суммы и проверка полноты |
| Локальное хранение | Работа с диском станции |
| Шифрование | Криптографическая защита |
| Отправка на сервер | Загрузка материалов |
| Очередь передачи | Повторная отправка и возобновление |

### Уровень 4. Службы оборудования

| Служба | Назначение |
|---|---|
| Обнаружение Bluetooth | Поиск BLE-устройств |
| Техническое зрение | Получение и обработка изображений |
| Опрос метеостанции | Получение погодных измерений |
| Опрос датчиков | Получение показаний датчиков станции |
| Управление приводами | Команды приводам и обратная связь |
| Беспроводная передача энергии | Интерфейс с зарядным оборудованием |
| Связь | Сетевые и бортовые коммуникации |

### Уровень 5. Аппаратный уровень

- GPIO;
- ADC;
- PWM;
- UART;
- I2C;
- SPI;
- RS-485;
- Ethernet;
- Wi-Fi;
- BLE;
- USB;

- датчики;
- приводы;
- зарядные преобразователи.

Перечень предварительный. Реальные интерфейсы зависят от компонентов.

## 5. Предлагаемые программные компоненты

### 5.1. Управление состоянием станции

Ответственность:

- хранить состояние станции;
- принимать события от функциональных модулей;
- проверять допустимость переходов;
- запускать согласованные операции;
- сохранять историю переходов;
- восстанавливать состояние после перезапуска с повторной проверкой оборудования.

Не должно:

- напрямую управлять электрическими выводами;
- обходить систему безопасности;
- самостоятельно придумывать команды автопилоту.

### 5.2. Система контроля безопасности

Ответственность:

- собирать критические статусы;
- проверять запреты;
- выдавать разрешения;
- инициировать безопасную остановку конкретных операций;
- фиксировать причины блокировки.

Пример результата проверки:

- разрешено;
- запрещено;
- неизвестно — данных недостаточно.

Не следует сводить все неисправности к одному флагу «авария». Разные отказы требуют разных реакций.

### 5.3. Планировщик заданий и маршрутов

Ответственность:

- получать задания;
- проверять их формат и идентификатор;
- сохранять текущую миссию;
- отслеживать статус проверки специалистом;
- передавать согласованное задание бортовой системе через установленный интерфейс.

Планировщик не должен самостоятельно реализовывать полётную стабилизацию.

### 5.4. Управление метеоданными

Ответственность:

- опрашивать датчики;
- проверять временные метки и качество;
- фильтровать измерения;
- рассчитывать погодные статусы;
- выдавать отдельные разрешения для операций.

### 5.5. Обнаружение и идентификация БАС

Ответственность:

- принимать события обнаружения;
- устанавливать связь;
- проводить аутентификацию;
- сопоставлять идентификатор с зарегистрированным БАС;
- получать визуальное подтверждение.

### 5.6. Управление посадкой

Ответственность:

- получать измерения камеры;
- определять относительное положение в согласованной системе координат;
- оценивать качество измерения;
- передавать данные штатному автопилоту;
- фиксировать потерю маркера;
- получать статус посадки.

### 5.7. Управление крышкой

Ответственность:

- принимать команды;
- проверять разрешения;
- запускать привод;
- контролировать концевые датчики и нагрузку;
- прекращать движение при отказе;
- выдавать подтверждённое положение.

### 5.8. Управление зарядкой

Ответственность:

- проверять положение аппарата;
- получать разрешение от BMS;
- управлять зарядным модулем;
- контролировать электрические и температурные параметры;
- прекращать зарядку по штатному завершению или отказу.

### 5.9. Управление самоочисткой

Ответственность:

- проверять отсутствие БАС;
- проверять положение крышки;
- запускать механизм;
- контролировать движение;
- выявлять заклинивание;
- регистрировать результат.

### 5.10. Управление данными

Координирует получение файлов, проверку, локальное хранение, шифрование, очередь и отправку.

Сам не должен содержать низкоуровневую реализацию всех протоколов. Для этого существуют отдельные компоненты.

## 6. Правила взаимодействия модулей

- Использовать явные интерфейсы.
- Не обращаться к внутренним переменным другого модуля.
- Не использовать глобальные флаги как универсальный способ обмена.
- Для команд и статусов задавать тип, единицы, временную метку и качество.
- Для операций задавать уникальный идентификатор, результат и тайм-аут.
- Ошибки передавать структурированно.
- Не блокировать критические задачи длительными файловыми и сетевыми операциями.
- Сетевые запросы и обработку видео выполнять отдельно от критического контура управления приводами.

## 8. Обработка ошибок

Каждый модуль должен предоставлять:

- состояние готовности;
- актуальные данные;
- признак достоверности;
- код последней ошибки;
- время последнего успешного обмена;
- метод безопасной остановки, если он применим.

Ошибка должна быть понятной человеку и пригодной для машинной обработки.

## 9. Тестируемость

Для каждого аппаратного интерфейса следует предусмотреть возможность подмены реального устройства тестовым имитатором.

Примеры:

- имитация ветра и осадков;
- имитация положения крышки;
- имитация наличия БАС;
- имитация состояния BMS;
- имитация обрыва сети;
- имитация частично переданного файла;
- имитация отказа датчика.

Это позволит разрабатывать большую часть логики до изготовления полной станции.
