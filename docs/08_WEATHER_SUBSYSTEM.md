# Метеоподсистема док-станции

**Статус:** предварительное проектирование.  
**Редакция:** 0.2.

## 1. Назначение

Метеоподсистема должна регулярно получать погодные измерения, проверять их достоверность и предоставлять другим модулям актуальную информацию для принятия решений.

Она не должна самостоятельно управлять полётом. Её задача — измерять условия и формировать данные/разрешения, которые учитываются системой безопасности и менеджером состояний.

## 2. Измеряемые параметры

| Параметр | Единица | Для чего нужен |
|---|---|---|
| Скорость ветра | м/с | Оценка возможности вылета, приёма и работы механизмов |
| Направление ветра | ° | Оценка направления воздействия ветра |
| Порывы ветра | м/с | Оценка кратковременных опасных нагрузок |
| Температура воздуха | °C | Контроль условий эксплуатации |
| Относительная влажность | % | Контроль влажности и конденсации |
| Осадки | состояние/интенсивность | Оценка условий для полёта и механизмов |
| Атмосферное давление | гПа | Регистрация погодных условий и дополнительная диагностика |

Дополнительно рекомендуется предусмотреть внутренние датчики:

- температура вычислительного отсека;
- температура силовой электроники;
- температура зарядной катушки;
- температура внутри отсека БАС;
- влажность внутри корпуса.

## 3. Возможная конструкция

Предварительно можно рассмотреть:

- компактную метеостанцию;
- ультразвуковой анемометр;
- датчик температуры и влажности;
- датчик осадков;
- барометр.

В качестве интерфейса для внешней метеостанции можно рассмотреть RS-485/Modbus RTU. Это предложение, не утверждённое решение.

## 4. Размещение

Датчик ветра следует размещать так, чтобы уменьшить влияние:

- пропеллерных потоков;
- корпуса станции;
- стен и ограждений;
- крышки;
- локального нагрева от электроники;
- препятствий, искажающих воздушный поток.

Нужно учитывать, что метеостанция на корпусе может измерять локальные условия, отличающиеся от условий на высоте и в точке посадки.

Требуется определить высоту установки, ориентацию, защиту от осадков и доступ для обслуживания.

## 6. Качество измерений

Для каждого значения желательно хранить:

- значение;
- единицу;
- временную метку;
- источник;
- статус достоверности;
- признак выхода за физически допустимый диапазон;
- время последнего успешного измерения.

Необходимо обнаруживать:

- отсутствие ответа;
- ошибку связи;
- невозможное значение;
- зависшее значение;
- слишком старую временную метку;
- резкий скачок;
- рассогласование нескольких датчиков, если они дублируются.

Фильтрация не должна скрывать опасные кратковременные порывы ветра. Поэтому нужно отдельно хранить текущую оценку, усреднённую скорость и максимум порывов за заданное окно.

## 7. Погодные разрешения

Погодная подсистема должна выдавать отдельные статусы:

- разрешение на плановый вылет;
- разрешение на штатную посадку;
- разрешение на приоритетный приём возвращающегося БАС;
- разрешение на открытие крышки;
- разрешение на самоочистку;
- разрешение на зарядку.

Итого предусматривается шесть независимых разрешений. Единые машинные значения: ALLOW, DENY, UNKNOWN; причина решения передаётся отдельно.

Погодные условия для этих операций могут различаться. Для первой версии принято закрытое обслуживание: после безопасной посадки крышка закрывается, а разрешение на движение крышки учитывает ветер, осадки, обледенение, состояние привода и безопасность траектории.

Например, ограничение для планового вылета не должно автоматически означать, что возвращающемуся аппарату запрещено выполнять заранее предусмотренный безопасный приём.

При этом приоритетный приём не означает, что станция может игнорировать физически опасные условия. Нужен отдельный сценарий для каждого диапазона и типа отказа.

## 8. Правила формирования разрешений

Разрешение не должно быть только true/false. Рекомендуются три состояния:

- РАЗРЕШЕНО;
- ЗАПРЕЩЕНО;
- НЕИЗВЕСТНО.

Причина должна быть доступна журналу и специалисту.

При отсутствии достоверных данных нельзя выдавать разрешение на плановый вылет. Для штатной посадки, приоритетного приёма и других операций предусмотрены отдельные правила; отсутствие данных не должно автоматически сводиться к одному общему сценарию.

Пороговые значения должны быть обоснованы:

- ограничениями выбранного БАС;
- ограничениями конструкции станции;
- ограничениями механики;
- испытаниями;
- эксплуатационной документацией.

ИИ не должен самостоятельно назначать эти пороги.

## 9. Обогрев и вентиляция

Температурный диапазон −30…+50 °C относится к исходному требованию по окружающей среде, но не означает, что все внутренние компоненты автоматически способны работать в этом диапазоне.

Необходимо отдельно определить:

- допустимые температуры электроники;
- температурный диапазон аккумулятора;
- допустимые температуры зарядной катушки;
- необходимость обогрева;
- необходимость вентиляции;
- защиту от конденсации;
- поведение при обледенении;
- тепловыделение при зарядке.

## 10. Диагностика

Примеры кодов:

- WEATHER_SENSOR_NO_RESPONSE;
- WEATHER_DATA_STALE;
- WEATHER_VALUE_OUT_OF_RANGE;
- WEATHER_COMMUNICATION_ERROR;
- WEATHER_SENSOR_CONFLICT;
- WEATHER_MODULE_NOT_INITIALIZED.

Коды предварительные.

## 11. Испытания

- сравнение показаний с контрольным прибором;
- проверка связи;
- проверка временных меток;
- проверка обнаружения обрыва;
- проверка устаревших значений;
- проверка порывов ветра;
- проверка реакции на отсутствие данных;
- проверка передачи статусов системе безопасности;
- проверка влияния корпуса и пропеллерных потоков.
