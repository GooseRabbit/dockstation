# План реализации сетевого подключения DockStation на Repka Pi 5

**Статус:** предварительный план; последовательность сетевой разработки согласована, конкретный протокол и программный стек требуют проверки и фиксации.  
**Редакция:** 0.13  
**Дата:** 2026-11-11.

Полный маршрут разработки программного продукта, включая графическое Windows-приложение и аппаратные подсистемы, приведён в [мастер-плане](31_REPKA_DOCKSTATION_SOFTWARE_IMPLEMENTATION_PLAN.md).

## 1. Цель

Подготовить вычислительный модуль DockStation на базе Repka Pi 5 к безопасному обмену с удалённым Windows-компьютером. Первый результат — проводное подключение по Ethernet, защищённое административное обслуживание и получение диагностики Repka с Windows.

Работа выполняется по прежней схеме: **этап → файл → функция → проверка**. Одна функция — одна небольшая задача; без больших переписываний существующих файлов.

## 2. Исходные условия и границы

| Положение | Текущий статус |
|---|---|
| Плата | Repka Pi 5 — выбранный на текущем этапе кандидат |
| ОС | Официальная Repka OS — основной кандидат; версию и пакеты проверяем на фактической плате |
| Первичный канал | Ethernet через локальный маршрутизатор/коммутатор |
| Клиент | Windows |
| Сетевой сервис | На Repka Pi 5 |
| Первый срез | Только чтение диагностики; никаких физических команд |
| Локальный контроллер | ESP32 остаётся отдельным контуром; потеря сети не должна останавливать защитные функции |

В первый срез входят: проверка Ethernet/IP/DNS/маршрута, SSH-доступ по ключу, локальный диагностический сервис, чтение состояния Linux и обработка отсутствующих данных.

Пока не входят: команды ESP32, управление крышкой/очисткой/зарядкой, автопилот, камеры, передача файлов БАС, серверная интеграция, полноценная регистрация Station ID/ролей и доступ через публичный интернет.

## 3. Схема первого подключения

Предлагается временный безопасный маршрут разработки:

```
Windows PC
   | Ethernet / LAN
Router / Switch
   | Ethernet
Repka Pi 5
   |-- SSH (аутентификация ключом)
   |-- DockStation Gateway
          |-- HTTP/JSON API только на 127.0.0.1
```

Windows создаёт SSH-туннель:

```powershell
ssh -N -L 18080:127.0.0.1:8080 <admin-user>@<repka-ip>
```

Затем клиент обращается к `http://127.0.0.1:18080/api/v1/health`. API на Repka слушает только loopback; весь сетевой участок между компьютерами защищён SSH. SSH настраивается по ключу; удалённый вход под root и парольную аутентификацию отключаем после проверки ключевого входа. Сам Gateway запускается от отдельной непривилегированной учётной записи.

Это временная схема разработки, не финальная эксплуатационная архитектура. Перед прямым LAN/VPN-доступом к API обязательны HTTPS, аутентификация и авторизация по согласованной политике. Проверку сертификатов отключать нельзя.

### 3.1. Предлагаемый API

Для первого прототипа предлагаются REST и JSON:

- `GET /api/v1/health` — состояние только API-процесса;
- `GET /api/v1/system/diagnostics` — системные и сетевые показатели Repka;
- `platform.resources.memory`, `storage`, `cpu_temperature`, `cpu_load` — показатели памяти, корневой файловой системы, явно идентифицированной температуры CPU/SoC и load average; недоступные числовые поля передаются как `null`;
- версия контракта, временная отметка и качество данных в ответе;
- периодический опрос клиента; WebSocket/SSE добавлять только при доказанной необходимости.

REST/JSON и HTTP-библиотека пока являются предложением, а не утверждённым внешним контрактом. Перед выбором библиотеки проверяем её совместимость с фактической Repka OS, компилятором и C++17-ядром.

Для первого образца предпочтительна DHCP reservation на маршрутизаторе, чтобы плата получала постоянный адрес без ручного статического IP. Окончательный способ адресации фиксируется после проверки реальной сети. IP-адреса развёртывания и секреты в Git не записываются.

## 4. Этапы, файлы и функции

## Этап 0. Проверка платформы и сети

**Цель:** подтвердить фактическую среду Repka и безопасный административный доступ.

### Файлы

| Файл | Назначение |
|---|---|
| `repka/README.md` | Инструкция первой настройки ОС, Ethernet и SSH |
| `repka/check_network.sh` | Только диагностическая проверка Linux-среды; без изменения конфигурации |
| `repka/network_helpers.sh` | Проверки обязательных команд, ОС, архитектуры и итогового статуса диагностики |

### Функции `check_network.sh`

1. `require_command()` — реализовано: наличие обязательных команд `ip` и `uname`.
2. `read_os_release()` — реализовано: безопасное чтение имени, ID и версии ОС без исполнения файла.
3. `check_architecture()` — реализовано: архитектура через `uname -m` и разрядность через `getconf LONG_BIT`.
4. `check_ethernet_link()` — реализовано: наличие Ethernet-интерфейса и состояние физического линка.
5. `read_ip_configuration()` — реализовано: чтение назначенных IPv4/IPv6-адресов всех интерфейсов через `ip -o address show`.
6. `check_default_route()` — реализовано: чтение маршрутов IPv4 и IPv6 по умолчанию через `ip -4/-6 -o route show default`.
7. `check_dns_resolution()` — реализовано: проверка системного разрешения контрольного имени через `getent ahosts` с тайм-аутом.
8. `check_ssh_service()` — реализовано: чтение состояния SSH service/socket units через `systemctl show`.
9. `print_diagnostics_report()` — реализовано: итоговый PASS/WARN/FAIL и соответствующий код завершения.

Контрольное имя намеренно не зашивается в скрипт: отсутствие настройки даёт `WARN`, а не ложный успешный результат и не требование доступа к конкретному внешнему сайту. `getent` использует системную NSS-конфигурацию, поэтому запись в `/etc/hosts` также может разрешить имя; функция проверяет системное разрешение имени, а не гарантирует доступность публичного DNS-сервера. Для проверки DNS-запроса выберите имя, отсутствующее в локальном hosts-файле.

Скрипт не устанавливает пакеты, не редактирует файлы, не включает SSH и не открывает порты. Он только проверяет; настройка выполняется отдельно по инструкции.

Проверка SSH также остаётся read-only: она не запускает, не останавливает и не включает службу, не меняет конфигурацию и не открывает порт. Активный `ssh.socket`/`sshd.socket` считается доступным вариантом socket activation. Проверка состояния unit не подтверждает успешный вход по ключу, доступность TCP-порта через firewall или возможность подключения с Windows; это отдельные проверки следующего этапа.

Проверки `require_command()`, `read_os_release()`, `check_architecture()` и `print_diagnostics_report()` вынесены в `repka/network_helpers.sh`; `check_network.sh` подключает этот файл относительно собственного расположения. В основном запуске сначала выполняются preflight-проверки, затем сетевые проверки; итоговая сводка сохраняет наиболее высокий код результата.

**Текущий минимальный VM-прототип:** в `repka_gateway/` подготовлен временный read-only HTTP/JSON Gateway на стандартной библиотеке Python 3.11+. Он предоставляет `GET /api/v1/health` и `GET /api/v1/system/diagnostics` и слушает исключительно `127.0.0.1`. Windows-клиент подключается через SSH local-forward. Снимок содержит сведения об ОС, архитектуре, uptime, RAM, корневой файловой системе, CPU/SoC temperature (если доступен явно маркированный термодатчик), load average, сетевых интерфейсах/IP, маршрутах, DNS и SSH. Четыре группы системных ресурсов публикуются в `platform.resources` с независимыми статусами и явными null для недоступных значений. ESP32 и физические датчики в этот срез не входят. Python является временным способом проверить VM-обмен без выбора дополнительной HTTP-библиотеки; это не отменяет предварительную позицию C++17 для производственного Gateway из мастер-плана.

**Результат:** проверки этапа 0 реализованы; собран временный loopback-only HTTP/JSON Gateway для VM-сценария. Окончательный производственный стек не выбран.

## Этап 1. Каркас Linux-приложения и системная диагностика

**Цель:** создать отдельную Linux-цель с корректным жизненным циклом процесса и read-only диагностикой, не меняя существующую сборку host-тестов и не запуская конкурирующий HTTP-сервер.

### Файлы

| Файл | Назначение |
|---|---|
| `CMakeLists.txt` | CMake-библиотека Linux runtime, исполняемая цель и CTest |
| `.github/workflows/linux-cmake.yml` | Автоматическая Linux-сборка и запуск CTest при push в рабочую ветку |
| `repka_gateway/main.cpp` | Безопасная точка входа процесса |
| `src/application/linux/application_bootstrap.hpp/.cpp` | Жизненный цикл приложения и обработка завершения |
| `src/platform/linux/runtime_environment.hpp/.cpp` | Сведения об ОС, ядре, архитектуре и системных зависимостях |
| `src/platform/linux/system_diagnostics.hpp/.cpp` | Системные показатели Linux |
| `src/platform/linux/network_diagnostics.hpp/.cpp` | Локальные сетевые показатели Linux |
| `src/platform/linux/runtime_config.hpp/.cpp` | Типизированная конфигурация процесса и валидация |
| `src/platform/linux/command_line.hpp/.cpp` | Разбор CLI и справка |
| `src/platform/logging/logger.hpp/.cpp` | Структурированный системный журнал |

### Функции и жизненный цикл

**`repka_gateway/main.cpp`**
1. `main()` — формирует массив аргументов и передаёт управление ApplicationBootstrap.
2. Возвращает ОС код `ApplicationExitCode`.

**`application_bootstrap.cpp`**
1. `run_application()` — координирует разбор CLI, запуск и завершение процесса.
2. `--help` и некорректные аргументы обрабатываются до инициализации Logger.
3. RuntimeConfig валидируется до открытия sink журналирования.
4. Устанавливаются обработчики SIGINT/SIGTERM; обработчик только выставляет `sig_atomic_t`-флаг.
5. Проверяются базовые системные зависимости.
6. Собираются read-only SystemDiagnostics и NetworkDiagnostics; DNS/TCP-пробы автоматически не запускаются.
7. Зарегистрированная служба получает RuntimeConfig и флаг завершения через ServiceRunner.
8. После завершения службы восстанавливаются исходные обработчики сигналов, выполняются flush и shutdown Logger.
9. Если ServiceRunner не передан, выполняется только bootstrap-проверка и выводится явное сообщение, что HTTP API не запущен.

**Текущая граница:** production-точка входа `repka_gateway/main.cpp` передаёт read-only HTTP-службу в существующий ApplicationBootstrap через ServiceRunner. HTTP API не управляет физическими устройствами и не публикует управляющие маршруты. Python Gateway остаётся отдельным временным VM-прототипом; C++ API ещё не проверен вручную в Ubuntu VM. Production-адаптеры, composition root прикладных менеджеров и systemd unit относятся к следующим задачам.

**Проверки:** `verification/repka_gateway/test_application_bootstrap.cpp` и CTest `application_bootstrap` проверяют справку, ранний отказ CLI, инициализацию/ошибку Logger, сбор диагностик, передачу конфигурации службе, SIGTERM, код ошибки службы и bootstrap-only режим. Вместе с шестью существующими проверочными программами в CTest зарегистрировано семь тестов. Добавлен GitHub Actions workflow для Linux CMake build и CTest с ASan/UBSan; доступный результат выполнения workflow пока не получен.

**Результат этапа 1:** отдельная Linux-цель запускает bootstrap, собирает read-only диагностику и корректно завершает работу. HTTP API описан в следующем этапе.

## Этап 2. Локальный read-only API

**Статус:** первый C++ API-срез реализован в исходниках и включён в Linux CMake-цель. Его фактические результаты host CI фиксируются в разделе 3.13 документа испытаний; ручная проверка этого C++ сервера в Ubuntu VM ещё не выполнена.

**Цель:** дать Windows Operator доступ к health и системной диагностике через SSH local-forward, сохраняя HTTP listener исключительно на loopback.

### Файлы реализации

| Файл | Назначение |
|---|---|
| \`src/communications/network_types.hpp\` | Типы HTTP-запроса, ответа, результата разбора и статуса сервера |
| \`src/communications/local_api_server.hpp/.cpp\` | Разбор ограниченного HTTP-запроса, маршрутизация, loopback listener, приём одного запроса и штатная остановка |
| \`src/communications/api_serialization.hpp/.cpp\` | JSON-экранирование, health, системная/сетевая диагностика и структурированные API-ошибки |
| \`repka_gateway/main.cpp\` | Регистрация C++ API как ServiceRunner существующего ApplicationBootstrap |
| \`verification/repka_gateway/test_local_api.cpp\` | CTest: сериализация, parser/route contract и реальный loopback round-trip |
| \`verification/integration/test_cpp_gateway_api.py\` | Проверка реального собранного C++ процесса через HTTP и валидатор Operator API |

### Реализованное поведение

**Жизненный цикл сервера**
- \`LocalApiServer::start(port)\` создаёт TCP listener только на фиксированном \`127.0.0.1\`; порт берётся из уже валидированного RuntimeConfig.
- \`serve_once(timeout)\` принимает ограниченный запрос и отправляет один ответ; listener использует неблокирующее ожидание.
- \`stop()\` закрывает listener. \`status()\` возвращает фактический loopback-адрес, порт и причину ошибки.
- \`run_local_api_server()\` работает внутри ServiceRunner ApplicationBootstrap, обрабатывает сигнал штатного завершения и записывает события запуска/остановки в PlatformLogger.
- Ответ закрывает соединение; ожидание заголовков и отправка ответа ограничены тайм-аутом. Размер HTTP-запроса ограничен 8192 байтами и числом 64 заголовка. Тела запросов и Transfer-Encoding не поддерживаются.

**HTTP parser и маршруты**
- \`parse_http_request()\` принимает корректный origin-form HTTP/1.0 или HTTP/1.1, ограничивает размер и количество заголовков, отклоняет дублирующийся/ненулевой Content-Length, Transfer-Encoding, folded-заголовки и тело запроса.
- \`dispatch_api_request()\` поддерживает только:
  - \`GET /api/v1/health\`;
  - \`GET /api/v1/system/diagnostics\`.
- Неизвестный маршрут возвращает 404, неподдерживаемый метод — 405 с \`Allow: GET\`, query/fragment в request target отклоняются. Test-only PING и физические/управляющие маршруты в C++ API отсутствуют.
- Ответы содержат Content-Type JSON, Content-Length, Cache-Control: no-store, X-Content-Type-Options: nosniff и Connection: close.

**Диагностика**
- JSON-контракт системной диагностики сохраняет схему \`1.0\`, источник \`LINUX_HOST\`, UTC timestamp, summary, platform, network и scope, ожидаемые существующим Operator API validator.
- Используются существующие read-only RuntimeEnvironment, SystemDiagnostics и NetworkDiagnostics; значения, которые сборщики не смогли прочитать, остаются null/UNAVAILABLE, а не подменяются нулями.
- DNS-проба не запускается автоматически и помечается \`NOT_CONFIGURED\`; статус SSH-службы пока не реализован в C++ сборщике и помечается \`UNAVAILABLE\`. Для IPv4/IPv6 default route сейчас возвращается \`UNKNOWN\` в family_status, потому что существующий C++ сборщик выдаёт общий статус таблиц, а не раздельный статус каждого семейства.
- Общий статус C++ diagnostics — \`WARN\`, пока DNS и SSH-проверки не реализованы; это намеренно не объявляется полной проверкой сети.

### Границы и безопасность

API остаётся read-only и доступен только через локальный loopback listener. Его предполагаемый внешний доступ — ранее проверенная SSH-схема; SSH не является частью C++ HTTP-сервера. Прямой bind на Ethernet/LAN, TLS, пользовательская аутентификация, systemd unit и управляющие команды в этот срез не добавлялись. Для операторского доступа по сети по-прежнему требуется доверенный SSH-туннель и строгая проверка host key.

Python Gateway не удалён и не переписан: он остаётся временным VM-прототипом до отдельной ручной проверки C++ API и согласованного переключения VM на новую службу.

**Критерий host-проверки:** Linux CMake build/CTest, проверка loopback round-trip, а также запуск собранного процесса и валидация обоих GET-ответов существующим Operator API validator. Эти проверки не подтверждают работу на Repka Pi 5/ARM64 или ручной SSH-туннель Windows ↔ C++ Gateway.

## Этап 3. Первоначальное графическое Windows Operator Application

**Цель:** сразу после подтверждения сетевого соединения создать графическое приложение для подключения и мониторинга. Это read-only MVP; полный перечень функций GUI приведён в мастер-плане 31.

Python + PySide6/QML — рекомендация из спецификации оператора, не окончательное утверждение. Для первого клиента допустим небольшой Python-модуль без сложного интерфейса.

### Файлы

| Файл | Назначение |
|---|---|
| `operator/connection_manager.py` | Управление SSH-туннелем |
| `operator/station_api_client.py` | Запросы к API |
| `operator/diagnostics_model.py` | Модель диагностических данных |
| `operator/diagnostics_cli.py` | Вспомогательная консольная проверка; не заменяет GUI |

### Функции

**`connection_manager.py`**
1. `validate_connection_config()` — проверка адреса, порта и пути к ключу.
2. `start_ssh_tunnel()` — запуск туннеля без пароля в командной строке.
3. `get_tunnel_status()` — состояние процесса и локального порта.
4. `stop_ssh_tunnel()` — остановка только собственного процесса туннеля.
5. `disconnect_active_connection()` — закрытие подключения и освобождение ресурсов.

**`station_api_client.py`**
1. `get_health()` — получение состояния API.
2. `get_system_diagnostics()` — получение системных и сетевых показателей.
3. `validate_api_response()` — проверка версии схемы, обязательных полей и типов.
4. `map_api_error()` — преобразование ошибок в понятный результат.

**`diagnostics_model.py`**
1. `apply_diagnostics()` — применение нового снимка.
2. `mark_diagnostics_stale()` — отметка устаревших данных.
3. `clear_connection_state()` — снятие признака актуальности после отключения.

**`diagnostics_cli.py`**
1. `parse_cli_arguments()` — разбор параметров.
2. `run_diagnostics_session()` — подключение, запросы и завершение сессии.
3. `print_diagnostics()` — вывод значений, времени и качества данных.

**Результат:** главное пользовательское средство — графическое приложение Windows, которое подключается к Repka, показывает диагностику и явно отображает потерю связи и устаревшие данные.

## Этап 4. Прямой защищённый API и удалённый доступ

**Цель:** заменить временный SSH-туннель штатным сетевым каналом после согласования идентичности и политики доступа.

### Файлы-кандидаты

- `src/security/tls_server_context.hpp/.cpp` — настройка TLS.
- `src/security/request_authenticator.hpp/.cpp` — аутентификация запросов.
- `repka/security/README.md` — установка и защита сертификатов и секретов.
- `operator/connection_manager.py` — единый контроль выбранного защищённого канала.
- Предварительная документация и результаты сравнения вариантов VPN фиксируются в этом плане; отдельный программный модуль до выбора решения не создаётся.

### Функции

**TLS и аутентификация — только после согласования docs/24**
1. `load_tls_server_context()` — загрузка сертификата и ключа из защищённого хранилища.
2. `validate_peer_certificate()` — проверка доверенной цепочки и срока действия.
3. `authenticate_request()` — проверка согласованного метода аутентификации.
4. `authorize_read_request()` — проверка права на чтение.
5. `record_authentication_failure()` — журналирование отказа без секретов.

**Удалённая связность**
1. `check_vpn_interface()` — состояние VPN-интерфейса.
2. `check_vpn_route()` — наличие требуемого маршрута.
3. `connect_via_secure_overlay()` — подключение через выбранную защищённую overlay-сеть без публикации API в открытый интернет.

WireGuard пока остаётся базовым кандидатом для сравнения, но пользовательский сценарий должен по возможности быть единым: оператор запускает и контролирует защищённое соединение из DockStation Operator, не управляя отдельной VPN-программой вручную. Это не означает, что VPN-движок обязан работать внутри процесса GUI: допустима управляемая системная служба или проверенный системный компонент.

### 4.1. Предварительное исследование встроенного VPN

**Статус: исследование запланировано; реализация не утверждена и в текущий этап не входит.**

Цель — определить, можно ли предоставить собственный для DockStation пользовательский механизм защищённого подключения, который будет запускаться, настраиваться и контролироваться из Windows-приложения и не потребует от оператора отдельной VPN-программы.

Рассмотреть как минимум:
1. Интеграцию проверенного WireGuard-совместимого механизма в приложение или управляемую Windows-службу.
2. Другие существующие зрелые VPN/overlay-решения с возможностью встраивания или программного управления.
3. Собственную разработку сетевого туннеля только как отдельный исследовательский вариант с оценкой стоимости, сопровождения и независимого аудита; собственные криптографические алгоритмы не разрабатывать.

Для каждого варианта проверить:
- возможность работы на Windows и Linux/Repka OS;
- необходимость прав администратора, драйвера и системной службы;
- автоматический запуск/остановку туннеля из Operator и безопасное восстановление после сбоя;
- маршрутизацию только к нужным станциям и отсутствие случайного открытия API в публичную сеть;
- работу за NAT и CGNAT, необходимость публичного узла или relay;
- управление ключами, выдачу, ротацию, отзыв и безопасное хранение;
- совместимость с multi-tenant моделью, Station ID и пользовательскими правами;
- установку, обновление, удаление и диагностику;
- поведение при недоступности VPN, сервера или управляющего приложения.

Результат исследования — сравнительная таблица, рекомендуемая архитектура, перечень рисков и оценка объёма работ. После этого владелец проекта отдельно решает, реализовывать ли интеграцию и какой вариант выбрать. До такого решения текущая проверенная SSH-схема остаётся временным способом VM-тестирования; SSH не считается VPN и не подменяет будущую сетевую архитектуру.

Приватные ключи и peer-конфигурации в репозиторий не помещаются. Не разрабатывать собственный криптографический протокол и не считать факт создания туннеля заменой аутентификации, авторизации, TLS-проверок прикладного API и серверной изоляции данных.

**Результат этапа исследования:** документированное сравнение вариантов и согласованная владельцем рекомендация; сам VPN может оставаться нереализованным до появления реальной потребности и готовой сетевой топологии.

**Результат этапа 4:** уполномоченный клиент получает доступ по защищённой сети; публичный входящий порт API отсутствует; ошибка сертификата/аутентификации всегда приводит к отказу.

## Этап 5. Подключение телеметрии самой станции

**Цель:** перейти от диагностики Linux к показу реального состояния DockStation.

### Файлы-кандидаты

- `src/telemetry/telemetry_manager.hpp/.cpp` — сбор телеметрии.
- `src/communications/station_snapshot_provider.hpp/.cpp` — снимок станции.
- `src/communications/local_api_routes.cpp` — read-only маршрут снимка.
- `operator/telemetry_model.py` — модель данных Windows.

### Функции

**`telemetry_manager.cpp`**
1. `collect_telemetry_snapshot()` — сбор доступных состояний модулей и датчиков.
2. `mark_stale_values()` — отметка устаревших значений.
3. `publish_telemetry()` — передача снимка локальным получателям.

**`station_snapshot_provider.cpp`**
1. `build_station_snapshot()` — формирование снимка из доступных источников.
2. `validate_snapshot_completeness()` — проверка полноты и согласованности.
3. `map_unavailable_sources()` — обозначение отсутствующих подсистем.

**`telemetry_model.py`**
1. `apply_snapshot()` — применение полного снимка.
2. `apply_measurement_update()` — применение отдельного измерения.
3. `mark_measurement_stale()` — отметка устаревшего значения.

Подключение ESP32 и физических датчиков начнётся после утверждения межконтроллерного интерфейса и перечня оборудования. Предполагать использование CAN или RS-485 на этом этапе не нужно.

## Этап 6. Поток событий и команды

Отдельный последующий этап. WebSocket/SSE добавляется, если периодического опроса недостаточно. Физические команды допускаются только после согласования идентичности, полномочий, срока действия, защиты от повторной доставки, Operation lifecycle, обработки OUTCOME_UNKNOWN, локальной проверки SafetyManager и журналирования.

Кандидаты: `src/communications/event_stream.hpp/.cpp`, `src/communications/command_gateway.hpp/.cpp` и адаптеры Windows. Сетевой запрос сам по себе никогда не управляет GPIO, реле или приводом.

## 5. Правила пофункциональной реализации

1. Перед каждой задачей получить актуальный `main`, прочитать целевой файл, зависимости и контракт.
2. Одна задача закрывает одну функцию или небольшой неделимый набор функций.
3. Сначала определить типы и контракт, затем реализовывать.
4. Для функции зафиксировать входы, выходы, ошибки, побочные эффекты, тайм-ауты и владение ресурсами.
5. Сетевой сервис не входит в контур критического реального времени.
6. Потеря сети не меняет локальную безопасность и не вызывает повтор физических команд.
7. Секреты и реальные данные развёртывания не хранятся в Git.
8. `tests/` и `tools/` в рамках этого плана не меняются.
9. В отчётах указывать только реально выполненные сборки и проверки. Без Repka Pi 5 аппаратную проверку не считать выполненной.

## 6. Критерии готовности первого результата

1. Repka Pi 5 запускается с проверенной версией Repka OS.
2. Ethernet получает ожидаемый адрес и физический линк рабочий.
3. SSH с Windows работает по ключу; удалённый root и парольная аутентификация отключены.
4. Gateway работает от непривилегированной учётной записи.
5. API слушает только `127.0.0.1`.
6. Windows через SSH-туннель получает `/api/v1/health` и `/api/v1/system/diagnostics`.
7. Недоступные значения явно обозначены.
8. При обрыве сети клиент помечает данные устаревшими, а локальная безопасность станции продолжает работать.
9. API не принимает физических команд и не управляет исполнительными механизмами.

## 7. Первые задачи реализации

1. **Этап 0 / `repka/check_network.sh` / `check_ethernet_link()`.** Реализовано; наличие Ethernet-интерфейса и линка, отсутствие carrier и ошибки чтения различаются.
2. **`read_ip_configuration()`.** Реализовано; читаются IPv4/IPv6-адреса всех интерфейсов без изменения сетевой конфигурации.
3. **`check_default_route()` реализована.** Отдельно проверяются IPv4 и IPv6; отсутствие маршрута и неполное чтение дают `WARN`. Добавлена host-проверка `verification/repka_gateway/test_check_default_route.sh`.
4. `check_ssh_service()` — проверить SSH.
5. Остальные функции read-only отчёта.
6. После проверки платформы — каркас службы и системная диагностика.

До приобретения Repka Pi 5 эти проверки возможны только на доступной Linux-среде и не являются приёмкой самой платы.

## Результаты ручной проверки Windows Operator ↔ Linux VM (2026-11-13)

**Стенд:** Windows Operator QML на Windows-хосте; временный Python read-only Gateway в Linux VM; SSH-перенаправление к Gateway, локальный API-порт Windows 18080 → Linux 127.0.0.1:8080. Это VM-проверка, а не тест на Repka Pi 5.

| Испытание | Фактический результат |
|---|---|
| GET /api/v1/health и GET /api/v1/system/diagnostics через локальный SSH-forward | PASS; оба запроса вернули ожидаемые ответы |
| Ручное отключение и повторное подключение в Operator | PASS; соединение и свежая диагностика восстановлены |
| Принудительное завершение активного ssh.exe | PASS; Operator отметил данные как неизвестные/устаревшие, примерно через 5 секунд автоматически создал новый SSH-процесс, после чего получил свежую диагностику; PID владельца локального порта изменился |
| Остановка Python Gateway через Ctrl+C при оставленном SSH-туннеле и повторный запуск Gateway | PASS; Operator обозначил отсутствие ответа и устаревшие данные; после повторного запуска Gateway свежая диагностика восстановилась без ручного переподключения |

**Граница результата:** подтверждён конкретный Windows QML Operator ↔ временный Python Gateway в Linux VM. Не проверены C++ HTTP API, ARM64/Repka Pi 5, ESP32, физические датчики, UART/USB, исполнительные механизмы и аппаратная безопасность. Испытание остановки Gateway подтверждает восстановление API-обмена; оно само по себе не доказывает повторное создание SSH-туннеля.
