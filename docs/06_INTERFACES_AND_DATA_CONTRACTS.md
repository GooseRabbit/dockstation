# Интерфейсы и контракты данных

**Статус:** предварительная спецификация.  
**Редакция:** 1.15  
**Дата актуализации:** 2026-11-12.

## 1. Назначение

Документ определяет, какую информацию должны обменивать программные модули и внешние системы.

Он не утверждает конкретный транспорт или формат сообщений. JSON, MAVLink, Modbus RTU, UART, Ethernet и другие варианты являются кандидатами до выбора оборудования и согласования.

## 2. Общие правила для любого сообщения

Для событий, которые участвуют в управлении состоянием станции, обязательны:

- event_id — уникальный идентификатор конкретного события;
- event_type — тип события;
- source — логический источник события;
- source_instance/session — идентификатор экземпляра или сессии источника, если источник может перезапускаться;
- occurred_at — время формирования события источником, если оно доступно;
- received_at — время получения события принимающей стороной;
- source_sequence — последовательный номер события от источника, если источник поддерживает такую нумерацию;
- operation_id и correlation_id — для события, относящегося к длительной операции или исходному запросу;
- payload — данные события;
- quality/status — достоверность и качество данных;
- schema_version — версия контракта.

Конкретный транспорт и формат не определены. Если источник не может предоставить какое-либо поле, это должно быть явно отражено в адаптере/контракте; нельзя подставлять выдуманное значение.

Время формирования источником и время получения — разные величины. Время получения назначает принимающая сторона. Для измерений обязательно указывать единицы. Например, скорость ветра — м/с, температура — °C, давление — Па или гПа, угол — градусы с определённой системой отсчёта.

Нельзя передавать значение без единиц, если его интерпретация может быть неоднозначной.


### 2.1. Категории и каталог типов событий

Для классификации событий StationStateManager использует одну из шести категорий:

| Категория | Назначение |
|---|---|
| `SUBSYSTEM` | Изменение состояния или результат диагностики отдельной подсистемы |
| `OPERATION` | Изменение статуса выполняемой операции |
| `SAFETY` | Решение SafetyManager о разрешении или запрете операции |
| `COMMAND` | Запрос на выполнение команды |
| `TIMER` | Срабатывание таймера или истечение времени ожидания |
| `RECOVERY` | Запрос восстановления или результат сверки после перезапуска |

Согласованный каталог типов событий для текущего ядра:

| `event_type` | Категория | Назначение |
|---|---|---|
| `STARTUP_REQUESTED` | `COMMAND` | Запрошен запуск станции |
| `INITIALIZATION_COMPLETED` | `SUBSYSTEM` | Завершена инициализация программных компонентов и проверка конфигурации |
| `SELF_TEST_COMPLETED` | `SUBSYSTEM` | Завершена стартовая самодиагностика |
| `SUBSYSTEM_STATUS_UPDATED` | `SUBSYSTEM` | Изменился статус подсистемы, включая сообщение о неисправности |
| `OPERATION_STATUS_UPDATED` | `OPERATION` | Изменился статус конкретной операции |
| `SAFETY_PERMISSION_UPDATED` | `SAFETY` | Изменилось разрешение SafetyManager на конкретную операцию |
| `COMMAND_REQUESTED` | `COMMAND` | Получена команда от оператора или внутреннего координатора |
| `OPERATION_TIMEOUT` | `TIMER` | Истекло время ожидания операции |
| `RECOVERY_REQUESTED` | `RECOVERY` | Запрошено восстановление станции |
| `RECOVERY_RECONCILIATION_COMPLETED` | `RECOVERY` | Завершена сверка сохранённого состояния с актуальными отчётами подсистем |

Дополнительные правила контракта:

- Категория определяется только по точному совпадению `event_type` с зарегистрированным значением. Поиск подстрок, приблизительное совпадение и автоматическое приведение регистра запрещены.
- Неизвестный или пустой `event_type` получает результат классификации `UNKNOWN`. Это результат классификации, а не седьмая категория.
- Неисправность подсистемы передаётся через `SUBSYSTEM_STATUS_UPDATED`: конкретная подсистема и её статус указываются в `payload`; `reason_code` и `reason_text` указываются только при установленной причине. Отдельный тип события для каждой неисправности не создаётся.
- Для `OPERATION_STATUS_UPDATED` используется жизненный цикл и точные значения статусов из §19. Не следует создавать отдельный `event_type` для каждого статуса операции.
- Для `SAFETY_PERMISSION_UPDATED` используются `operation_id`, `permission` со значением `ALLOW`, `DENY` или `UNKNOWN`, а также предусмотренные §12 причина, срок действия и `safety_revision`.
- Для `COMMAND_REQUESTED` в `payload` указываются идентификатор и тип команды, отправитель и необходимые параметры. Например, `STOP_AUTOMATION` является значением типа команды, а не отдельным `event_type`.
- Для `OPERATION_TIMEOUT` указываются идентификатор операции и тип тайм-аута. Сам факт тайм-аута не доказывает, что физическое действие не состоялось.
- Классификация не подтверждает достоверность события, не разрешает переход глобального состояния и не даёт права на физическое действие. Статус `FAIL`, `UNKNOWN` или `DENY` сам по себе не переводит станцию в глобальное аварийное состояние.
- Изменение или расширение каталога требует согласованного обновления этого подраздела, `classify_event()` и её тестов.

## 3. Общие статусы данных

Предлагаемый набор общих статусов качества данных:

| Статус | Значение |
|---|---|
| OK | Значение получено и прошло проверку |
| STALE | Значение существует, но устарело |
| INVALID | Значение не прошло проверку |
| UNAVAILABLE | Ожидаемый источник недоступен |
| NOT_CONFIGURED | Источник/устройство не предусмотрен действующей конфигурацией и не ожидается |
| UNKNOWN | Достоверное состояние определить не удалось |
| ERROR | Ошибка получения или обработки данных |

Для телеметрии датчиков в §25.1 используется набор OK, STALE, INVALID, UNAVAILABLE, NOT_CONFIGURED, UNKNOWN. ERROR остаётся общим результатом ошибки получения/обработки, а не штатным состоянием измерения датчика.

NOT_CONFIGURED не означает, что ожидаемый конфигурацией датчик отсутствует или неисправен. Если устройство предусмотрено конфигурацией, но его доступность не удалось подтвердить, используется UNKNOWN или UNAVAILABLE в зависимости от достоверности сведений; подтверждённый отказ оценивается по контракту диагностики.

Внутреннее значение VALID, применяемое в отдельных контрактах к проверенному конверту события или результату валидации конфигурации, сохраняет своё специальное значение и не является альтернативным статусом качества телеметрии датчика.

Отсутствие данных не должно заменяться нулём. Например, «ветер неизвестен» — не то же самое, что «ветер 0 м/с».

Предварительная структура:

```json
{
  "timestamp": "временная метка",
  "source_id": "идентификатор метеостанции",
  "wind_speed_mps": null,
  "wind_direction_deg": null,
  "wind_gust_mps": null,
  "temperature_c": null,
  "relative_humidity_percent": null,
  "precipitation_status": "UNKNOWN",
  "pressure_hpa": null,
  "quality": "UNKNOWN"
}
```

Это иллюстрация структуры, не готовый формат протокола.

Поля должны иметь правила допустимого диапазона, периодичности и устаревания после выбора датчиков.

## 5. Контракт погодных разрешений

Предлагаемая структура:

```json
{
  "timestamp": "временная метка",
  "allow_takeoff": "UNKNOWN",
  "allow_normal_landing": "UNKNOWN",
  "allow_priority_recovery": "UNKNOWN",
  "allow_lid_open": "UNKNOWN",
  "allow_cleaning": "UNKNOWN",
  "allow_charging": "UNKNOWN",
  "reason_codes": []
}
```

Для всех разрешений используются единые машинные значения: `ALLOW`, `DENY`, `UNKNOWN`. Каждое разрешение должно иметь объяснение. Значение не должно быть обычным булевым флагом без возможности различить запрет и отсутствие данных.

Конкретные пороги должны храниться в конфигурации с версией и ссылкой на источник требований.

## 6. Контракт состояния станции

Снимок состояния должен различать глобальную фазу работы станции и статусы отдельных подсистем.

Предварительные поля снимка глобального состояния:

- идентификатор станции;
- версия программного обеспечения;
- текущее глобальное состояние станции;
- state_revision — версия/номер подтверждённого перехода;
- transition_id — идентификатор последнего подтверждённого перехода;
- время последнего подтверждённого перехода;
- активные operation_id, если есть;
- список активных предупреждений;
- время формирования снимка.

Состояния крышки, площадки, наличия БАС, зарядки, очистки, метеоподсистемы, связи с сервером и локального накопителя являются отдельными статусами подсистем. Их можно передавать в составе расширенного диагностического снимка, но нельзя трактовать как одно глобальное состояние станции.

Снимок должен указывать актуальность/качество статусов подсистем. Последнее известное значение с истёкшим сроком актуальности не должно представляться как подтверждённое текущее состояние.


### 6.1. Атомарная фиксация глобального перехода

Для фиксации глобального состояния используется StationStateRepository — логический порт одной атомарной операции, а не указание на отдельную физическую БД.

Входной TransitionPlan содержит ожидаемые состояние и state_revision, целевое состояние и уникальный transition_id. TransitionEvidence содержит нормализованное событие и доверенные подтверждения условий F05. F10 также получает `expected_cursor` — тот же снимок курсора источника/сессии, относительно которого вызывающий контур выполнил F04. Перед записью функция повторно проверяет общий конверт события, требует quality_status=VALID, повторно проверяет актуальность события через F04 и повторно применяет F05. Целевое состояние в плане должно в точности совпасть с разрешённым F05 результатом.

Повторный read-only вызов F04 защищает прямые вызовы F10 от заведомо устаревшего/неупорядоченного события, но сам по себе не закрывает конкурентную гонку. Для этого `StationStateRepository::commit_transition()` обязан атомарно сравнить все поля `expected_cursor` (source, source_instance и last_sequence) с сохранённым курсором данного источника. В той же транзакции репозиторий должен сохранить событие, новый snapshot и историю перехода, а затем продвинуть курсор до source/source_instance/source_sequence принятого события. Если сохранённый курсор успел измениться после проверки F04, репозиторий возвращает отдельный `SOURCE_CURSOR_CHANGED`; частичная фиксация запрещена.

StationStateRepository обязан атомарно:
- проверить совпадение сохранённых глобального state и revision с ожидаемыми значениями плана;
- проверить точное совпадение сохранённого курсора источника/сессии с `expected_cursor`, включая наличие/отсутствие source_instance и last_sequence;
- проверить уникальность event_id и transition_id;
- для повторного event_id сравнить все поля события, кроме received_at, который назначается принимающей стороной;
- сохранить новый snapshot, историю перехода, исходное событие и обновлённый source cursor одной транзакцией. Новый курсор содержит source, source_instance и source_sequence из принятого события.

Новая revision равна expected_revision + 1. Конкурентное изменение состояния возвращается как SNAPSHOT_CHANGED, конкурентное изменение курсора — как SOURCE_CURSOR_CHANGED; повтор, конфликт содержимого event_id и конфликт transition_id имеют отдельные результаты. Ошибка/неизвестный статус репозитория не считается успешной записью. До обращения к репозиторию F10 возвращает STALE_EVENT для регрессии source_sequence и EVENT_ORDER_UNKNOWN, если источник, сессия или последовательность не позволяют доказать актуальность события.

StateChanged публикуется только после подтверждённой фиксации. Оно содержит старое и новое глобальное состояние, новую revision, event_id, transition_id и известные reason_code/reason_text. При отказе хранилища публикации нет. Если же хранилище подтвердило commit, но Publisher вернул REJECTED/UNKNOWN, результат означает «состояние сохранено, публикация не подтверждена»; повторно выполнять commit запрещено.

Текущий интерфейс Publisher не обеспечивает durable outbox и не доказывает доставку всем получателям. До промышленной эксплуатации выбранный адаптер должен обеспечить outbox либо эквивалентную идемпотентную публикацию с восстановлением по transition_id. Хостовые fake-тесты проверяют только логический контракт и не доказывают транзакционность выбранного накопителя или сохранность при отключении питания.

### 6.2. Профильный обработчик стартовых событий (SSM-F13)

`GlobalTransitionProcessor` является профильной реализацией `EventProcessorPort` только для трёх точных пар первого согласованного среза:

| Событие | Категория | Разрешённая проверка перехода |
|---|---|---|
| `STARTUP_REQUESTED` | `COMMAND` | F05: ВЫКЛЮЧЕНА → ЗАПУСК |
| `INITIALIZATION_COMPLETED` | `SUBSYSTEM` | F05: ЗАПУСК → САМОПРОВЕРКА |
| `SELF_TEST_COMPLETED` | `SUBSYSTEM` | F05: САМОПРОВЕРКА → ОЖИДАНИЕ |

Все остальные пары возвращают `UNSUPPORTED`; наличие события в общем каталоге F02 не означает готовность профильного обработчика. Качество события для глобального перехода должно быть строго `VALID`.

Перед проверкой F05 обработчик читает последний подтверждённый snapshot через F16. Отсутствующий, повреждённый или недоступный snapshot не заменяется начальным состоянием по умолчанию. Для INITIALIZATION_COMPLETED и SELF_TEST_COMPLETED доверенный `TransitionContextProvider` возвращает подтверждения Configuration/Diagnostics/Recovery managers. Значения из `payload` не используются как доказательство. При `Unavailable` любые частичные положительные флаги отбрасываются; F05 получает безопасный контекст по умолчанию и отклоняет переход, требующий подтверждения.

Уникальный `transition_id` запрашивается у `TransitionIdProvider` только после разрешения F05. Затем F10 повторно проверяет событие/контекст и выполняет условную фиксацию snapshot, истории, исходного события и курсора. В F10 передаётся тот же `expected_cursor`, который проверял F04 в общем контуре F13.

Результат `COMMITTED_NOTIFICATION_NOT_CONFIRMED` означает, что snapshot и переход уже сохранены, но публикация StateChanged не подтверждена. Его нельзя трактовать как откат или повод повторить commit. Неизвестный результат, конфликт или конкурентное изменение не считается успехом. Обработчик не управляет GPIO, приводами, реле и не выполняет физических действий.

## 7. Контракт обнаруженного БАС

Данные обнаружения и аутентификации нужно разделять.

### Событие обнаружения

- идентификатор радиоустройства;
- тип радиоинтерфейса;
- время;
- измеренная сила сигнала, если доступна;
- предварительный идентификатор;
- статус обнаружения.

### Результат аутентификации

- идентификатор БАС;
- идентификатор станции;
- результат проверки;
- метод проверки;
- время;
- причина отказа.

Успешное обнаружение не означает успешную аутентификацию.

Предварительные поля:

- время измерения;
- идентификатор камеры;
- идентификатор маркера;

## 9. Контракт состояния крышки

Предлагаемые состояния:

- CLOSED — закрыта;
- OPEN — открыта;
- MOVING_OPEN — открывается;
- MOVING_CLOSE — закрывается;

События:

- команда открытия;

- достижение конечного положения;

- перегрузка;
- препятствие;

Команда должна иметь идентификатор операции. Подтверждение завершения не должно отправляться до проверки обратной связи.

## 11. Контракт передачи файлов

### Манифест

Для каждого файла:

- уникальный идентификатор;
- имя или безопасный относительный путь;
- размер в байтах;
- тип содержимого;
- время создания, если известно;
- контрольная сумма, если доступна;
- источник;
- статус передачи.

Имена файлов и пути считаются недоверенными входными данными. Нельзя позволять им создавать произвольные пути за пределами выделенной папки хранения.

### Статусы передачи

- DISCOVERED — найден;
- QUEUED — поставлен в очередь;
- TRANSFERRING — передаётся;
- PAUSED — приостановлен;
- VERIFYING — проверяется;
- LOCAL_COMPLETE — локальная копия проверена;
- UPLOADING — отправляется серверу;
- SERVER_CONFIRMED — сервер подтвердил приём;
- FAILED — ошибка;
- NEEDS_RETRY — требуется повтор.

## 12. Контракт безопасности и разрешения на операцию

Каждый функциональный исполнительный модуль должен запрашивать разрешение перед опасной операцией. Запрос содержит operation_id, тип действия, состояние оборудования и актуальные данные, необходимые для проверки.

Ответ должен связывать разрешение с конкретной операцией и содержать:

- operation_id;
- permission: ALLOW, DENY или UNKNOWN;
- reason_codes;
- valid_until или иной согласованный срок действия;
- safety_revision — версию правил, по которым принято решение.

При отсутствии ответа, истечении срока действия, отзыве разрешения или потере связи разрешение не считается действующим. Исполнительный модуль не должен выполнять опасную команду на основании старого разрешения. StationStateManager не вправе переопределять результат SafetyManager.

## 13. Контракт готовности площадки для БАС

Станция предоставляет БАС однозначный статус:

- READY — площадка готова для согласованного сценария;
- NOT_READY — площадка не готова;
- UNKNOWN — достоверная оценка невозможна.

В ответе указываются время, идентификатор станции, причина неготовности и срок актуальности статуса. Дальнейшее поведение аппарата при NOT_READY определяется его бортовым алгоритмом и заранее согласованной эксплуатационной процедурой.

## 14. Контракт бортовой системы и питания при обслуживании

После остановки двигателей часть бортовой электроники должна оставаться доступной в объёме, необходимом для передачи файлов, обмена с BMS и контроля зарядки. Конкретная схема питания и режимы низкого энергопотребления зависят от выбранного БАС.

Необходимо определить:
- какие бортовые узлы остаются включёнными;
- от какого источника они питаются;
- как станция получает статус питания;
- как исключается чрезмерный разряд аккумулятора во время длительной передачи;
- как зарядное устройство взаимодействует с BMS;
- что происходит при потере связи с BMS.

## 15. Контракт миссии

Минимальные поля задания:
- уникальный идентификатор миссии;
- идентификатор целевого БАС;
- версия формата;
- объект инспекции;
- план/маршрут или ссылка на него;
- время создания и срок действия (при наличии — время начала действия);
- источник задания;
- статус предварительного разрешения;
- статус отзыва/отмены, если задание отозвано;
- признак ручного подтверждения: REQUIRED, NOT_REQUIRED или UNKNOWN;
- ограничения выполнения.

Отсутствующий, нечитаемый или противоречивый признак ручного подтверждения трактуется как UNKNOWN и блокирует автоматический вылет. Конкретные типы миссий/режимов, для которых выставляется REQUIRED, определяются отдельно.

Конкретный формат маршрута и способ передачи автопилоту пока не определены. Наличие задания в очереди не означает автоматического разрешения на полёт: оно дополнительно проходит локальные проверки станции и БАС.

## 16. Интерфейс основного контроллера и вычислительного модуля

Необходимо определить двусторонний обмен:
- состояние вычислительного модуля;
- контрольный сигнал работоспособности (heartbeat);
- версия протокола;
- команды функциональных операций;
- результаты обработки изображения;
- запросы разрешения;
- ответы SafetyManager;
- ошибки и временные метки.

Потеря heartbeat вычислительного модуля не должна отключать или обходить локальную аппаратную защиту основного контроллера.

## 17. Контракт телеметрии и удалённых команд

Телеметрия должна иметь отдельную версионируемую схему и временную метку.

Удалённая команда должна содержать идентификатор, отправителя, срок действия, тип команды, параметры, подтверждение полномочий и защиту от повтора. Разрешённый каталог команд и роли пока не определены.

## 18. Контракт ошибки

Структурированное сообщение об ошибке должно включать:

- event_id и event_type;
- источник/модуль;
- error_code;
- severity: INFO, WARNING, ERROR или CRITICAL;
- понятное описание;
- operation_id и correlation_id, если ошибка относится к операции/запросу;
- время формирования и получения;
- качество/достоверность данных, если применимо;
- recovery_hint — рекомендацию или ссылку на утверждённую реакцию, но не произвольную команду;
- reason_text — короткое понятное описание установленной причины, если оно доступно.

Если причина не установлена, поле reason_text не заполняется предположением; интерфейс явно показывает, что причина неизвестна.

Само значение severity не задаёт автоматически глобальное состояние станции. Реакция выбирается по утверждённой политике конкретного отказа.

## 19. Идентификаторы операций и lifecycle

Каждая длительная операция должна иметь уникальный operation_id, который сохраняется в запросе, подтверждениях, промежуточных событиях, результате и ошибках. Для связи с исходным событием/командой использовать correlation_id.

В реализации SSM идентификатор запрашивается у отдельного логического порта OperationIdProvider. Функция формирования ActionRequest не задаёт формат или алгоритм ID и не проверяет глобальную уникальность самостоятельно: поставщик обязан не выдавать повторно идентификатор, который уже использовался или сохранён в истории операций станции. Это требование должно сохраняться и после перезапуска. Конкретный механизм (например, устойчивый счётчик, случайный идентификатор или иной вариант) не выбран до определения платформы и хранилища.

Текущие структуры ActionPlan и ActionRequest используют невладеющие string_view. Все исходные строки, включая выданный operation_id, должны оставаться действительными до тех пор, пока сохраняющий/исполняющий порт не скопирует или не сериализует данные во владеющее хранилище. Асинхронная очередь не должна удерживать эти представления без гарантии срока жизни. Это временное решение для переносимого хостового ядра; при выборе платформы, формата хранения и способа обмена необходимо проверить время жизни, стоимость копирования и ограничения памяти.

Статусы операции:

| Статус | Значение |
|---|---|
| REQUESTED | SSM зарегистрировал запрос и operation_id; передача исполнительному модулю ещё не подтверждена |
| ACCEPTED | Исполнитель принял запрос к обработке; физическое действие ещё не подтверждено |
| STARTED | Исполнитель подтвердил начало действия |
| COMPLETED | Действие завершено и требуемый результат подтверждён |
| FAILED | Исполнитель сообщил об отказе |
| CANCEL_REQUESTED | Запрошена отмена |
| CANCELLED | Исполнитель подтвердил отмену |
| OUTCOME_UNKNOWN | Нельзя достоверно определить, началось/завершилось ли физическое действие |

### 19.1. Рабочая матрица переходов lifecycle операции

Матрица ниже определяет допустимые переходы **между статусами одной операции**. Она не является матрицей глобальных состояний станции. Рабочее правило согласовано владельцем проекта 2026-11-05 для реализации SSM-F09.

| Текущий статус | Допустимый следующий статус |
|---|---|
| REQUESTED | ACCEPTED, FAILED, OUTCOME_UNKNOWN |
| ACCEPTED | STARTED, FAILED, CANCEL_REQUESTED, OUTCOME_UNKNOWN |
| STARTED | COMPLETED, FAILED, CANCEL_REQUESTED, OUTCOME_UNKNOWN |
| CANCEL_REQUESTED | CANCELLED, FAILED, OUTCOME_UNKNOWN |
| COMPLETED | Нет: терминальный статус |
| FAILED | Нет: терминальный статус |
| CANCELLED | Нет: терминальный статус |
| OUTCOME_UNKNOWN | Нет обычного перехода; только отдельная процедура сверки |

Правила применения матрицы:

1. Обычное событие `OPERATION_STATUS_UPDATED` может изменить только операцию, найденную по `operation_id`. `correlation_id` события должен совпадать с сохранённой связью этой операции. Неизвестный `operation_id` или несовпадение `correlation_id` не создаёт новую операцию и не обновляет существующую.
2. Перед обновлением используются проверки повторности события (SSM-F03) и порядка/актуальности (SSM-F04). Повторное событие не должно повторять побочные эффекты; конфликт, устаревшее или неупорядоченное событие не продвигает lifecycle.
3. Допускается только переход, прямо указанный в таблице. Пропуск статуса, обратный переход или переход из терминального статуса не разрешается по догадке. Для специализированной операции потребуется отдельное документированное и согласованное изменение матрицы.
4. Одновременные обновления одной операции не должны молча перезаписывать друг друга. Изменение сохраняется условно относительно актуальной версии/ревизии записи операции либо эквивалентным атомарным способом. Конкретный интерфейс репозитория для чтения и условного обновления будет определён перед реализацией F09.
5. `OUTCOME_UNKNOWN` блокирует обычные обновления lifecycle. Даже позднее сообщение `ACCEPTED`, `STARTED` или `COMPLETED` не снимает неопределённость автоматически. Разрешение возможно только через отдельную процедуру сверки с актуальными данными исполнителя/оборудования.
6. Изменение lifecycle само по себе не меняет глобальное состояние станции и не разрешает физическое действие. Для опасного действия исполнитель по-прежнему обязан проверить актуальное разрешение SafetyManager непосредственно перед выполнением.

Матрица намеренно консервативна. В частности, после `CANCEL_REQUESTED` обычным обновлением допускаются только `CANCELLED`, `FAILED` и `OUTCOME_UNKNOWN`; неожиданное сообщение о другом исходе требует сверки, а не автоматического выбора статуса.

### 19.2. Контракт атомарного обновления операции (SSM-F09)

Адаптер события преобразует распознанный статус в типизированное поле `OperationUpdate.next_status`; F09 не разбирает транспортный payload и не выбирает формат JSON. При этом исходный `Event` сохраняется как доказательство источника обновления.

Для общего входного контура F13 профильный `OperationUpdateEventProcessor` принимает только точную пару `OPERATION_STATUS_UPDATED / Operation` и требует `quality_status = VALID` до разбора данных. Он вызывает `OperationUpdateDecoderPort::decode_next_status(const Event&)`; доверенный адаптер преобразует payload конкретного формата в типизированный `OperationLifecycleStatus`. Формат payload этим интерфейсом не задаётся.

Процессор не изменяет исходный `Event` и передаёт его вместе с тем же `expected_cursor`, который F13 использовала для F04, в F09 `handle_operation_update()`. Только F09 проверяет lifecycle matrix, `operation_id`, `correlation_id`, дубликаты и порядок, а затем просит `OperationUpdateRepository` атомарно сохранить lifecycle, событие и курсор.

`Applied` отображается в `NoStateChange` (изменился lifecycle операции, но не глобальное состояние станции); `Duplicate` и `EventConflict` сохраняются; отклоняющие результаты F09 отображаются в `Rejected`; конкурентные изменения операции/курсора — в `ConcurrentUpdate`; ошибка репозитория и неизвестный код — в `Error`. `StaleEvent`/`EventOrderUnknown`, неожиданно возвращённые F09 после прохождения F13 с тем же immutable Event/SourceCursor, считаются ошибкой согласованности. `UnsupportedPayload` адаптера отклоняется; ошибка, неизвестный статус декодера или `Decoded` без `next_status` не считаются успехом.

Для обычного обновления F09 требует:
- корректный конверт события с `event_type = OPERATION_STATUS_UPDATED`, `operation_id`, `correlation_id` и непустыми обязательными полями;
- `quality_status = VALID`;
- доказуемый номер `source_sequence` и курсор того же `source`/сессии; отсутствующий номер, повторный номер или несовпадающая сессия не разрешают продвижение lifecycle;
- существующую запись операции, созданную F07; `operation_id` и `correlation_id` события должны совпасть с ней.

Запись операции содержит исходный ActionRequest, текущий lifecycle и revision. F07 создаёт начальную запись со статусом `REQUESTED` и revision=1. Каждое принятое F09 обновление увеличивает revision на единицу.

Логический порт `OperationUpdateRepository` объединяет чтение операции и поиск сохранённого события. Он предоставляет:
- `find_operation(operation_id)` — чтение снимка операции и её текущей revision;
- `find_by_id(event_id)` из `EventRepository` — read-only проверку ранее сохранённого события для F03;
- `commit_operation_update(expected_record, next_status, event, expected_cursor)` — одну атомарную фиксацию.

Атомарная фиксация обязана проверить, что revision/status операции и переданный курсор источника всё ещё актуальны; проверить уникальность `event_id`; сохранить новый lifecycle и revision, исходное событие и новый `source_sequence`. Эти данные не должны фиксироваться частично. Повторная доставка, пришедшая одновременно с первой, возвращает DUPLICATE_EVENT; тот же `event_id` с иным содержимым — EVENT_CONFLICT. Конкурентное изменение операции или курсора возвращается как отдельный конфликт, без автоматического повтора.

Обычный вызывающий слой получает текущий курсор источника из своего слоя приёма событий и передаёт его F09. После успешной фиксации он продвигает локальный снимок курсора. Реализация репозитория должна устойчиво хранить курсор и обеспечивать атомарное сравнение; конкретный способ его загрузки/восстановления определяется при реализации адаптера хранилища.

Все `string_view` в запросе, событии и курсоре являются невладеющими. Репозиторий обязан скопировать/сериализовать их до возврата из метода фиксации. Тестовый fake проверяет контракт и порядок действий, но не доказывает реальную транзакционность или сохранность после отключения питания.

Перед отправкой физически значимого запроса намерение и operation_id должны быть записаны через StateRepository. Новая запись получает lifecycle REQUESTED и может быть передана исполнителю только после подтверждения устойчивой фиксации. Хранилище обязано атомарно обеспечить уникальность operation_id: точный повтор ранее сохранённого ActionRequest возвращает ALREADY_SAVED_SAME и не разрешает повторную отправку; тот же operation_id с отличающимся содержимым возвращает CONFLICT. Ошибка/неопределённый результат записи не даёт права на отправку. Под «устойчивой фиксацией» понимается запись, которую можно восстановить после перезапуска; фактическая гарантия при внезапном отключении питания проверяется на выбранном накопителе.

F08 получает ActionRequest только вместе с точным подтверждением новой записи от F07. Подтверждение содержит копии невладеющих представлений полей запроса; перед вызовом ActionDispatcher все поля сравниваются без преобразования, включая различие между отсутствующими и пустыми parameters. Исходные строки должны оставаться доступными и неизменными до завершения F08. Если диспетчер ставит запрос в асинхронную очередь, он обязан скопировать или сериализовать все поля до возврата. Несовпадение или статус, отличный от PERSISTED, блокирует передачу.

ActionDispatcher маршрутизирует запрос по target_module и передаёт operation_id без изменения. Получающий функциональный менеджер обязан обеспечивать идемпотентность по operation_id: точный повтор распознаётся как ALREADY_KNOWN и не запускает действие заново; тот же ID с другими данными возвращает CONFLICT. Если достоверно подтверждён приём, возвращается ACCEPTED; если подтверждено, что запрос не принят, — REJECTED; если нельзя определить, дошёл ли запрос, — UNKNOWN. UNKNOWN не разрешает автоматический повтор или генерацию нового operation_id: требуется запросить состояние исходной операции/выполнить сверку.

Для F06–F09 идентификаторы operation_id, correlation_id, target_module и action не должны быть пустыми или состоять только из ASCII-пробельных символов (пробел, табуляция, CR, LF, form feed, vertical tab). Дополнительное ограничение на алфавит или формат идентификаторов этим правилом не вводится. Отсутствующие и пустые parameters при этом остаются разными допустимыми состояниями. Успешный OperationIdProvider обязан вернуть непробельный ID. Если OperationUpdateRepository::find_operation() возвращает FOUND, запись должна содержать корректный ActionRequest, известный lifecycle-статус и revision > 0; нарушение этого контракта трактуется как REPOSITORY_ERROR, а не как обновляемая операция.

ACCEPTED означает только принятие запроса функциональным менеджером. Это не подтверждение STARTED и не доказательство физического движения/выполнения. Для опасной операции функциональный менеджер отдельно проверяет актуальное разрешение SafetyManager непосредственно перед физическим действием.

Недопустимые перескоки между статусами должны отклоняться или классифицироваться как конфликт по правилам конкретной операции. Не все операции обязаны использовать каждый статус, но пропуск статуса допустим только если контракт исполнителя явно определяет эквивалентное подтверждение.

Операция считается физически завершённой только после требуемого подтверждения результата; одного сообщения ACCEPTED недостаточно.

К событию обновления операции может прилагаться необязательная пара reason_code и reason_text: машинный код и короткое описание причины отказа/блокировки, если причина идентифицирована. Эти поля не образуют новый статус lifecycle и не заменяют код ошибки. Если причина не установлена, она не придумывается.

## 20. Идемпотентность, повторы и порядок событий

Повторная доставка одной и той же команды или события не должна повторно запускать физическое действие или повторно фиксировать переход.

Нужно различать:

- event_id — идентификатор сообщения/события для обнаружения повторной доставки;
- command_id — идентификатор команды, если он отделён от события;
- operation_id — идентификатор длительной операции;
- correlation_id — связь запроса и последующих событий.

Повтор с тем же идентификатором и тем же содержимым обрабатывается идемпотентно: повторный побочный эффект не выполняется, ранее известный результат может быть возвращён повторно. Тот же идентификатор с другим содержимым считается конфликтом и журналируется.

### 20.1. Сравнение повторно доставленных событий

Для проверки по `event_id` используется логический порт `EventRepository`, который предоставляет поиск ранее сохранённого события. Результат поиска должен различать найденную запись, отсутствие записи и ошибку чтения. При статусе `NOT_FOUND` представление `event` должно быть полностью пустым: все текстовые поля пусты, все optional-поля и `source_sequence` отсутствуют. Любое заполненное поле при `NOT_FOUND` является противоречивым ответом. Ошибка чтения или противоречивый ответ хранилища не трактуется как отсутствие события и блокирует дальнейшую обработку.

При сравнении содержимого учитываются все поля конверта и `payload`, кроме `received_at`. Это поле назначается принимающей стороной и может отличаться при повторном получении того же события. Остальные текстовые поля и непрозрачное содержимое `payload` сравниваются точно, без нормализации или преобразования.

Результаты проверки:

- `NEW` — запись с таким `event_id` не найдена;
- `DUPLICATE` — запись найдена, её содержимое совпадает;
- `CONFLICT` — `event_id` уже используется, но содержимое отличается;
- `REPOSITORY_ERROR` — поиск завершился ошибкой или вернул противоречивую запись.

`check_duplicate_event()` выполняет только чтение: не меняет входное событие и не сохраняет его. `NEW` означает отсутствие записи на момент проверки, а не резервирование идентификатора. Сохранение результата обработки и координация с побочными действиями должны быть обеспечены вызывающим контуром до выполнения физически значимого действия. Защита от конкурентной параллельной обработки одного `event_id` отдельно определяется при реализации `handle_event()`; сама функция проверки не заявляет атомарного резервирования. F03 сообщает только статус NEW/DUPLICATE/CONFLICT/REPOSITORY_ERROR и не возвращает сохранённый результат обработки: его получение относится к последующему контракту оркестрации.

Если источник передаёт source_sequence, события от одного экземпляра источника проверяются на нарушение последовательности. При отсутствии последовательного номера нельзя определять устаревание только по календарному времени: часы источников могут быть рассинхронизированы. Для операций дополнительно проверяются operation_id и допустимость перехода lifecycle.

### 20.2. Общий входной контур обработки события (SSM-F13)

Общий вход нормализованных событий выполняется функцией `handle_event()` через логический порт `EventProcessorPort`. Этот порт не является транспортом, форматом payload или отдельным физическим устройством.

До передачи события профильному обработчику общий контур выполняет проверки в следующем порядке:
1. F01 `validate_event()` — структурная корректность конверта с `EventValidationPolicy`, полученной от доверенного адаптера источника.
2. F02 `classify_event()` — точное определение одной из шести зарегистрированных категорий. Неизвестный тип не маршрутизируется.
3. F03 `check_duplicate_event()` — read-only проверка `event_id`. DUPLICATE, CONFLICT и REPOSITORY_ERROR прекращают обработку.
4. F04 `check_event_freshness()` — проверка `source`, `source_instance` и `source_sequence` относительно переданного `SourceCursor`. Продолжается только CURRENT; STALE и UNORDERED не передаются обработчику.
5. `EventProcessorPort::process(event, category, expected_cursor)` — передача события профильному обработчику.

Профильный обработчик разбирает payload только по контракту конкретного типа события и применяет соответствующие правила. Он может обращаться к F05/F10, F09, F11, F12 и другим функциям по назначению. Общий контур F13 не разбирает payload, не назначает значения статусов из произвольных строк, не меняет глобальное состояние самостоятельно и не выполняет управление GPIO, реле или двигателями.

Статусы `EventProcessorPort`:
- `PROCESSED` — профильная обработка завершена и результат подтверждён;
- `NO_STATE_CHANGE` — событие принято и обработано, но глобальное состояние станции не изменилось;
- `REJECTED` — профильные правила отклонили событие;
- `UNSUPPORTED` — профильный обработчик для события пока отсутствует;
- `DUPLICATE` / `EVENT_CONFLICT` — повтор или конфликт выявлен при атомарной повторной проверке;
- `CONCURRENT_UPDATE` — ожидаемая запись или курсор изменились до фиксации;
- `ERROR` — результат обработки/фиксации не подтверждён.

**Обязательное условие конкурентной безопасности:** F03 и F04 являются предварительными read-only проверками. Между проверкой и обработкой другой поток может принять то же событие или продвинуть курсор. Поэтому реализация `EventProcessorPort` обязана повторно проверить уникальность `event_id` и актуальность `expected_cursor` атомарно с записью профильного результата. Для успешного результата она должна подтвердить фиксацию события и курсора вместе с тем изменением состояния, которое вызвано событием. Если используемое хранилище не может обеспечить такую согласованность, обработчик возвращает CONCURRENT_UPDATE/ERROR и не заявляет успех. Слепой повтор физической команды запрещён.

F13 не продвигает курсор самостоятельно. Он передаёт ожидаемый курсор обработчику, а продвижение выполняется только в его транзакции. Профильные обработчики стартовых переходов, обновления lifecycle и тайм-аутов, а также EventProcessorRouter реализованы как логические компоненты и имеют отдельные хостовые/контрактные тесты. Реальные адаптеры постоянного хранилища и application/bootstrap-подключение всех компонентов ещё не реализованы. В частности, согласование записи курсора с фиксацией глобального перехода через StationStateRepository остаётся обязательной задачей физического адаптера; наличие F10 и тестируемого интерфейсного контракта само по себе не доказывает физическую атомарность.

`quality_status` не подменяется значением VALID. Структурно корректное событие со статусом UNKNOWN/UNAVAILABLE может быть передано профильному обработчику, если это нужно для отражения неизвестного состояния подсистемы. Каждый профильный обработчик обязан отдельно проверять качество, требуемое его контрактом; UNKNOWN/STALE/INVALID/ERROR не могут служить основанием для опасного действия или перехода, который требует достоверного подтверждения.

Физически значимая команда по-прежнему проходит через сохранение намерения F07 и диспетчеризацию F08. Функциональный исполнитель повторно проверяет актуальный ALLOW от SafetyManager непосредственно перед опасным действием.

### 20.3. Запуск восстановления после перезапуска (SSM-F14)

`RecoveryRepository` — логический порт; его может реализовать тот же физический адаптер хранения, что и другие repository-интерфейсы. Отдельная база данных не требуется. Порт предоставляет:
- `load_snapshot()` — чтение последнего подтверждённого `StationStateSnapshot`; результат различает FOUND, NOT_FOUND и ERROR;
- `mark_recovery_in_progress(expected_snapshot)` — атомарную проверку ожидаемых state/revision и устойчивую установку признака RECOVERY_IN_PROGRESS. Результат различает MARKED, ALREADY_IN_PROGRESS, SNAPSHOT_CHANGED и ERROR.

Повторная установка того же маркера должна быть идемпотентной. Более новый snapshot нельзя перезаписывать маркером, основанным на устаревшей revision. В начальном snapshot revision=0 transition_id должен быть пустым; для положительной revision transition_id обязателен. Неизвестное значение глобального состояния или противоречивая связь revision/transition_id делает snapshot недопустимым для начала автоматического восстановления.

`RecoveryReportRequester::request_fresh_reports(snapshot)` запрашивает актуальные отчёты применимых подсистем. Ответ различает ACCEPTED, ALREADY_PENDING, REJECTED, UNKNOWN и ERROR. Этот порт только инициирует чтение/сбор данных: он не выдаёт команды приводам, зарядке, очистке и другим физическим исполнительным модулям. Повторный запрос для того же snapshot должен быть безопасным.

Порядок F14: LOAD SNAPSHOT → VALIDATE → MARK RECOVERY_IN_PROGRESS → REQUEST FRESH REPORTS. Запрашивать отчёты до подтверждённой установки постоянного маркера нельзя. Если загрузка/валидация/фиксация маркера не удалась, отчёты не запрашиваются. Если запрос отчётов отклонён или его результат неизвестен, маркер остаётся установленным, чтобы следующая попытка могла безопасно повторить запрос.

ACCEPTED/ALREADY_PENDING не означает, что свежие отчёты уже получены. Их получает доверенный адаптер, который подтверждает источник, свежесть и привязку к попытке восстановления; F15 проверяет переданный статус качества и сопоставляет отчёты с сохранёнными операциями. Сам F14 не сверяет оборудование, не снимает маркер восстановления, не выбирает новое глобальное состояние и не возобновляет незавершённые физические операции. Политика снятия маркера после успешной сверки должна быть реализована отдельной согласованной операцией.


### 20.4. Сверка после перезапуска (SSM-F15)

F15 получает исторический `StationStateSnapshot` и агрегат `RecoveryReports`. Это логические структуры; конкретный транспорт, формат payload и аппаратные протоколы не задаются.

`RecoveryReports` содержит:
- `subsystem_collection` — подтверждение, что адаптер собрал все применимые сводные отчёты подсистем;
- массив `RecoverySubsystemReport` с уникальным `subsystem_id`, качеством данных и нормализованным условием `SAFE`, `UNSAFE` или `UNKNOWN`;
- полный список сохранённых незавершённых `OperationRecord`;
- свежие `RecoveryOperationReport` от исполнительных модулей для этих операций, с `operation_id`, `correlation_id`, качеством и фактическим исходом `NOT_EXECUTED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, `CANCELLED` или `UNKNOWN`.

Правила сверки:
1. Snapshot проверяется на известное глобальное состояние и согласованность revision/transition_id. Он остаётся исторической записью и не доказывает положение оборудования.
2. Для результата `EvidenceComplete` необходимы полные коллекции, хотя бы один сводный отчёт подсистемы, уникальные ID отчётов, `quality=VALID` и `condition=SAFE` для каждой применимой подсистемы.
3. Список незавершённых операций должен содержать только корректные нетерминальные записи: непробельные `operation_id`, `correlation_id`, `target_module` и `action`, а также `revision > 0`. Для каждой записи требуется ровно один свежий отчёт с точным совпадением `operation_id` и `correlation_id`; лишний, дублирующий или чужой отчёт является конфликтом. Повреждённая сохранённая запись даёт INVALID_INPUT, а не считается отсутствующей операцией.
4. `UNKNOWN`, устаревшее, недоступное, невалидное или неполное свидетельство не закрывает сверку. Подтверждённая `UNSAFE` подсистема, выполняющаяся операция и конфликт получают отдельные результаты.
5. Сохранённый `STARTED` противоречит актуальному достоверному отчёту `NOT_EXECUTED`. Такая пара не считается согласованной.
6. `EvidenceComplete` означает только, что собранные сведения полны, актуальны, безопасны по нормализованным отчётам и не содержат выявленных противоречий. Это не разрешение на физическое действие и не автоматическое возобновление миссии.

Качество `VALID` вправе выставить только доверенный адаптер после проверки источника и свежести данных. Адаптер также обязан гарантировать полноту набора «все применимые подсистемы» и «все незавершённые операции». Пока не определены идентификатор попытки восстановления и способ привязки асинхронного отчёта именно к этой попытке, это требование остаётся открытой интеграционной зависимостью: одних `operation_id/correlation_id` недостаточно для общей корреляции отчётов подсистем.

F15 не меняет глобальное состояние, не записывает lifecycle, не снимает `RECOVERY_IN_PROGRESS`, не выбирает между ОГРАНИЧЕННЫМ РЕЖИМОМ / ОЖИДАНИЕМ ВМЕШАТЕЛЬСТВА / АВАРИЙНЫМ СОСТОЯНИЕМ и не отправляет физические команды. Связь конкретного глобального состояния с ожидаемыми состояниями подсистем не кодируется, пока полная матрица переходов и политика восстановления не утверждены. Снятие маркера и применение результатов сверки требуют отдельной согласованной процедуры.



### 20.5. Чтение глобального snapshot (SSM-F16)

StationStateSnapshotReader — read-only порт последнего подтверждённого снимка глобального состояния. Поля state, revision и transition_id должны быть прочитаны из одной атомарно сохранённой записи; нельзя собирать их из разных версий. Его может реализовать тот же физический адаптер хранения, что и StationStateRepository, StateRepository и RecoveryRepository; отдельное хранилище не требуется.

read_snapshot() возвращает один из статусов:
- FOUND — snapshot прочитан и возвращён как std::optional со значением;
- NOT_FOUND — подтверждённой записи нет;
- ERROR — чтение не подтверждено.

Если порт вернул FOUND без значения snapshot, F16 считает такой ответ повреждённым и возвращает INVALID_SNAPSHOT.

F16 get_snapshot(reader) выполняет одно чтение и проверяет:
1. глобальное состояние входит в объявленный StationState;
2. при revision=0 transition_id пуст;
3. при revision>0 transition_id непустой и не состоит только из пробельных символов.

Результат различает AVAILABLE, NOT_FOUND, INVALID_SNAPSHOT и READ_ERROR. Snapshot в результате F16 также имеет тип std::optional и присутствует только при AVAILABLE. При ошибке, неизвестном статусе порта или повреждённом snapshot функция не подставляет начальное состояние и не предоставляет значение snapshot.

Функция read-only: не меняет состояние, revision, историю, маркер восстановления и не обращается к оборудованию. transition_id — невладеющий string_view; адаптер обязан обеспечить срок жизни строки не меньше срока использования возвращённого результата вызывающим кодом. Реальный адаптер и устойчивость чтения при потере питания остаются интеграционной задачей.




### 20.6. Чтение истории глобальных переходов (SSM-F17)

F17 читает из того же долговременного хранилища только подтверждённые записи истории, создаваемые одной транзакцией F10 вместе с новым snapshot и исходным событием. Адаптер истории должен выдавать каждую запись ровно один раз; уникальность event_id и transition_id обеспечивается транзакцией F10. Минимальная запись содержит прежнее/новое состояние, revision после перехода, event_id, transition_id и парную причину reason_code/reason_text, если она известна. История не заменяет EventLogger: исходное событие и подробные диагностические сведения остаются в профильном журнале и связываются по event_id.

TransitionHistoryFilter содержит необязательные включительные minimum_revision и maximum_revision, а также resulting_state для фильтрации по целевому состоянию. Противоречивый диапазон или неизвестное значение состояния отклоняются до обращения к хранилищу.

TransitionHistoryReader возвращает COMPLETE, INCOMPLETE или ERROR. COMPLETE означает полный набор, соответствующий фильтру, в пределах доступной адаптеру политики хранения; записи должны идти строго по возрастанию revision и не повторяться. INCOMPLETE никогда не выдаётся вызывающему коду как полноценная история: частичные записи отбрасываются. Ошибка и неизвестный статус также не возвращают записи.

F17 проверяет известность исходного/целевого состояния, положительную revision, различие состояний, непустые event_id/transition_id, согласованность парной причины, порядок revision и соответствие фильтру. Пустая полная выборка возвращается как EMPTY, корректная непустая — AVAILABLE; повреждённая запись или порядок — INVALID_HISTORY. Результат содержит владеющие строки, не зависящие от времени жизни буфера адаптера.

F17 не меняет состояние, историю или маркер восстановления, не публикует события и не обращается к оборудованию. Глубина хранения, срок хранения и политика архивирования истории остаются открытыми решениями; адаптер обязан сообщать INCOMPLETE, если не может подтвердить полноту требуемой выборки. Запрос истории вызывается вне критического контура управления.


### 20.7. Композиция профильных обработчиков F13

`EventProcessorRouter` реализует тот же `EventProcessorPort`, который принимает `handle_event()`. В F13 передаётся один экземпляр маршрутизатора; он выбирает профиль по точному совпадению пары `event_type + EventCategory`.

Текущая таблица поддерживаемых маршрутов:

| `event_type` | Категория | Профильный обработчик |
|---|---|---|
| `STARTUP_REQUESTED` | `COMMAND` | `GlobalTransitionProcessor` |
| `INITIALIZATION_COMPLETED` | `SUBSYSTEM` | `GlobalTransitionProcessor` |
| `SELF_TEST_COMPLETED` | `SUBSYSTEM` | `GlobalTransitionProcessor` |
| `OPERATION_STATUS_UPDATED` | `OPERATION` | `OperationUpdateEventProcessor` |
| `OPERATION_TIMEOUT` | `TIMER` | `OperationTimeoutEventProcessor` |

Три стартовые пары направляются одному экземпляру `GlobalTransitionProcessor`. Для каждого точного ключа таблицы допускается только один обработчик. Пустой тип, категория UNKNOWN, нулевой указатель, пустая таблица или повторный ключ делают конфигурацию недопустимой; при такой конфигурации маршрутизатор возвращает ERROR и не вызывает профили. Конфигурацию можно проверить до запуска приёма через `is_configured()`.

Для совпавшей пары вызывается ровно один обработчик. Последовательный перебор профилей с попыткой передать событие следующему после начала обработки запрещён: это исключает неоднозначность и риск нескольких побочных эффектов. Если точного маршрута нет, возвращается UNSUPPORTED. Если уже выбранный и зарегистрированный обработчик вернул UNSUPPORTED либо неизвестный код статуса, это считается ошибкой согласования маршрута и возвращается ERROR. Остальные известные статусы передаются в F13 без изменения.

Массив маршрутов, строки `event_type` и объекты профильных обработчиков не принадлежат маршрутизатору: они должны оставаться действительными и неизменными всё время его использования. Маршрутизатор не выполняет F01–F04, не разбирает payload, не продвигает source cursor и не выполняет запись состояния. Это только композиция уже реализованных профильных обработчиков.

Наличие типа в общем каталоге F02 само по себе не создаёт маршрут. В частности, SUBSYSTEM_STATUS_UPDATED, SAFETY_PERMISSION_UPDATED, COMMAND_REQUESTED и события восстановления остаются UNSUPPORTED, пока для них не появятся согласованные профильные обработчики. Компонент StationEventPipeline собирает пять текущих маршрутов, принимает доверенную политику валидации и вызывает handle_event() с одним экземпляром EventProcessorRouter. Он не создаёт сами профильные обработчики и их зависимости: приложение обязано сконструировать их до создания pipeline и обеспечить срок их жизни.

### 20.8. Точка входа StationEventPipeline (SSM-F13)

StationEventPipeline — application-facing композиция общего входа F13 и текущих профильных обработчиков. Конструктор получает:
- общий read-only EventRepository для предварительной проверки повторов F03;
- один EventProcessorPort для трёх стартовых пар GlobalTransitionProcessor;
- EventProcessorPort для OPERATION_STATUS_UPDATED / Operation;
- EventProcessorPort для OPERATION_TIMEOUT / Timer.

Внутри pipeline создаётся фиксированная таблица из пяти точных пар, маршрутизатор и вызов handle_event(). Метод handle(event, validation_policy, expected_cursor) выполняет F01–F04 и передаёт событие одному выбранному профилю. Политика обязательных полей поступает от доверенного адаптера источника, а курсор должен соответствовать тому же source/session.

Pipeline не владеет репозиторием или профильными обработчиками. Они должны жить дольше pipeline. Объект не копируется и не перемещается, чтобы внутренний маршрутизатор сохранял корректную ссылку на собственную таблицу. handle() не продвигает курсор: это разрешено только подтверждённой транзакцией выбранного профиля.

Pipeline является готовой логической точкой подключения F13, но не исполняемым приложением. В репозитории пока нет application main/bootstrap, который создаёт физические адаптеры хранения, декодеры и профили, запускает транспорт приёма и восстанавливает курсоры. Эти зависимости должны быть добавлены после выбора платформы и хранения.


## 21. Тайм-ауты и неопределённый результат

Для каждого обмена/операции необходимо определить:

- время ожидания ответа;
- максимальное время операции;
- число повторов и условия их допустимости;
- поведение при повторном запросе;
- поведение при позднем ответе;
- поведение при потере связи;
- способ проверки фактического результата после тайм-аута.

Точные значения определяются после выбора оборудования и протоколов.

Тайм-аут после возможной передачи физической команды не доказывает, что команда не исполнилась. До получения достоверного состояния операция получает OUTCOME_UNKNOWN. Автоматический повтор движения/зарядки/очистки запрещён, пока конкретная политика операции не разрешит повтор после проверки фактического состояния и условий безопасности.


### 21.1. Обработка события OPERATION_TIMEOUT (SSM-F11)

Событие OPERATION_TIMEOUT формируется логическим Timer только после истечения заданного для конкретного этапа срока по монотонному времени. Длительности и правила запуска Timer зависят от конкретной операции, оборудования и протокола; F11 не задаёт их и не использует календарные часы.

Типизированный вход F11 содержит исходное событие, один из видов тайм-аута (до отправки, ожидание ответа диспетчера, ожидание завершения операции или подтверждения отмены) и явную оценку DispatchCertainty:
- NotDispatched — F08 ещё не вызывался, поэтому запрос точно не мог достичь исполнителя;
- MayHaveBeenDispatched — запрос мог достичь исполнителя или результат отправки неизвестен.

Значения по умолчанию для timeout_type и dispatch_certainty — UNKNOWN; они отклоняются без обращения к хранилищу. Допустимые сочетания: BeforeDispatch + NotDispatched; любой тайм-аут после передачи + MayHaveBeenDispatched. Противоречивое сочетание отклоняется. Timer обязан указывать operation_id, correlation_id, source_sequence и идентификатор своей сессии, если он может перезапускаться.

F11 повторно проверяет конверт, требует quality_status=VALID, точный event_type=OPERATION_TIMEOUT, проверяет повторность через F03 и последовательность через F04, находит существующую операцию и сверяет correlation_id. F11 не создаёт новую операцию.

Правило изменения lifecycle:
- BeforeDispatch при REQUESTED и доказанном NotDispatched переводит операцию в FAILED: команда не отправлялась и физическое действие через неё не могло начаться;
- DispatchResponse при REQUESTED и MayHaveBeenDispatched переводит в OUTCOME_UNKNOWN;
- OperationCompletion при REQUESTED/ACCEPTED/STARTED и MayHaveBeenDispatched переводит в OUTCOME_UNKNOWN;
- CancellationCompletion при CANCEL_REQUESTED и MayHaveBeenDispatched переводит в OUTCOME_UNKNOWN;
- повторный тайм-аут не меняет уже установленный OUTCOME_UNKNOWN; тайм-аут, пришедший после COMPLETED/FAILED/CANCELLED или после продвижения операции за соответствующий этап, игнорируется без изменения записи.

Изменение lifecycle и сохранение исходного OPERATION_TIMEOUT/event_id/source_sequence выполняются одной атомарной операцией OperationUpdateRepository. Применяется та же рабочая матрица lifecycle §19.1. Конкурентное изменение операции/курсора не повторяется автоматически.

Поздний ответ после OUTCOME_UNKNOWN не открывает lifecycle обычным событием. Требуется отдельная сверка фактического состояния с исполнителем/оборудованием; F11 не повторяет физическую команду, не выбирает новую миссию и не меняет глобальное состояние станции. F10 не вызывается: для тайм-аутов пока нет согласованных правил изменения глобального состояния.


### 21.2. Профильный обработчик события (F13 → F11)

`OperationTimeoutEventProcessor` реализует `EventProcessorPort` для точной пары `OPERATION_TIMEOUT / Timer`. Другие категории и типы событий он возвращает как `Unsupported`; сам по себе этот адаптер не является универсальным маршрутизатором всех профилей F13.

До вызова декодера проверяется `quality_status = VALID`. `OperationTimeoutDecoderPort::decode_timeout(const Event&)` преобразует непрозрачный payload в типизированные `OperationTimeoutType` и `DispatchCertainty`; формат сериализации не закрепляется. Ошибка декодера и неизвестный код его результата дают `Error`, неподдерживаемый payload и значения `UNKNOWN` — `Rejected`.

После успешного декодирования адаптер формирует `OperationTimeout` и передаёт в F11 исходный `Event`, исходный `expected_cursor` и общий `OperationUpdateRepository` без изменения данных. F11 остаётся единственным владельцем проверок F03/F04, поиска операции, правил lifecycle и атомарной фиксации.

Результат F11 отображается в общий статус F13 следующим образом: `Applied` → `NoStateChange`; `Duplicate` и `EventConflict` сохраняются; отклоняющие результаты → `Rejected`; конкурентное изменение операции/курсора → `ConcurrentUpdate`; ошибки, устаревший или неупорядоченный курсор и неизвестный код → `Error`.

Контрактный тест адаптера использует заглушку F11 и проверяет границу маршрутизации, качество данных, передачу исходных значений и отображение результатов. Он не заменяет модульные тесты `handle_operation_timeout()` и не подтверждает интеграцию реального репозитория или Timer.

## 22. Временные метки и синхронизация

Необходимо определить источник календарного времени станции и БАС, способ синхронизации и допустимую погрешность.

Время события, время получения и время обработки — разные понятия. Для анализа полёта и передачи данных желательно хранить исходные временные метки и не подменять их временем получения на сервере.

Для измерения интервалов, контроля длительности операций и тайм-аутов должна использоваться абстракция монотонного времени, не зависящая от коррекции календарных часов. Календарное время применяется для журналов, аудита и сопоставления с внешними системами. Конкретная реализация Clock/Timer определяется после выбора платформы.

## 23. Версионирование интерфейсов

Каждый внешний контракт должен иметь версию.

Изменение обязательного поля, единицы измерения, семантики статуса или системы координат считается изменением интерфейса и требует проверки всех зависимых модулей.

## 24. Что пока не утверждено

- JSON или другой формат сообщений;
- MQTT, HTTP, WebSocket или другой сетевой транспорт;
- MAVLink или другой интерфейс автопилота;
- Modbus RTU или другой интерфейс метеостанции;
- формат временных меток;
- точные единицы и диапазоны отдельных полей;
- периодичность обновления;
- способ идентификации устройства;
- структура файлового манифеста;
- геодезическая система координат, формат координат/треков/плановых маршрутов, частота обновления и допустимая точность;
- картографический поставщик, лицензии, офлайн-режим, локальное кэширование и детализация отображения трека.

Не реализовывать окончательный протокол на основании только примеров из этого документа.

## 25. Контракты операторского приложения

### 25.1. Сводка телеметрии датчика

Каждый зарегистрированный датчик должен предоставлять общий набор полей (точная схема и формат пока не выбраны):
- sensor_id — стабильный уникальный идентификатор;
- name и measurement_type — название и измеряемая величина;
- value и unit — значение и единица измерения, если измерение числовое;
- quality_status — OK, STALE, INVALID, UNAVAILABLE, NOT_CONFIGURED или UNKNOWN;
- measured_at и received_at — время измерения и получения;
- source_module — источник данных;
- error_code / description — причина отсутствия или недостоверности данных.

Не все типы датчиков обязаны иметь числовое value: дискретный концевой выключатель может передавать состояние. Нельзя подменять отсутствующее значение нулём или показывать его как нормальное.

### 25.2. Удалённая команда

Команда от приложения должна содержать:
- `command_id` — уникальный идентификатор команды;
- `station_id` — постоянный идентификатор целевой станции;
- `actor_id/user_id` и идентификатор сессии/подтверждённого контекста авторизации;
- `command_type` и `payload` — тип команды и параметры;
- `issued_at` и `expires_at` — время выпуска и срок действия;
- `nonce` или `sequence_number` — защита от повторной доставки;
- `correlation_id`, а для длительной операции — `operation_id`;
- `contract_version` — версия контракта.

Поля пользователя и роли, переданные клиентом, сами по себе не считаются доказательством полномочий. Их проверяет доверенный сервис/станция. При исполнении получатель проверяет адресата, срок действия, авторизацию и отсутствие повтора. Для команд, которые сервер может хранить и пересылать, необходимо обеспечить криптографически проверяемый контекст полномочий и защиту очереди от подмены.

Результат включает статус lifecycle операции, reason_code и короткое reason_text при установленной причине, источник блокировки и временные метки формирования/получения. Повторная доставка одной команды не должна повторять побочный эффект.

### 25.3. Команды обслуживания

Перезапуск модуля должен передавать стабильный module_id, идентификатор команды, пользователя и причину запроса. Станция проверяет, входит ли модуль в разрешённый каталог перезапуска и безопасны ли текущие условия.

Перезагрузка станции — отдельный тип команды. Она не должна представляться как перезапуск основного модуля или аппаратное отключение питания.

### 25.4. Привязка пользователя к станции

Сервис управления доступом должен хранить связь:
- user_id;
- station_id;
- роль/набор полномочий;
- статус привязки;
- кто и когда создал/изменил/отозвал привязку.

После отвязки ранее выданная сессия или токен доступа к этой станции должны быть отозваны. Сам station_id не является секретом и не служит самостоятельным доказательством права доступа.

### 25.5. Идентичность станции и регистрация

Реестр станций должен предоставлять:
- `station_id` — постоянный уникальный идентификатор;
- `inventory_number` — человекочитаемый номер, назначаемый администратором в пределах пространства учёта (предложение, см. REQ-APP-023/DEC-030);
- `hardware_serial` — заводской серийный номер, если он имеется;
- `display_name` — редактируемое отображаемое имя;
- `enrollment_status` — состояние первичной регистрации;
- `device_key_id` / `certificate_fingerprint` — ссылка на ключ или отпечаток сертификата, без передачи приватного ключа;
- `certificate_status` — ACTIVE, EXPIRED, REVOKED, PENDING или UNKNOWN;
- `created_at`, `registered_by`, `retired_at` и статус жизненного цикла станции.

Изменение `display_name` или `inventory_number` не меняет `station_id). Зарегистрированный `station_id` нельзя редактировать или повторно использовать. Повторное предъявление уже зарегистрированной идентичности требует процедуры восстановления/передачи владения и аудита.

### 25.6. Канал подключения

Клиент должен передавать или фиксировать тип подключения: SERVER, WIFI_LOCAL или WIRED_LOCAL, а также сведения о сессии/соединении. Транспорт не меняет семантику команд и статусов.

### 25.7. Видеопоток

Доступ к видеопотоку/кадрам должен иметь отдельное право и отдельный идентификатор сессии. Формат потока, протокол, ограничения качества и поведение при потере канала остаются открытыми.

Просмотр оператором и видеозапись — независимые функции. Открытие/закрытие потока не должно само по себе запускать/останавливать запись. Для текущего прототипа оператор явно запускает запись отдельным запросом и останавливает её отдельным запросом; запись продолжается до запроса остановки. После остановки станция завершает файл и возвращает фактический результат сохранения. Запись не запускается автоматически при старте камеры или приложения.

Если настроенное локальное хранилище отсутствует или недоступно, просмотр камеры может продолжаться, но запрос записи отклоняется с явным статусом/причиной. Нельзя возвращать успешный результат записи без подтверждённого сохранения файла. Конкретные имена полей, формат файла, кодек и транспорт видеопотока определяются отдельно.


### 25.8. Реестр БАС и текущий аппарат

Одна станция может иметь несколько зарегистрированных/закреплённых БАС. Операторское приложение должно показывать список таких аппаратов, их идентификаторы, конфигурацию, статус регистрации/доверия и доступность; уполномоченный пользователь должен иметь возможность управлять привязкой в пределах своих прав.

Для одного физического цикла приёма, посадки и обслуживания выбирается один целевой БАС. Одна физическая зона станции не принимает и не обслуживает несколько БАС одновременно. Обнаружение неизвестного устройства не должно автоматически добавлять его в список разрешённых.

Способ обнаружения, аутентификации и визуального/физического сопоставления определяется отдельно для каждой поддерживаемой модели или конфигурации БАС. Список зарегистрированных аппаратов не означает, что все они могут быть распознаны одним и тем же радиомеханизмом.

### 25.9. Политика допуска миссий при недоступности сервера

По умолчанию потеря сервера блокирует начало нового вылета. В приложении предусматривается отдельная явная настройка локального допуска заранее разрешённых миссий: ограниченное число миссий либо действие до ручного удаления задания из очереди. Без заданной действующей локальной квоты вылет не разрешается. Квота, её остаток, назначивший пользователь и срок/основание должны быть доступны для контроля и аудита. Точные роли, область действия квоты и правила синхронизации после восстановления сервера требуют отдельной детализации.

### 25.10. Критерий завершения передачи для допуска к вылету

В приложении оператор выбирает один из двух критериев для допуска к следующей миссии:
- LOCAL_COMPLETE — файлы приняты станцией и прошли предусмотренную локальную проверку целостности;
- SERVER_CONFIRMED — сервер подтвердил получение материалов.

Выбранный критерий отображается явно и применяется при проверке допуска к следующей миссии. Значение по умолчанию, область действия (станция/миссия) и полномочия на изменение пока не фиксируются.

### 25.11. Лимит циклов без физического осмотра и резерв хранилища

Приложение должно отображать настроенный предел автоматических циклов без физического осмотра и текущее значение счётчика. После достижения предела автоматический запуск следующей миссии блокируется с причиной до предусмотренного подтверждения осмотра.

Перед допуском следующей миссии станция проверяет наличие достаточного резерва локального хранилища для ожидаемых материалов. При недостатке места приложение показывает причину блокировки и доступный объём; числовой резерв рассчитывается после выбора БАС, состава материалов и накопителя.

### 25.12. Подтверждение опасных/аварийных действий оператором

В исключительном случае при подозрении на неисправность крышки приложение может запросить дополнительное подтверждение оператора перед её открытием. Это подтверждение не заменяет актуальный результат SafetyManager, достоверные датчики и локальные межблокировки и не может отменить DENY/UNKNOWN.

Уполномоченному удалённому оператору может быть доступна команда подтверждения выхода из аварийного состояния. Перед подтверждением приложение показывает предупреждение, установленную причину и результаты повторных проверок и требует явного действия оператора. Команда не обходит действующую аппаратную/локальную блокировку; инициатор, время, причина, предупреждение и результат записываются в аудит.

### 25.13. Геопозиция станции, БАС и маршруты

Клиентскому приложению необходимы геоданные для отображения на карте станции и всех БАС, зарегистрированных/привязанных к ней. Точная транспортная схема и сериализация пока не утверждены. Контракт должен логически различать следующие сущности.

**Позиция станции:**
- station_id;
- координаты и система координат;
- источник/способ определения координат;
- время фиксации и время получения;
- качество/точность и статус достоверности;
- время последнего подтверждения координат, если станция стационарна.

**Позиция БАС:**
- station_id и drone_id;
- координаты и система координат;
- время измерения на борту и время получения станцией/сервером;
- качество/точность и статус достоверности;
- дополнительные параметры (например, высота, курс и скорость) — только если они доступны из доверенного источника и согласованы по единицам и системе отсчёта.

**Фактический трек:**
- station_id, drone_id и mission_id;
- упорядоченные точки фактически зарегистрированного движения;
- временная метка каждой точки, система координат и качество;
- признаки пропусков/разрывов данных, чтобы линия на карте не создавала ложное впечатление непрерывного наблюдения.

**Предстоящий маршрут:**
- station_id, drone_id и mission_id;
- версия/идентификатор плана и время его формирования;
- упорядоченные плановые точки/сегменты;
- система координат и статус плана (например, подготовлен, утверждён, передан, отменён — окончательный перечень определить отдельно);
- временные/высотные параметры, если они предусмотрены форматом миссии.

Фактический трек и плановый маршрут передаются и отображаются как разные сущности/слои. Плановые точки никогда не считаются фактической телеметрией. Отсутствующее значение координат не заменяется нулём или последней точкой без признака STALE. При потере связи клиент сохраняет последнюю известную позицию только как историческую/устаревшую и показывает время её получения.

Формат геоданных, геодезическая система/датум, единицы высоты, частота обновления, допустимая точность, правила прореживания и хранения треков, источник времени, картографический сервис и офлайн-кэширование требуют отдельного решения. До согласования этих параметров не закреплять конкретный формат API или библиотеку карты.

Доступ к координатам, трекам и планам подчиняется тем же проверкам station_id, OwnerSpace и прав пользователя, что и доступ к телеметрии и миссиям. Карта не является каналом команд управления полётом и не заменяет SafetyManager или автопилот.


### 25.14. Подготовка и импорт планового маршрута

Контракт должен поддерживать получение планового маршрута как минимум из трёх логических источников: ручное создание/редактирование точек, ввод или вставка координат и импорт внешнего файла. Дополнительные источники могут добавляться отдельными адаптерами.

Внутри системы импортируемые источники должны преобразовываться в единую каноническую модель планового маршрута. Исходный файл/представление и сведения о формате желательно сохранять для диагностики и повторного разбора; нормализованный план не должен терять информацию о системе координат, единицах и параметрах точек.

**Логическая модель кандидата маршрута должна предусматривать:**
- route_id или временный идентификатор черновика;
- station_id, drone_id и mission_id, если назначение уже выполнено;
- source_format и source_name/идентификатор источника;
- schema_version или версию адаптера импорта;
- систему координат/датум и единицы высоты;
- упорядоченный список точек и сегментов;
- для каждой точки — координаты, порядковый номер и дополнительные параметры (например, высота, скорость или тип действия) только если они поддерживаются исходным форматом и выбранным типом миссии;
- время создания/импорта, автора и версию плана;
- статус обработки и результат проверки.

**Результат импорта** должен различать как минимум успешный разбор, предупреждения, некорректные данные, неподдерживаемый формат и внутреннюю ошибку. Диагностика должна указывать проблемную точку/поле и причину. Неоднозначные координатные системы, единицы или значения нельзя угадывать и молча преобразовывать.

До принятия маршрута должны быть проверены структура, диапазоны координат, порядок точек, обязательные параметры выбранного типа миссии и корректность назначения station_id/drone_id/mission_id. Правила допустимых высот, скоростей, геозон, ограничений автопилота и иные полётные ограничения определяются отдельными утверждёнными политиками и проверяются соответствующими компонентами; один лишь успешный импорт не означает, что маршрут безопасен.

Форматы GeoJSON, KML, GPX, CSV и форматы планировщиков конкретных автопилотов являются только кандидатами для оценки. Ни один формат не считается обязательным, пока не выбраны поддерживаемые БАС/автопилоты и не проверена совместимость. Транспорт передачи принятого плана на станцию/БАС также остаётся отдельным решением.

Импорт, нормализация, предварительный просмотр и сохранение черновика не равны утверждению миссии, передаче маршрута автопилоту или разрешению на выполнение полёта.

## 26. Первичная регистрация станции

Предварительная последовательность регистрации и выдачи Station ID:
1. В безопасном режиме первичной настройки станция создаёт индивидуальную пару ключей; закрытый ключ остаётся на станции и не передаётся через API.
2. Уполномоченный установщик физически подтверждает режим регистрации, а администратор проходит аутентификацию в доверенном сервисе.
3. Станция передаёт запрос регистрации/CSR, открытый ключ, одноразовый challenge и доступные аппаратные сведения.
4. Доверенный сервис регистрации проверяет подлинность устройства и полномочия регистратора, затем проверяет уникальность аппаратной и криптографической идентичности.
5. Реестр/EnrollmentAuthority назначает уникальный Station ID и выдаёт станции подтверждение регистрации и сертификат.
6. Станция проверяет ответ, сохраняет Station ID и сертификат, а реестр фиксирует связь ID с аппаратной и криптографической идентичностью.

Это укрупнённый контрактный сценарий, а не утверждённый протокол provisioning. Офлайн-регистрация, формат ID, PKI, аппаратное хранилище ключей и порядок восстановления описаны в [спецификации идентичности станции и криптографической защиты](24_STATION_IDENTITY_AND_CRYPTOGRAPHIC_SECURITY.md) и пока требуют согласования. Ручной ввод номера или сканирование QR-кода не являются достаточной аутентификацией.


## 27. Контракт конфигурации станции

Архитектурное разделение согласовано решением DEC-054: ConfigurationManager загружает и проверяет конфигурацию; DiagnosticsManager использует проверенный снимок; StationStateManager использует достоверное подтверждение проверки при запуске; SafetyManager отдельно принимает решение по каждой опасной операции.

### 27.1. Версия схемы и ревизия

- schema_version определяет структуру и правила интерпретации сохранённых данных.
- configuration_revision идентифицирует конкретную редакцию параметров.
- Изменение параметров не обязательно меняет версию схемы.
- Ревизия сама по себе не доказывает корректность конфигурации.

### 27.2. Статусы загрузки и проверки

| Статус | Значение |
|---|---|
| VALID | Конфигурация получена, декодирована и прошла обязательные проверки |
| NOT_FOUND | Сохранённая конфигурация отсутствует |
| UNAVAILABLE | Хранилище или обязательная зависимость недоступны |
| READ_ERROR | Ошибка чтения записи |
| DECODE_ERROR | Запись невозможно корректно декодировать |
| UNSUPPORTED_VERSION | Версия схемы не поддерживается |
| INVALID | Структура или содержимое не прошло обязательную проверку |
| INTERNAL_ERROR | Внутренняя ошибка обработки |

Результат может содержать известные ревизию и версию схемы, проблемы, предупреждения и проверенный снимок. Снимок предоставляется только при VALID. Диагностические сообщения не должны раскрывать секретные значения.

### 27.3. Проверенный снимок

ValidatedConfigurationSnapshot логически неизменяем для получателей и содержит типизированные конфигурационные данные, schema_version и configuration_revision. Получатели читают предназначенные им параметры, но не изменяют активный снимок напрямую. Точная внутренняя структура ещё не утверждена.

CFG-F06 — единственная предусмотренная точка создания снимка. Она принимает тот же неизменённый ConfigurationCandidate, который был передан в CFG-F05, и результат CFG-F05. Результат проверки содержит validated_schema_version и validated_configuration_revision; обе строки должны точно совпасть с кандидатом, а revision должна быть непустой. При несовпадении, повреждённом списке issues или противоречии VALID/ERROR возвращается INTERNAL_ERROR без snapshot.

### 27.4. Порты хранения и декодирования

SettingsRepository предоставляет сохранённую запись и различает отсутствие, недоступность и ошибку чтения. ConfigurationDecoderPort преобразует запись в типизированного кандидата и отличает ошибку декодирования от неподдерживаемой версии. Конкретный формат, файловая система, база данных, носитель и механизм защиты целостности не выбраны.

### 27.5. Правила использования

StationStateManager и DiagnosticsManager не разбирают сохранённые данные повторно в обход ConfigurationManager. Проверка VALID относится к той же ревизии, что и предоставленный снимок; старый результат не подтверждает новую ревизию. Конфигурация не является разрешением SafetyManager на опасное действие.

### 27.6. Типизированное представление и срок жизни

После декодирования конфигурация предоставляется как нейтральное дерево `ConfigurationDocumentView`. Значения имеют типы `Unknown`, `Null`, `Boolean`, `SignedInteger`, `UnsignedInteger`, `Number`, `String`, `Object`, `Array` или `Opaque`. Объекты хранят именованные поля, массивы — упорядоченные элементы. `Opaque` сохраняет непроинтерпретированный байтовый фрагмент; неизвестные поля не должны отбрасываться без явной политики.

`ConfigurationRecordView` представляет сохранённую запись как последовательность байтов; это не выбор формата. `SettingsRepository` различает FOUND, NOT_FOUND, UNAVAILABLE и READ_ERROR. `ConfigurationDecoderPort` различает DECODED, INVALID_RECORD, UNSUPPORTED_VERSION и ERROR.

Представления конфигурации, issues и строковые поля не владеют памятью. Порт/адаптер обязан обеспечить действительность backing storage на всё время, пока кандидаты, результаты или снимки используются. Конкретный механизм управления памятью должен быть явно описан в адаптере и не определяется этим контрактом.

Этот раздел фиксирует логический контракт и не выбирает формат хранения, физический носитель или криптографический алгоритм.

### 27.7. Проверка версии схемы (CFG-F01)

`ConfigurationSchemaVersionSetView` передаёт CFG-F01 явный массив строк
`versions` и его `size`. Тип не владеет памятью; массив и строки должны быть
действительны на протяжении вызова. Набор обязан быть непустым, не содержать
пустых/некорректных значений и дубликатов. Отсутствующая политика не означает,
что поддерживаются все версии или что список пустых версий допустим.

Версия схемы является непрозрачным идентификатором. Проверка не навязывает
SemVer, числовую последовательность или иной конкретный формат. Идентификатор
должен быть непустым и не содержать ASCII whitespace, управляющие символы или
NUL. Сопоставление с элементами политики точное и чувствительное к регистру.

`ConfigurationValidationResult` содержит
`ConfigurationValidationStatus`, не владеющий памятью список issues и, для
результата CFG-F05, точные `validated_schema_version` и
`validated_configuration_revision` проверенного кандидата. F06 сравнивает эти
идентификаторы с переданным кандидатом. CFG-F01 возвращает `Valid` при точном
совпадении, `Invalid` при отсутствии или некорректности версии кандидата,
`UnsupportedVersion` при корректной, но неизвестной версии и `InternalError`
при некорректной политике. Issues имеют статический срок жизни и не содержат
значений конфигурации.

### 27.8. Проверка обязательных полей (CFG-F02)

`ConfigurationRequiredFieldPathView` описывает один путь массивом
`segments` — точных имён полей объекта от корня документа. Путь задаётся
сегментами, а не строкой с разделителем, поэтому символы внутри имени поля
не требуют экранирования. `diagnostic_path` — готовая строка того же пути,
которая будет записана в `ConfigurationIssue.field_path`.
`ConfigurationRequiredFieldSetView` содержит явный непустой набор таких
путей без дубликатов. Типы являются view и не владеют памятью.

CFG-F02 проверяет только существование конечного поля. Присутствующее значение
`Null` или `Unknown` считается существующим; его тип и допустимость относятся
к CFG-F03. Отсутствующее поле даёт `REQUIRED_FIELD_MISSING`. Если промежуточный
сегмент не является объектом, возвращается `REQUIRED_FIELD_PATH_UNRESOLVABLE`.
Повторяющиеся одноимённые ключи на пути дают
`REQUIRED_FIELD_PATH_AMBIGUOUS`; функция не выбирает один из них произвольно.
Некорректный object view даёт `INTERNAL_ERROR`.

Для списка проблем вызывающий код передаёт отдельный `issue_buffer` и его
ёмкость. Буфер должен вместить все ошибки (в худшем случае — число путей
политики), не перекрывать входные данные и оставаться действительным, пока
используется результат. При нехватке ёмкости функция возвращает
`INTERNAL_ERROR` и один статический issue `REQUIRED_FIELD_ISSUE_BUFFER_TOO_SMALL`,
не публикуя усечённый список. Пустая/некорректная политика также возвращает
`INTERNAL_ERROR`. Конкретный production-перечень остаётся открытым в CFG-Q02.


### 27.9. Проверка типов и значений (CFG-F03)

`ConfigurationValueRuleView` задаёт один путь и ожидаемый точный тип. Для числовых типов правило может содержать нижнюю и/или верхнюю границу; тип каждой границы обязан совпадать с типом поля. Для скалярных типов допускается явный список допустимых значений. Неявное приведение типов не выполняется.

`ConfigurationValueRuleSetView` — непустой набор уникальных правил, передаваемый вызывающим кодом. Проверка не содержит production-диапазонов, перечней режимов или значений по умолчанию. Некорректная политика возвращает `INTERNAL_ERROR`; ошибки кандидата возвращают `INVALID` с проблемами, привязанными к диагностическому пути. При недостаточном буфере issues частичный список не публикуется.

Коды проблем: `CONFIGURATION_VALUE_FIELD_MISSING`, `CONFIGURATION_VALUE_PATH_UNRESOLVABLE`, `CONFIGURATION_VALUE_PATH_AMBIGUOUS`, `CONFIGURATION_VALUE_TYPE_MISMATCH`, `CONFIGURATION_VALUE_BELOW_MINIMUM`, `CONFIGURATION_VALUE_ABOVE_MAXIMUM`, `CONFIGURATION_VALUE_NOT_ALLOWED`, `CONFIGURATION_VALUE_NOT_FINITE`. Плавающие числа NaN/Inf не принимаются. Единицы измерения пока не проверяются: текущий `ConfigurationValueView` не содержит их метаданных, а формат конфигурации ещё не выбран.


### 27.10. Проверка взаимной согласованности (CFG-F04)

CFG-F04 принимает явный непустой ConfigurationConsistencyRuleSetView. Каждое правило связывает два сегментированных пути, задаёт один ожидаемый тип для обоих операндов и одну операцию: точное равенство/неравенство либо числовое сравнение (<, <=, >, >=). Оба поля должны существовать и иметь указанный тип. Сравнение signed, unsigned и Number между собой не смешивается.

Для равенства и неравенства поддерживаются скалярные типы Null, Boolean, SignedInteger, UnsignedInteger, Number и String. Порядковые операции поддерживают только числовые типы. Сравнение строк и составных Object/Array/Opaque не выполняется. Number сравнивается точно, без допуска или epsilon; NaN и Inf отклоняются. Если позже потребуются допуски, смешанные числовые типы, условные зависимости или более сложные выражения, для них потребуется отдельное правило/контракт.

Нарушение отношения, отсутствующий операнд, неверный тип, неоднозначный путь и неразрешимый путь возвращают INVALID с issue на diagnostic_path всего отношения. Повреждённый object view, пустая/некорректная политика и недостаточный issue buffer возвращают INTERNAL_ERROR. Список issues публикуется только полностью, после предварительного подсчёта; частичная запись в буфер запрещена.

CFG-F04 не содержит production-зависимостей и не утверждает ни одного конкретного правила станции. Правила передаются вызывающим слоем только после утверждения владельцем проекта.


### 27.11. Объединённая проверка конфигурации (CFG-F05)

CFG-F05 принимает ConfigurationValidationPolicyView с четырьмя явными политиками: поддерживаемые версии CFG-F01, обязательные пути CFG-F02, правила типов/значений CFG-F03 и правила согласованности CFG-F04. Все четыре набора должны быть заданы и непусты. Production-политики не встраиваются в функцию.

Проверки выполняются в порядке F01 → F02 → F03 → F04. Сначала проверяется версия схемы; при INVALID, UNSUPPORTED_VERSION или INTERNAL_ERROR дальнейшие проверки не запускаются, а результат F01 возвращается без изменения общего issue buffer. Это запрещает интерпретировать данные по правилам неизвестной схемы.

После успешной проверки версии CFG-F02…F04 выполняются последовательно. Все найденные issues копируются в единый caller-owned buffer в том же порядке. Если найдена хотя бы одна ошибка данных, итог — INVALID. Если хотя бы одна обязательная проверка сообщила INTERNAL_ERROR или нарушила контракт результата, итог — INTERNAL_ERROR, который имеет приоритет над INVALID; доступные issues при этом сохраняются. Неизвестный статус подвалидатора трактуется как INTERNAL_ERROR. WARNING сохраняются в общем списке и не блокируют VALID; ERROR в результате подвалидатора со статусом VALID считается нарушением контракта. VALID возвращается только когда все четыре этапа завершились VALID и список не содержит ERROR.

Ёмкость общего буфера до начала проверок должна быть не меньше 1 + суммы размеров наборов CFG-F02, CFG-F03 и CFG-F04 — это worst-case число issues с одним дополнительным слотом для возможного WARNING от F01. Сложение проверяется на переполнение. Нулевой/недостаточный буфер возвращает INTERNAL_ERROR до запуска проверок и не изменяет переданную память. Ошибка F01 имеет максимум один статический issue и возвращается напрямую; успешный F01 может добавить не более одного WARNING в общий буфер. Функция не выделяет динамическую память и не создаёт snapshot; его создание остаётся CFG-F06.

### 27.12. Создание проверенного снимка (CFG-F06)

`build_validated_configuration_snapshot(candidate, validation)` создаёт
`ValidatedConfigurationSnapshot` только при `validation.status == Valid`.
CFG-F05 записывает в результат `validated_schema_version` и
`validated_configuration_revision`; CFG-F06 требует точного совпадения обеих
строк с переданным кандидатом и непустых идентификаторов кандидата. Это
запрещает применить `VALID` к другой версии схемы или ревизии.

При `Invalid`, `UnsupportedVersion` или `InternalError` snapshot отсутствует,
а исходный статус и корректный список issues сохраняются. Для `Valid`
допускаются только корректные `Warning`; наличие `Error`, неизвестная
серьёзность, неизвестный статус, повреждённый список issues или пустые
диагностические поля дают `InternalError` без snapshot. Предупреждения
сохраняются в результате CFG-F06.

Снимок не копирует дерево и не владеет его памятью: он сохраняет представление
того же документа. Декодер/адаптер обязан сохранять backing storage и не
изменять опубликованные данные весь срок использования снимка. Функция не
повторяет CFG-F01…F05, не загружает и не записывает конфигурацию, не назначает
значения и не выдаёт разрешения на физические операции.


### 27.13. Полная загрузка конфигурации (CFG-F07)

`load_configuration(repository, decoder, policy, issue_buffer, issue_capacity)`
выполняет один последовательный read-only проход:

1. Один раз вызывает `SettingsRepository::read_current()`.
2. Только для `FOUND` передаёт запись в `ConfigurationDecoderPort::decode()`.
3. Только для `DECODED` передаёт кандидата в CFG-F05 с переданной политикой и
   caller-owned буфером issues.
4. Только при согласованном результате CFG-F05 `VALID` вызывает CFG-F06.
5. Возвращает `ConfigurationLoadResult`; статус `VALID` допускается только
   вместе с присутствующим snapshot той же schema_version/revision.

Отображение результатов портов:

| Источник | Результат | ConfigurationLoadStatus |
|---|---|---|
| SettingsRepository | NOT_FOUND | NOT_FOUND |
| SettingsRepository | UNAVAILABLE | UNAVAILABLE |
| SettingsRepository | READ_ERROR | READ_ERROR |
| ConfigurationDecoderPort | INVALID_RECORD | DECODE_ERROR |
| ConfigurationDecoderPort | UNSUPPORTED_VERSION | UNSUPPORTED_VERSION |
| ConfigurationDecoderPort | ERROR | INTERNAL_ERROR |
| CFG-F05 | INVALID | INVALID |
| CFG-F05 | UNSUPPORTED_VERSION | UNSUPPORTED_VERSION |
| CFG-F05 / CFG-F06 | INTERNAL_ERROR или нарушение контракта | INTERNAL_ERROR |
| CFG-F05 → CFG-F06 | VALID и snapshot присутствует | VALID |

Неизвестные значения enum, несовместимое сочетание статуса и данных порта,
`NOT_FOUND`/`UNAVAILABLE`/`READ_ERROR` с любым непустым представлением записи
(ненулевой указатель или ненулевая длина), `FOUND` с ненулевой длиной и null-указателем, несвязанный с кандидатом
результат F05, `VALID` с `ERROR` или отсутствие snapshot после успешной
проверки закрывают загрузку через `INTERNAL_ERROR`. F06 вызывается только
после `VALID` от F05; поэтому любой ответ F06, отличный от `VALID` или
`INTERNAL_ERROR`, является нарушением внутреннего контракта и не превращается
в ошибку данных `INVALID`/ `UNSUPPORTED_VERSION`. Ни частичный документ, ни
предыдущий snapshot не подставляются. Статусы `NOT_FOUND`, `UNAVAILABLE`,
`READ_ERROR`, `DECODE_ERROR`, `UNSUPPORTED_VERSION` и `INVALID` остаются
различимыми.

Результат F05 использует тот же `issue_buffer`, который передал вызывающий
код. Его память должна оставаться действительной, пока используется
`ConfigurationLoadResult.issues`. Статические диагностические issues F07 имеют
статический срок жизни. Версия и ревизия указываются в результате только если
они достоверно известны из успешно декодированного кандидата.

Байтовое представление записи от SettingsRepository требуется только на время
вызова декодера. Строки, дерево и прочие backing-буферы кандидата должны
оставаться доступными и неизменными на весь срок использования возвращённого
snapshot. Это обязанность ConfigurationDecoderPort/адаптера; F07 не копирует
конфигурацию и не выбирает формат или физическое хранилище.

F07 не повторяет алгоритмы F01-F06, не выполняет повторные чтения, не исправляет
или мигрирует данные, не записывает настройки, не выбирает значения по
умолчанию и не выдаёт разрешения на физические действия. Host-контрактные
тесты с fake-портами не доказывают срок жизни реального накопителя, работу
production-декодера, сохранность данных при отключении питания, целевую сборку
или аппаратную интеграцию.


### 27.14. Получение ревизии выбранной активной конфигурации (CFG-F08)

`get_configuration_revision(const ConfigurationLoadResult& active_configuration)` возвращает `std::optional<std::string_view>`. Функция не выполняет чтение, декодирование, проверку, переключение конфигурации или хранение глобального указателя на активный снимок. Вызывающий компонент сам выбирает и удерживает тот `ConfigurationLoadResult`, который в данный момент считает активным.

Ревизия возвращается только если одновременно выполняются условия:

- статус результата — `VALID`;
- присутствует проверенный snapshot;
- в результате присутствуют schema_version и configuration_revision;
- оба идентификатора непусты и точно совпадают с соответствующими полями snapshot;
- список issues структурно корректен и содержит только корректные `WARNING`.

Отсутствующий snapshot/metadata, несовпадение идентификаторов, некорректный список issues, пустые диагностические поля, `ERROR` или неизвестная серьёзность дают `std::nullopt`. Предупреждения не блокируют получение ревизии. Возвращаемый `string_view` не владеет памятью и действителен только пока действительна память snapshot и исходного декодированного документа.

Функция не может самостоятельно доказать, что переданный результат действительно является самым новым или выбранным активным: это обязанность владельца текущего снимка в вызывающем слое. F08 предоставляет только безопасное извлечение ревизии из согласованного результата. Она не является механизмом управления жизненным циклом активной конфигурации.
