# Интерфейсы и контракты данных

**Статус:** предварительная спецификация.  
**Редакция:** 0.2.

## 1. Назначение

Документ определяет, какую информацию должны обменивать программные модули и внешние системы.

Он не утверждает конкретный транспорт или формат сообщений. JSON, MAVLink, Modbus RTU, UART, Ethernet и другие варианты являются кандидатами до выбора оборудования и согласования.

## 2. Общие правила для любого сообщения

Для событий, которые участвуют в управлении состоянием станции, обязательны:

- event_id — уникальный идентификатор конкретного события;
- event_type — тип события;
- source — логический источник события;
- source_instance/session — идентификатор экземпляра или сессии источника, если источник может перезапускаться;
- occurred_at — время формирования события источником, если оно доступно;
- received_at — время получения события принимающей стороной;
- source_sequence — последовательный номер события от источника, если источник поддерживает такую нумерацию;
- operation_id и correlation_id — для события, относящегося к длительной операции или исходному запросу;
- payload — данные события;
- quality/status — достоверность и качество данных;
- schema_version — версия контракта.

Конкретный транспорт и формат не определены. Если источник не может предоставить какое-либо поле, это должно быть явно отражено в адаптере/контракте; нельзя подставлять выдуманное значение.

Время формирования источником и время получения — разные величины. Время получения назначает принимающая сторона. Для измерений обязательно указывать единицы. Например, скорость ветра — м/с, температура — °C, давление — Па или гПа, угол — градусы с определённой системой отсчёта.

Нельзя передавать значение без единиц, если его интерпретация может быть неоднозначной.

## 3. Общие статусы данных

Предлагаемый набор:

| Статус | Значение |
|---|---|
| VALID | Значение получено и прошло проверку |
| STALE | Значение существует, но устарело |
| INVALID | Значение не прошло проверку |
| UNAVAILABLE | Источник недоступен |
| UNKNOWN | Состояние пока неизвестно |
| ERROR | Ошибка получения или обработки |

Отсутствие данных не должно заменяться нулём. Например, «ветер неизвестен» — не то же самое, что «ветер 0 м/с».

## 4. Контракт метеоданных

Предварительная структура:

```json
{
  "timestamp": "временная метка",
  "source_id": "идентификатор метеостанции",
  "wind_speed_mps": null,
  "wind_direction_deg": null,
  "wind_gust_mps": null,
  "temperature_c": null,
  "relative_humidity_percent": null,
  "precipitation_status": "UNKNOWN",
  "pressure_hpa": null,
  "quality": "UNKNOWN"
}
```

Это иллюстрация структуры, не готовый формат протокола.

Поля должны иметь правила допустимого диапазона, периодичности и устаревания после выбора датчиков.

## 5. Контракт погодных разрешений

Предлагаемая структура:

```json
{
  "timestamp": "временная метка",
  "allow_takeoff": "UNKNOWN",
  "allow_normal_landing": "UNKNOWN",
  "allow_priority_recovery": "UNKNOWN",
  "allow_lid_open": "UNKNOWN",
  "allow_cleaning": "UNKNOWN",
  "allow_charging": "UNKNOWN",
  "reason_codes": []
}
```

Для всех разрешений используются единые машинные значения: `ALLOW`, `DENY`, `UNKNOWN`. Каждое разрешение должно иметь объяснение. Значение не должно быть обычным булевым флагом без возможности различить запрет и отсутствие данных.

Конкретные пороги должны храниться в конфигурации с версией и ссылкой на источник требований.

## 6. Контракт состояния станции

Снимок состояния должен различать глобальную фазу работы станции и статусы отдельных подсистем.

Предварительные поля снимка глобального состояния:

- идентификатор станции;
- версия программного обеспечения;
- текущее глобальное состояние станции;
- state_revision — версия/номер подтверждённого перехода;
- transition_id — идентификатор последнего подтверждённого перехода;
- время последнего подтверждённого перехода;
- активные operation_id, если есть;
- список активных предупреждений;
- время формирования снимка.

Состояния крышки, площадки, наличия БАС, зарядки, очистки, метеоподсистемы, связи с сервером и локального накопителя являются отдельными статусами подсистем. Их можно передавать в составе расширенного диагностического снимка, но нельзя трактовать как одно глобальное состояние станции.

Снимок должен указывать актуальность/качество статусов подсистем. Последнее известное значение с истёкшим сроком актуальности не должно представляться как подтверждённое текущее состояние.

## 7. Контракт обнаруженного БАС

Данные обнаружения и аутентификации нужно разделять.

### Событие обнаружения

- идентификатор радиоустройства;
- тип радиоинтерфейса;
- время;
- измеренная сила сигнала, если доступна;
- предварительный идентификатор;
- статус обнаружения.

### Результат аутентификации

- идентификатор БАС;
- идентификатор станции;
- результат проверки;
- метод проверки;
- время;
- причина отказа.

Успешное обнаружение не означает успешную аутентификацию.

## 8. Контракт посадочного измерения

Предварительные поля:

- время измерения;
- идентификатор камеры;
- идентификатор маркера;
- относительное положение;
- относительная ориентация;
- система координат;
- единицы;
- оценка качества;
- признак достоверности;
- причина недостоверности.

До выбора камеры, автопилота и алгоритма нельзя утверждать конкретный формат координат или частоту передачи.

## 9. Контракт состояния крышки

Предлагаемые состояния:

- CLOSED — закрыта;
- OPEN — открыта;
- MOVING_OPEN — открывается;
- MOVING_CLOSE — закрывается;
- UNKNOWN — положение неизвестно;
- FAULT — неисправность.

События:

- команда открытия;
- команда закрытия;
- достижение конечного положения;
- тайм-аут;
- перегрузка;
- препятствие;
- отказ датчика.

Команда должна иметь идентификатор операции. Подтверждение завершения не должно отправляться до проверки обратной связи.

## 10. Контракт зарядки

Предварительные поля:

- идентификатор БАС;
- состояние зарядки;
- входное напряжение;
- входной ток;
- передаваемая мощность;
- температура силового модуля;
- температура катушки;
- температура батареи, если доступна;
- состояние BMS;
- целевой уровень заряда;
- причина остановки;
- качество данных;
- временная метка.

Все электрические параметры должны иметь единицы и определённые точки измерения.

## 11. Контракт передачи файлов

### Манифест

Для каждого файла:

- уникальный идентификатор;
- имя или безопасный относительный путь;
- размер в байтах;
- тип содержимого;
- время создания, если известно;
- контрольная сумма, если доступна;
- источник;
- статус передачи.

Имена файлов и пути считаются недоверенными входными данными. Нельзя позволять им создавать произвольные пути за пределами выделенной папки хранения.

### Статусы передачи

- DISCOVERED — найден;
- QUEUED — поставлен в очередь;
- TRANSFERRING — передаётся;
- PAUSED — приостановлен;
- VERIFYING — проверяется;
- LOCAL_COMPLETE — локальная копия проверена;
- UPLOADING — отправляется серверу;
- SERVER_CONFIRMED — сервер подтвердил приём;
- FAILED — ошибка;
- NEEDS_RETRY — требуется повтор.

## 12. Контракт безопасности и разрешения на операцию

Каждый функциональный исполнительный модуль должен запрашивать разрешение перед опасной операцией. Запрос содержит operation_id, тип действия, состояние оборудования и актуальные данные, необходимые для проверки.

Ответ должен связывать разрешение с конкретной операцией и содержать:

- operation_id;
- permission: ALLOW, DENY или UNKNOWN;
- reason_codes;
- valid_until или иной согласованный срок действия;
- safety_revision — версию правил, по которым принято решение.

При отсутствии ответа, истечении срока действия, отзыве разрешения или потере связи разрешение не считается действующим. Исполнительный модуль не должен выполнять опасную команду на основании старого разрешения. StationStateManager не вправе переопределять результат SafetyManager.

## 13. Контракт готовности площадки для БАС

Станция предоставляет БАС однозначный статус:

- READY — площадка готова для согласованного сценария;
- NOT_READY — площадка не готова;
- UNKNOWN — достоверная оценка невозможна.

В ответе указываются время, идентификатор станции, причина неготовности и срок актуальности статуса. Дальнейшее поведение аппарата при NOT_READY определяется его бортовым алгоритмом и заранее согласованной эксплуатационной процедурой.

## 14. Контракт бортовой системы и питания при обслуживании

После остановки двигателей часть бортовой электроники должна оставаться доступной в объёме, необходимом для передачи файлов, обмена с BMS и контроля зарядки. Конкретная схема питания и режимы низкого энергопотребления зависят от выбранного БАС.

Необходимо определить:
- какие бортовые узлы остаются включёнными;
- от какого источника они питаются;
- как станция получает статус питания;
- как исключается чрезмерный разряд аккумулятора во время длительной передачи;
- как зарядное устройство взаимодействует с BMS;
- что происходит при потере связи с BMS.

## 15. Контракт миссии

Минимальные поля задания:
- уникальный идентификатор миссии;
- идентификатор целевого БАС;
- версия формата;
- объект инспекции;
- план/маршрут или ссылка на него;
- время создания и срок действия;
- источник задания;
- статус предварительного разрешения;
- ограничения выполнения.

Конкретный формат маршрута и способ передачи автопилоту пока не определены. Наличие задания в очереди не означает автоматического разрешения на полёт: оно дополнительно проходит локальные проверки станции и БАС.

## 16. Интерфейс основного контроллера и вычислительного модуля

Необходимо определить двусторонний обмен:
- состояние вычислительного модуля;
- контрольный сигнал работоспособности (heartbeat);
- версия протокола;
- команды функциональных операций;
- результаты обработки изображения;
- запросы разрешения;
- ответы SafetyManager;
- ошибки и временные метки.

Потеря heartbeat вычислительного модуля не должна отключать или обходить локальную аппаратную защиту основного контроллера.

## 17. Контракт телеметрии и удалённых команд

Телеметрия должна иметь отдельную версионируемую схему и временную метку.

Удалённая команда должна содержать идентификатор, отправителя, срок действия, тип команды, параметры, подтверждение полномочий и защиту от повтора. Разрешённый каталог команд и роли пока не определены.

## 18. Контракт ошибки

Структурированное сообщение об ошибке должно включать:

- event_id и event_type;
- источник/модуль;
- error_code;
- severity: INFO, WARNING, ERROR или CRITICAL;
- понятное описание;
- operation_id и correlation_id, если ошибка относится к операции/запросу;
- время формирования и получения;
- качество/достоверность данных, если применимо;
- recovery_hint — рекомендацию или ссылку на утверждённую реакцию, но не произвольную команду.

Само значение severity не задаёт автоматически глобальное состояние станции. Реакция выбирается по утверждённой политике конкретного отказа.

## 19. Идентификаторы операций и lifecycle

Каждая длительная операция должна иметь уникальный operation_id, который сохраняется в запросе, подтверждениях, промежуточных событиях, результате и ошибках. Для связи с исходным событием/командой использовать correlation_id.

Статусы операции:

| Статус | Значение |
|---|---|
| REQUESTED | SSM зарегистрировал запрос и operation_id; передача исполнительному модулю ещё не подтверждена |
| ACCEPTED | Исполнитель принял запрос к обработке; физическое действие ещё не подтверждено |
| STARTED | Исполнитель подтвердил начало действия |
| COMPLETED | Действие завершено и требуемый результат подтверждён |
| FAILED | Исполнитель сообщил об отказе |
| CANCEL_REQUESTED | Запрошена отмена |
| CANCELLED | Исполнитель подтвердил отмену |
| OUTCOME_UNKNOWN | Нельзя достоверно определить, началось/завершилось ли физическое действие |

Недопустимые перескоки между статусами должны отклоняться или классифицироваться как конфликт по правилам конкретной операции. Не все операции обязаны использовать каждый статус, но пропуск статуса допустим только если контракт исполнителя явно определяет эквивалентное подтверждение.

Операция считается физически завершённой только после требуемого подтверждения результата; одного сообщения ACCEPTED недостаточно.

## 20. Идемпотентность, повторы и порядок событий

Повторная доставка одной и той же команды или события не должна повторно запускать физическое действие или повторно фиксировать переход.

Нужно различать:

- event_id — идентификатор сообщения/события для обнаружения повторной доставки;
- command_id — идентификатор команды, если он отделён от события;
- operation_id — идентификатор длительной операции;
- correlation_id — связь запроса и последующих событий.

Повтор с тем же идентификатором и тем же содержимым обрабатывается идемпотентно: повторный побочный эффект не выполняется, ранее известный результат может быть возвращён повторно. Тот же идентификатор с другим содержимым считается конфликтом и журналируется.

Если источник передаёт source_sequence, события от одного экземпляра источника проверяются на нарушение последовательности. При отсутствии последовательного номера нельзя определять устаревание только по календарному времени: часы источников могут быть рассинхронизированы. Для операций дополнительно проверяются operation_id и допустимость перехода lifecycle.

## 21. Тайм-ауты и неопределённый результат

Для каждого обмена/операции необходимо определить:

- время ожидания ответа;
- максимальное время операции;
- число повторов и условия их допустимости;
- поведение при повторном запросе;
- поведение при позднем ответе;
- поведение при потере связи;
- способ проверки фактического результата после тайм-аута.

Точные значения определяются после выбора оборудования и протоколов.

Тайм-аут после возможной передачи физической команды не доказывает, что команда не исполнилась. До получения достоверного состояния операция получает OUTCOME_UNKNOWN. Автоматический повтор движения/зарядки/очистки запрещён, пока конкретная политика операции не разрешит повтор после проверки фактического состояния и условий безопасности.

## 22. Временные метки и синхронизация

Необходимо определить источник календарного времени станции и БАС, способ синхронизации и допустимую погрешность.

Время события, время получения и время обработки — разные понятия. Для анализа полёта и передачи данных желательно хранить исходные временные метки и не подменять их временем получения на сервере.

Для измерения интервалов, контроля длительности операций и тайм-аутов должна использоваться абстракция монотонного времени, не зависящая от коррекции календарных часов. Календарное время применяется для журналов, аудита и сопоставления с внешними системами. Конкретная реализация Clock/Timer определяется после выбора платформы.

## 23. Версионирование интерфейсов

Каждый внешний контракт должен иметь версию.

Изменение обязательного поля, единицы измерения, семантики статуса или системы координат считается изменением интерфейса и требует проверки всех зависимых модулей.

## 24. Что пока не утверждено

- JSON или другой формат сообщений;
- MQTT, HTTP, WebSocket или другой сетевой транспорт;
- MAVLink или другой интерфейс автопилота;
- Modbus RTU или другой интерфейс метеостанции;
- формат временных меток;
- точные единицы и диапазоны отдельных полей;
- периодичность обновления;
- способ идентификации устройства;
- структура файлового манифеста.

Не реализовывать окончательный протокол на основании только примеров из этого документа.
