# Интерфейсы и контракты данных

**Статус:** предварительная спецификация.  
**Редакция:** 1.2  
**Дата актуализации:** 2026-11-05.

## 1. Назначение

Документ определяет, какую информацию должны обменивать программные модули и внешние системы.

Он не утверждает конкретный транспорт или формат сообщений. JSON, MAVLink, Modbus RTU, UART, Ethernet и другие варианты являются кандидатами до выбора оборудования и согласования.

## 2. Общие правила для любого сообщения

Для событий, которые участвуют в управлении состоянием станции, обязательны:

- event_id — уникальный идентификатор конкретного события;
- event_type — тип события;
- source — логический источник события;
- source_instance/session — идентификатор экземпляра или сессии источника, если источник может перезапускаться;
- occurred_at — время формирования события источником, если оно доступно;
- received_at — время получения события принимающей стороной;
- source_sequence — последовательный номер события от источника, если источник поддерживает такую нумерацию;
- operation_id и correlation_id — для события, относящегося к длительной операции или исходному запросу;
- payload — данные события;
- quality/status — достоверность и качество данных;
- schema_version — версия контракта.

Конкретный транспорт и формат не определены. Если источник не может предоставить какое-либо поле, это должно быть явно отражено в адаптере/контракте; нельзя подставлять выдуманное значение.

Время формирования источником и время получения — разные величины. Время получения назначает принимающая сторона. Для измерений обязательно указывать единицы. Например, скорость ветра — м/с, температура — °C, давление — Па или гПа, угол — градусы с определённой системой отсчёта.

Нельзя передавать значение без единиц, если его интерпретация может быть неоднозначной.


### 2.1. Категории и каталог типов событий

Для классификации событий StationStateManager использует одну из шести категорий:

| Категория | Назначение |
|---|---|
| `SUBSYSTEM` | Изменение состояния или результат диагностики отдельной подсистемы |
| `OPERATION` | Изменение статуса выполняемой операции |
| `SAFETY` | Решение SafetyManager о разрешении или запрете операции |
| `COMMAND` | Запрос на выполнение команды |
| `TIMER` | Срабатывание таймера или истечение времени ожидания |
| `RECOVERY` | Запрос восстановления или результат сверки после перезапуска |

Согласованный каталог типов событий для текущего ядра:

| `event_type` | Категория | Назначение |
|---|---|---|
| `STARTUP_REQUESTED` | `COMMAND` | Запрошен запуск станции |
| `INITIALIZATION_COMPLETED` | `SUBSYSTEM` | Завершена инициализация программных компонентов и проверка конфигурации |
| `SELF_TEST_COMPLETED` | `SUBSYSTEM` | Завершена стартовая самодиагностика |
| `SUBSYSTEM_STATUS_UPDATED` | `SUBSYSTEM` | Изменился статус подсистемы, включая сообщение о неисправности |
| `OPERATION_STATUS_UPDATED` | `OPERATION` | Изменился статус конкретной операции |
| `SAFETY_PERMISSION_UPDATED` | `SAFETY` | Изменилось разрешение SafetyManager на конкретную операцию |
| `COMMAND_REQUESTED` | `COMMAND` | Получена команда от оператора или внутреннего координатора |
| `OPERATION_TIMEOUT` | `TIMER` | Истекло время ожидания операции |
| `RECOVERY_REQUESTED` | `RECOVERY` | Запрошено восстановление станции |
| `RECOVERY_RECONCILIATION_COMPLETED` | `RECOVERY` | Завершена сверка сохранённого состояния с актуальными отчётами подсистем |

Дополнительные правила контракта:

- Категория определяется только по точному совпадению `event_type` с зарегистрированным значением. Поиск подстрок, приблизительное совпадение и автоматическое приведение регистра запрещены.
- Неизвестный или пустой `event_type` получает результат классификации `UNKNOWN`. Это результат классификации, а не седьмая категория.
- Неисправность подсистемы передаётся через `SUBSYSTEM_STATUS_UPDATED`: конкретная подсистема и её статус указываются в `payload`; `reason_code` и `reason_text` указываются только при установленной причине. Отдельный тип события для каждой неисправности не создаётся.
- Для `OPERATION_STATUS_UPDATED` используется жизненный цикл и точные значения статусов из §19. Не следует создавать отдельный `event_type` для каждого статуса операции.
- Для `SAFETY_PERMISSION_UPDATED` используются `operation_id`, `permission` со значением `ALLOW`, `DENY` или `UNKNOWN`, а также предусмотренные §12 причина, срок действия и `safety_revision`.
- Для `COMMAND_REQUESTED` в `payload` указываются идентификатор и тип команды, отправитель и необходимые параметры. Например, `STOP_AUTOMATION` является значением типа команды, а не отдельным `event_type`.
- Для `OPERATION_TIMEOUT` указываются идентификатор операции и тип тайм-аута. Сам факт тайм-аута не доказывает, что физическое действие не состоялось.
- Классификация не подтверждает достоверность события, не разрешает переход глобального состояния и не даёт права на физическое действие. Статус `FAIL`, `UNKNOWN` или `DENY` сам по себе не переводит станцию в глобальное аварийное состояние.
- Изменение или расширение каталога требует согласованного обновления этого подраздела, `classify_event()` и её тестов.

## 3. Общие статусы данных

Предлагаемый набор:

| Статус | Значение |
|---|---|
| VALID | Значение получено и прошло проверку |
| STALE | Значение существует, но устарело |
| INVALID | Значение не прошло проверку |
| UNAVAILABLE | Источник недоступен |
| UNKNOWN | Состояние пока неизвестно |
| ERROR | Ошибка получения или обработки |

Отсутствие данных не должно заменяться нулём. Например, «ветер неизвестен» — не то же самое, что «ветер 0 м/с».

## 4. Контракт метеоданных

Предварительная структура:

```json
{
  "timestamp": "временная метка",
  "source_id": "идентификатор метеостанции",
  "wind_speed_mps": null,
  "wind_direction_deg": null,
  "wind_gust_mps": null,
  "temperature_c": null,
  "relative_humidity_percent": null,
  "precipitation_status": "UNKNOWN",
  "pressure_hpa": null,
  "quality": "UNKNOWN"
}
```

Это иллюстрация структуры, не готовый формат протокола.

Поля должны иметь правила допустимого диапазона, периодичности и устаревания после выбора датчиков.

## 5. Контракт погодных разрешений

Предлагаемая структура:

```json
{
  "timestamp": "временная метка",
  "allow_takeoff": "UNKNOWN",
  "allow_normal_landing": "UNKNOWN",
  "allow_priority_recovery": "UNKNOWN",
  "allow_lid_open": "UNKNOWN",
  "allow_cleaning": "UNKNOWN",
  "allow_charging": "UNKNOWN",
  "reason_codes": []
}
```

Для всех разрешений используются единые машинные значения: `ALLOW`, `DENY`, `UNKNOWN`. Каждое разрешение должно иметь объяснение. Значение не должно быть обычным булевым флагом без возможности различить запрет и отсутствие данных.

Конкретные пороги должны храниться в конфигурации с версией и ссылкой на источник требований.

## 6. Контракт состояния станции

Снимок состояния должен различать глобальную фазу работы станции и статусы отдельных подсистем.

Предварительные поля снимка глобального состояния:

- идентификатор станции;
- версия программного обеспечения;
- текущее глобальное состояние станции;
- state_revision — версия/номер подтверждённого перехода;
- transition_id — идентификатор последнего подтверждённого перехода;
- время последнего подтверждённого перехода;
- активные operation_id, если есть;
- список активных предупреждений;
- время формирования снимка.

Состояния крышки, площадки, наличия БАС, зарядки, очистки, метеоподсистемы, связи с сервером и локального накопителя являются отдельными статусами подсистем. Их можно передавать в составе расширенного диагностического снимка, но нельзя трактовать как одно глобальное состояние станции.

Снимок должен указывать актуальность/качество статусов подсистем. Последнее известное значение с истёкшим сроком актуальности не должно представляться как подтверждённое текущее состояние.


### 6.1. Атомарная фиксация глобального перехода

Для фиксации глобального состояния используется StationStateRepository — логический порт одной атомарной операции, а не указание на отдельную физическую БД.

Входной TransitionPlan содержит ожидаемые состояние и state_revision, целевое состояние и уникальный transition_id. TransitionEvidence содержит нормализованное событие и доверенные подтверждения условий F05. Перед записью функция повторно проверяет общий конверт события, требует quality_status=VALID и повторно применяет F05. Целевое состояние в плане должно в точности совпасть с разрешённым F05 результатом. Вызывающий слой до фиксации обязан выполнить проверки F03/F04, применимые к источнику события.

StationStateRepository обязан атомарно:
- проверить совпадение сохранённых глобального state и revision с ожидаемыми значениями плана;
- проверить уникальность event_id и transition_id;
- для повторного event_id сравнить все поля события, кроме received_at, который назначается принимающей стороной;
- сохранить новый snapshot, историю перехода и исходное событие одной транзакцией.

Новая revision равна expected_revision + 1. Конкурентное изменение возвращается как SNAPSHOT_CHANGED; повтор, конфликт содержимого event_id и конфликт transition_id имеют отдельные результаты. Ошибка/неизвестный статус репозитория не считается успешной записью.

StateChanged публикуется только после подтверждённой фиксации. Оно содержит старое и новое глобальное состояние, новую revision, event_id, transition_id и известные reason_code/reason_text. При отказе хранилища публикации нет. Если же хранилище подтвердило commit, но Publisher вернул REJECTED/UNKNOWN, результат означает «состояние сохранено, публикация не подтверждена»; повторно выполнять commit запрещено.

Текущий интерфейс Publisher не обеспечивает durable outbox и не доказывает доставку всем получателям. До промышленной эксплуатации выбранный адаптер должен обеспечить outbox либо эквивалентную идемпотентную публикацию с восстановлением по transition_id. Хостовые fake-тесты проверяют только логический контракт и не доказывают транзакционность выбранного накопителя или сохранность при отключении питания.

## 7. Контракт обнаруженного БАС

Данные обнаружения и аутентификации нужно разделять.

### Событие обнаружения

- идентификатор радиоустройства;
- тип радиоинтерфейса;
- время;
- измеренная сила сигнала, если доступна;
- предварительный идентификатор;
- статус обнаружения.

### Результат аутентификации

- идентификатор БАС;
- идентификатор станции;
- результат проверки;
- метод проверки;
- время;
- причина отказа.

Успешное обнаружение не означает успешную аутентификацию.

## 8. Контракт посадочного измерения

Предварительные поля:

- время измерения;
- идентификатор камеры;
- идентификатор маркера;
- относительное положение;
- относительная ориентация;
- система координат;
- единицы;
- оценка качества;
- признак достоверности;
- причина недостоверности.

До выбора камеры, автопилота и алгоритма нельзя утверждать конкретный формат координат или частоту передачи.

## 9. Контракт состояния крышки

Предлагаемые состояния:

- CLOSED — закрыта;
- OPEN — открыта;
- MOVING_OPEN — открывается;
- MOVING_CLOSE — закрывается;
- UNKNOWN — положение неизвестно;
- FAULT — неисправность.

События:

- команда открытия;
- команда закрытия;
- достижение конечного положения;
- тайм-аут;
- перегрузка;
- препятствие;
- отказ датчика.

Команда должна иметь идентификатор операции. Подтверждение завершения не должно отправляться до проверки обратной связи.

## 10. Контракт зарядки

Предварительные поля:

- идентификатор БАС;
- состояние зарядки;
- входное напряжение;
- входной ток;
- передаваемая мощность;
- температура силового модуля;
- температура катушки;
- температура батареи, если доступна;
- состояние BMS;
- целевой уровень заряда;
- причина остановки;
- качество данных;
- временная метка.

Все электрические параметры должны иметь единицы и определённые точки измерения.

## 11. Контракт передачи файлов

### Манифест

Для каждого файла:

- уникальный идентификатор;
- имя или безопасный относительный путь;
- размер в байтах;
- тип содержимого;
- время создания, если известно;
- контрольная сумма, если доступна;
- источник;
- статус передачи.

Имена файлов и пути считаются недоверенными входными данными. Нельзя позволять им создавать произвольные пути за пределами выделенной папки хранения.

### Статусы передачи

- DISCOVERED — найден;
- QUEUED — поставлен в очередь;
- TRANSFERRING — передаётся;
- PAUSED — приостановлен;
- VERIFYING — проверяется;
- LOCAL_COMPLETE — локальная копия проверена;
- UPLOADING — отправляется серверу;
- SERVER_CONFIRMED — сервер подтвердил приём;
- FAILED — ошибка;
- NEEDS_RETRY — требуется повтор.

## 12. Контракт безопасности и разрешения на операцию

Каждый функциональный исполнительный модуль должен запрашивать разрешение перед опасной операцией. Запрос содержит operation_id, тип действия, состояние оборудования и актуальные данные, необходимые для проверки.

Ответ должен связывать разрешение с конкретной операцией и содержать:

- operation_id;
- permission: ALLOW, DENY или UNKNOWN;
- reason_codes;
- valid_until или иной согласованный срок действия;
- safety_revision — версию правил, по которым принято решение.

При отсутствии ответа, истечении срока действия, отзыве разрешения или потере связи разрешение не считается действующим. Исполнительный модуль не должен выполнять опасную команду на основании старого разрешения. StationStateManager не вправе переопределять результат SafetyManager.

## 13. Контракт готовности площадки для БАС

Станция предоставляет БАС однозначный статус:

- READY — площадка готова для согласованного сценария;
- NOT_READY — площадка не готова;
- UNKNOWN — достоверная оценка невозможна.

В ответе указываются время, идентификатор станции, причина неготовности и срок актуальности статуса. Дальнейшее поведение аппарата при NOT_READY определяется его бортовым алгоритмом и заранее согласованной эксплуатационной процедурой.

## 14. Контракт бортовой системы и питания при обслуживании

После остановки двигателей часть бортовой электроники должна оставаться доступной в объёме, необходимом для передачи файлов, обмена с BMS и контроля зарядки. Конкретная схема питания и режимы низкого энергопотребления зависят от выбранного БАС.

Необходимо определить:
- какие бортовые узлы остаются включёнными;
- от какого источника они питаются;
- как станция получает статус питания;
- как исключается чрезмерный разряд аккумулятора во время длительной передачи;
- как зарядное устройство взаимодействует с BMS;
- что происходит при потере связи с BMS.

## 15. Контракт миссии

Минимальные поля задания:
- уникальный идентификатор миссии;
- идентификатор целевого БАС;
- версия формата;
- объект инспекции;
- план/маршрут или ссылка на него;
- время создания и срок действия (при наличии — время начала действия);
- источник задания;
- статус предварительного разрешения;
- статус отзыва/отмены, если задание отозвано;
- признак ручного подтверждения: REQUIRED, NOT_REQUIRED или UNKNOWN;
- ограничения выполнения.

Отсутствующий, нечитаемый или противоречивый признак ручного подтверждения трактуется как UNKNOWN и блокирует автоматический вылет. Конкретные типы миссий/режимов, для которых выставляется REQUIRED, определяются отдельно.

Конкретный формат маршрута и способ передачи автопилоту пока не определены. Наличие задания в очереди не означает автоматического разрешения на полёт: оно дополнительно проходит локальные проверки станции и БАС.

## 16. Интерфейс основного контроллера и вычислительного модуля

Необходимо определить двусторонний обмен:
- состояние вычислительного модуля;
- контрольный сигнал работоспособности (heartbeat);
- версия протокола;
- команды функциональных операций;
- результаты обработки изображения;
- запросы разрешения;
- ответы SafetyManager;
- ошибки и временные метки.

Потеря heartbeat вычислительного модуля не должна отключать или обходить локальную аппаратную защиту основного контроллера.

## 17. Контракт телеметрии и удалённых команд

Телеметрия должна иметь отдельную версионируемую схему и временную метку.

Удалённая команда должна содержать идентификатор, отправителя, срок действия, тип команды, параметры, подтверждение полномочий и защиту от повтора. Разрешённый каталог команд и роли пока не определены.

## 18. Контракт ошибки

Структурированное сообщение об ошибке должно включать:

- event_id и event_type;
- источник/модуль;
- error_code;
- severity: INFO, WARNING, ERROR или CRITICAL;
- понятное описание;
- operation_id и correlation_id, если ошибка относится к операции/запросу;
- время формирования и получения;
- качество/достоверность данных, если применимо;
- recovery_hint — рекомендацию или ссылку на утверждённую реакцию, но не произвольную команду;
- reason_text — короткое понятное описание установленной причины, если оно доступно.

Если причина не установлена, поле reason_text не заполняется предположением; интерфейс явно показывает, что причина неизвестна.

Само значение severity не задаёт автоматически глобальное состояние станции. Реакция выбирается по утверждённой политике конкретного отказа.

## 19. Идентификаторы операций и lifecycle

Каждая длительная операция должна иметь уникальный operation_id, который сохраняется в запросе, подтверждениях, промежуточных событиях, результате и ошибках. Для связи с исходным событием/командой использовать correlation_id.

В реализации SSM идентификатор запрашивается у отдельного логического порта OperationIdProvider. Функция формирования ActionRequest не задаёт формат или алгоритм ID и не проверяет глобальную уникальность самостоятельно: поставщик обязан не выдавать повторно идентификатор, который уже использовался или сохранён в истории операций станции. Это требование должно сохраняться и после перезапуска. Конкретный механизм (например, устойчивый счётчик, случайный идентификатор или иной вариант) не выбран до определения платформы и хранилища.

Текущие структуры ActionPlan и ActionRequest используют невладеющие string_view. Все исходные строки, включая выданный operation_id, должны оставаться действительными до тех пор, пока сохраняющий/исполняющий порт не скопирует или не сериализует данные во владеющее хранилище. Асинхронная очередь не должна удерживать эти представления без гарантии срока жизни. Это временное решение для переносимого хостового ядра; при выборе платформы, формата хранения и способа обмена необходимо проверить время жизни, стоимость копирования и ограничения памяти.

Статусы операции:

| Статус | Значение |
|---|---|
| REQUESTED | SSM зарегистрировал запрос и operation_id; передача исполнительному модулю ещё не подтверждена |
| ACCEPTED | Исполнитель принял запрос к обработке; физическое действие ещё не подтверждено |
| STARTED | Исполнитель подтвердил начало действия |
| COMPLETED | Действие завершено и требуемый результат подтверждён |
| FAILED | Исполнитель сообщил об отказе |
| CANCEL_REQUESTED | Запрошена отмена |
| CANCELLED | Исполнитель подтвердил отмену |
| OUTCOME_UNKNOWN | Нельзя достоверно определить, началось/завершилось ли физическое действие |

### 19.1. Рабочая матрица переходов lifecycle операции

Матрица ниже определяет допустимые переходы **между статусами одной операции**. Она не является матрицей глобальных состояний станции. Рабочее правило согласовано владельцем проекта 2026-11-05 для реализации SSM-F09.

| Текущий статус | Допустимый следующий статус |
|---|---|
| REQUESTED | ACCEPTED, FAILED, OUTCOME_UNKNOWN |
| ACCEPTED | STARTED, FAILED, CANCEL_REQUESTED, OUTCOME_UNKNOWN |
| STARTED | COMPLETED, FAILED, CANCEL_REQUESTED, OUTCOME_UNKNOWN |
| CANCEL_REQUESTED | CANCELLED, FAILED, OUTCOME_UNKNOWN |
| COMPLETED | Нет: терминальный статус |
| FAILED | Нет: терминальный статус |
| CANCELLED | Нет: терминальный статус |
| OUTCOME_UNKNOWN | Нет обычного перехода; только отдельная процедура сверки |

Правила применения матрицы:

1. Обычное событие `OPERATION_STATUS_UPDATED` может изменить только операцию, найденную по `operation_id`. `correlation_id` события должен совпадать с сохранённой связью этой операции. Неизвестный `operation_id` или несовпадение `correlation_id` не создаёт новую операцию и не обновляет существующую.
2. Перед обновлением используются проверки повторности события (SSM-F03) и порядка/актуальности (SSM-F04). Повторное событие не должно повторять побочные эффекты; конфликт, устаревшее или неупорядоченное событие не продвигает lifecycle.
3. Допускается только переход, прямо указанный в таблице. Пропуск статуса, обратный переход или переход из терминального статуса не разрешается по догадке. Для специализированной операции потребуется отдельное документированное и согласованное изменение матрицы.
4. Одновременные обновления одной операции не должны молча перезаписывать друг друга. Изменение сохраняется условно относительно актуальной версии/ревизии записи операции либо эквивалентным атомарным способом. Конкретный интерфейс репозитория для чтения и условного обновления будет определён перед реализацией F09.
5. `OUTCOME_UNKNOWN` блокирует обычные обновления lifecycle. Даже позднее сообщение `ACCEPTED`, `STARTED` или `COMPLETED` не снимает неопределённость автоматически. Разрешение возможно только через отдельную процедуру сверки с актуальными данными исполнителя/оборудования.
6. Изменение lifecycle само по себе не меняет глобальное состояние станции и не разрешает физическое действие. Для опасного действия исполнитель по-прежнему обязан проверить актуальное разрешение SafetyManager непосредственно перед выполнением.

Матрица намеренно консервативна. В частности, после `CANCEL_REQUESTED` обычным обновлением допускаются только `CANCELLED`, `FAILED` и `OUTCOME_UNKNOWN`; неожиданное сообщение о другом исходе требует сверки, а не автоматического выбора статуса.

### 19.2. Контракт атомарного обновления операции (SSM-F09)

Адаптер события преобразует распознанный статус в типизированное поле `OperationUpdate.next_status`; F09 не разбирает транспортный payload и не выбирает формат JSON. При этом исходный `Event` сохраняется как доказательство источника обновления.

Для обычного обновления F09 требует:
- корректный конверт события с `event_type = OPERATION_STATUS_UPDATED`, `operation_id`, `correlation_id` и непустыми обязательными полями;
- `quality_status = VALID`;
- доказуемый номер `source_sequence` и курсор того же `source`/сессии; отсутствующий номер, повторный номер или несовпадающая сессия не разрешают продвижение lifecycle;
- существующую запись операции, созданную F07; `operation_id` и `correlation_id` события должны совпасть с ней.

Запись операции содержит исходный ActionRequest, текущий lifecycle и revision. F07 создаёт начальную запись со статусом `REQUESTED` и revision=1. Каждое принятое F09 обновление увеличивает revision на единицу.

Логический порт `OperationUpdateRepository` объединяет чтение операции и поиск сохранённого события. Он предоставляет:
- `find_operation(operation_id)` — чтение снимка операции и её текущей revision;
- `find_by_id(event_id)` из `EventRepository` — read-only проверку ранее сохранённого события для F03;
- `commit_operation_update(expected_record, next_status, event, expected_cursor)` — одну атомарную фиксацию.

Атомарная фиксация обязана проверить, что revision/status операции и переданный курсор источника всё ещё актуальны; проверить уникальность `event_id`; сохранить новый lifecycle и revision, исходное событие и новый `source_sequence`. Эти данные не должны фиксироваться частично. Повторная доставка, пришедшая одновременно с первой, возвращает DUPLICATE_EVENT; тот же `event_id` с иным содержимым — EVENT_CONFLICT. Конкурентное изменение операции или курсора возвращается как отдельный конфликт, без автоматического повтора.

Обычный вызывающий слой получает текущий курсор источника из своего слоя приёма событий и передаёт его F09. После успешной фиксации он продвигает локальный снимок курсора. Реализация репозитория должна устойчиво хранить курсор и обеспечивать атомарное сравнение; конкретный способ его загрузки/восстановления определяется при реализации адаптера хранилища.

Все `string_view` в запросе, событии и курсоре являются невладеющими. Репозиторий обязан скопировать/сериализовать их до возврата из метода фиксации. Тестовый fake проверяет контракт и порядок действий, но не доказывает реальную транзакционность или сохранность после отключения питания.

Перед отправкой физически значимого запроса намерение и operation_id должны быть записаны через StateRepository. Новая запись получает lifecycle REQUESTED и может быть передана исполнителю только после подтверждения устойчивой фиксации. Хранилище обязано атомарно обеспечить уникальность operation_id: точный повтор ранее сохранённого ActionRequest возвращает ALREADY_SAVED_SAME и не разрешает повторную отправку; тот же operation_id с отличающимся содержимым возвращает CONFLICT. Ошибка/неопределённый результат записи не даёт права на отправку. Под «устойчивой фиксацией» понимается запись, которую можно восстановить после перезапуска; фактическая гарантия при внезапном отключении питания проверяется на выбранном накопителе.

F08 получает ActionRequest только вместе с точным подтверждением новой записи от F07. Подтверждение содержит копии невладеющих представлений полей запроса; перед вызовом ActionDispatcher все поля сравниваются без преобразования, включая различие между отсутствующими и пустыми parameters. Исходные строки должны оставаться доступными и неизменными до завершения F08. Если диспетчер ставит запрос в асинхронную очередь, он обязан скопировать или сериализовать все поля до возврата. Несовпадение или статус, отличный от PERSISTED, блокирует передачу.

ActionDispatcher маршрутизирует запрос по target_module и передаёт operation_id без изменения. Получающий функциональный менеджер обязан обеспечивать идемпотентность по operation_id: точный повтор распознаётся как ALREADY_KNOWN и не запускает действие заново; тот же ID с другими данными возвращает CONFLICT. Если достоверно подтверждён приём, возвращается ACCEPTED; если подтверждено, что запрос не принят, — REJECTED; если нельзя определить, дошёл ли запрос, — UNKNOWN. UNKNOWN не разрешает автоматический повтор или генерацию нового operation_id: требуется запросить состояние исходной операции/выполнить сверку.

ACCEPTED означает только принятие запроса функциональным менеджером. Это не подтверждение STARTED и не доказательство физического движения/выполнения. Для опасной операции функциональный менеджер отдельно проверяет актуальное разрешение SafetyManager непосредственно перед физическим действием.

Недопустимые перескоки между статусами должны отклоняться или классифицироваться как конфликт по правилам конкретной операции. Не все операции обязаны использовать каждый статус, но пропуск статуса допустим только если контракт исполнителя явно определяет эквивалентное подтверждение.

Операция считается физически завершённой только после требуемого подтверждения результата; одного сообщения ACCEPTED недостаточно.

К событию обновления операции может прилагаться необязательная пара reason_code и reason_text: машинный код и короткое описание причины отказа/блокировки, если причина идентифицирована. Эти поля не образуют новый статус lifecycle и не заменяют код ошибки. Если причина не установлена, она не придумывается.

## 20. Идемпотентность, повторы и порядок событий

Повторная доставка одной и той же команды или события не должна повторно запускать физическое действие или повторно фиксировать переход.

Нужно различать:

- event_id — идентификатор сообщения/события для обнаружения повторной доставки;
- command_id — идентификатор команды, если он отделён от события;
- operation_id — идентификатор длительной операции;
- correlation_id — связь запроса и последующих событий.

Повтор с тем же идентификатором и тем же содержимым обрабатывается идемпотентно: повторный побочный эффект не выполняется, ранее известный результат может быть возвращён повторно. Тот же идентификатор с другим содержимым считается конфликтом и журналируется.

### 20.1. Сравнение повторно доставленных событий

Для проверки по `event_id` используется логический порт `EventRepository`, который предоставляет поиск ранее сохранённого события. Результат поиска должен различать найденную запись, отсутствие записи и ошибку чтения. Ошибка чтения или противоречивый ответ хранилища не трактуется как отсутствие события и блокирует дальнейшую обработку.

При сравнении содержимого учитываются все поля конверта и `payload`, кроме `received_at`. Это поле назначается принимающей стороной и может отличаться при повторном получении того же события. Остальные текстовые поля и непрозрачное содержимое `payload` сравниваются точно, без нормализации или преобразования.

Результаты проверки:

- `NEW` — запись с таким `event_id` не найдена;
- `DUPLICATE` — запись найдена, её содержимое совпадает;
- `CONFLICT` — `event_id` уже используется, но содержимое отличается;
- `REPOSITORY_ERROR` — поиск завершился ошибкой или вернул противоречивую запись.

`check_duplicate_event()` выполняет только чтение: не меняет входное событие и не сохраняет его. `NEW` означает отсутствие записи на момент проверки, а не резервирование идентификатора. Сохранение результата обработки и координация с побочными действиями должны быть обеспечены вызывающим контуром до выполнения физически значимого действия. Защита от конкурентной параллельной обработки одного `event_id` отдельно определяется при реализации `handle_event()`; сама функция проверки не заявляет атомарного резервирования. F03 сообщает только статус NEW/DUPLICATE/CONFLICT/REPOSITORY_ERROR и не возвращает сохранённый результат обработки: его получение относится к последующему контракту оркестрации.

Если источник передаёт source_sequence, события от одного экземпляра источника проверяются на нарушение последовательности. При отсутствии последовательного номера нельзя определять устаревание только по календарному времени: часы источников могут быть рассинхронизированы. Для операций дополнительно проверяются operation_id и допустимость перехода lifecycle.

## 21. Тайм-ауты и неопределённый результат

Для каждого обмена/операции необходимо определить:

- время ожидания ответа;
- максимальное время операции;
- число повторов и условия их допустимости;
- поведение при повторном запросе;
- поведение при позднем ответе;
- поведение при потере связи;
- способ проверки фактического результата после тайм-аута.

Точные значения определяются после выбора оборудования и протоколов.

Тайм-аут после возможной передачи физической команды не доказывает, что команда не исполнилась. До получения достоверного состояния операция получает OUTCOME_UNKNOWN. Автоматический повтор движения/зарядки/очистки запрещён, пока конкретная политика операции не разрешит повтор после проверки фактического состояния и условий безопасности.

## 22. Временные метки и синхронизация

Необходимо определить источник календарного времени станции и БАС, способ синхронизации и допустимую погрешность.

Время события, время получения и время обработки — разные понятия. Для анализа полёта и передачи данных желательно хранить исходные временные метки и не подменять их временем получения на сервере.

Для измерения интервалов, контроля длительности операций и тайм-аутов должна использоваться абстракция монотонного времени, не зависящая от коррекции календарных часов. Календарное время применяется для журналов, аудита и сопоставления с внешними системами. Конкретная реализация Clock/Timer определяется после выбора платформы.

## 23. Версионирование интерфейсов

Каждый внешний контракт должен иметь версию.

Изменение обязательного поля, единицы измерения, семантики статуса или системы координат считается изменением интерфейса и требует проверки всех зависимых модулей.

## 24. Что пока не утверждено

- JSON или другой формат сообщений;
- MQTT, HTTP, WebSocket или другой сетевой транспорт;
- MAVLink или другой интерфейс автопилота;
- Modbus RTU или другой интерфейс метеостанции;
- формат временных меток;
- точные единицы и диапазоны отдельных полей;
- периодичность обновления;
- способ идентификации устройства;
- структура файлового манифеста.

Не реализовывать окончательный протокол на основании только примеров из этого документа.

## 25. Контракты операторского приложения

### 25.1. Сводка телеметрии датчика

Каждый зарегистрированный датчик должен предоставлять общий набор полей (точная схема и формат пока не выбраны):
- sensor_id — стабильный уникальный идентификатор;
- name и measurement_type — название и измеряемая величина;
- value и unit — значение и единица измерения, если измерение числовое;
- quality_status — OK, STALE, INVALID, UNAVAILABLE, NOT_CONFIGURED или UNKNOWN;
- measured_at и received_at — время измерения и получения;
- source_module — источник данных;
- error_code / description — причина отсутствия или недостоверности данных.

Не все типы датчиков обязаны иметь числовое value: дискретный концевой выключатель может передавать состояние. Нельзя подменять отсутствующее значение нулём или показывать его как нормальное.

### 25.2. Удалённая команда

Команда от приложения должна содержать:
- `command_id` — уникальный идентификатор команды;
- `station_id` — постоянный идентификатор целевой станции;
- `actor_id/user_id` и идентификатор сессии/подтверждённого контекста авторизации;
- `command_type` и `payload` — тип команды и параметры;
- `issued_at` и `expires_at` — время выпуска и срок действия;
- `nonce` или `sequence_number` — защита от повторной доставки;
- `correlation_id`, а для длительной операции — `operation_id`;
- `contract_version` — версия контракта.

Поля пользователя и роли, переданные клиентом, сами по себе не считаются доказательством полномочий. Их проверяет доверенный сервис/станция. При исполнении получатель проверяет адресата, срок действия, авторизацию и отсутствие повтора. Для команд, которые сервер может хранить и пересылать, необходимо обеспечить криптографически проверяемый контекст полномочий и защиту очереди от подмены.

Результат включает статус lifecycle операции, reason_code и короткое reason_text при установленной причине, источник блокировки и временные метки формирования/получения. Повторная доставка одной команды не должна повторять побочный эффект.

### 25.3. Команды обслуживания

Перезапуск модуля должен передавать стабильный module_id, идентификатор команды, пользователя и причину запроса. Станция проверяет, входит ли модуль в разрешённый каталог перезапуска и безопасны ли текущие условия.

Перезагрузка станции — отдельный тип команды. Она не должна представляться как перезапуск основного модуля или аппаратное отключение питания.

### 25.4. Привязка пользователя к станции

Сервис управления доступом должен хранить связь:
- user_id;
- station_id;
- роль/набор полномочий;
- статус привязки;
- кто и когда создал/изменил/отозвал привязку.

После отвязки ранее выданная сессия или токен доступа к этой станции должны быть отозваны. Сам station_id не является секретом и не служит самостоятельным доказательством права доступа.

### 25.5. Идентичность станции и регистрация

Реестр станций должен предоставлять:
- `station_id` — постоянный уникальный идентификатор;
- `inventory_number` — человекочитаемый номер, назначаемый администратором в пределах пространства учёта (предложение, см. REQ-APP-023/DEC-030);
- `hardware_serial` — заводской серийный номер, если он имеется;
- `display_name` — редактируемое отображаемое имя;
- `enrollment_status` — состояние первичной регистрации;
- `device_key_id` / `certificate_fingerprint` — ссылка на ключ или отпечаток сертификата, без передачи приватного ключа;
- `certificate_status` — ACTIVE, EXPIRED, REVOKED, PENDING или UNKNOWN;
- `created_at`, `registered_by`, `retired_at` и статус жизненного цикла станции.

Изменение `display_name` или `inventory_number` не меняет `station_id). Зарегистрированный `station_id` нельзя редактировать или повторно использовать. Повторное предъявление уже зарегистрированной идентичности требует процедуры восстановления/передачи владения и аудита.

### 25.6. Канал подключения

Клиент должен передавать или фиксировать тип подключения: SERVER, WIFI_LOCAL или WIRED_LOCAL, а также сведения о сессии/соединении. Транспорт не меняет семантику команд и статусов.

### 25.7. Видеопоток

Если камера поддерживается, доступ к видеопотоку/кадрам должен иметь отдельное право и отдельный идентификатор сессии. Формат потока, протокол, ограничения качества и поведение при потере канала остаются открытыми.


### 25.8. Реестр БАС и текущий аппарат

Одна станция может иметь несколько зарегистрированных/закреплённых БАС. Операторское приложение должно показывать список таких аппаратов, их идентификаторы, конфигурацию, статус регистрации/доверия и доступность; уполномоченный пользователь должен иметь возможность управлять привязкой в пределах своих прав.

Для одного физического цикла приёма, посадки и обслуживания выбирается один целевой БАС. Одна физическая зона станции не принимает и не обслуживает несколько БАС одновременно. Обнаружение неизвестного устройства не должно автоматически добавлять его в список разрешённых.

Способ обнаружения, аутентификации и визуального/физического сопоставления определяется отдельно для каждой поддерживаемой модели или конфигурации БАС. Список зарегистрированных аппаратов не означает, что все они могут быть распознаны одним и тем же радиомеханизмом.

### 25.9. Политика допуска миссий при недоступности сервера

По умолчанию потеря сервера блокирует начало нового вылета. В приложении предусматривается отдельная явная настройка локального допуска заранее разрешённых миссий: ограниченное число миссий либо действие до ручного удаления задания из очереди. Без заданной действующей локальной квоты вылет не разрешается. Квота, её остаток, назначивший пользователь и срок/основание должны быть доступны для контроля и аудита. Точные роли, область действия квоты и правила синхронизации после восстановления сервера требуют отдельной детализации.

### 25.10. Критерий завершения передачи для допуска к вылету

В приложении оператор выбирает один из двух критериев для допуска к следующей миссии:
- LOCAL_COMPLETE — файлы приняты станцией и прошли предусмотренную локальную проверку целостности;
- SERVER_CONFIRMED — сервер подтвердил получение материалов.

Выбранный критерий отображается явно и применяется при проверке допуска к следующей миссии. Значение по умолчанию, область действия (станция/миссия) и полномочия на изменение пока не фиксируются.

### 25.11. Лимит циклов без физического осмотра и резерв хранилища

Приложение должно отображать настроенный предел автоматических циклов без физического осмотра и текущее значение счётчика. После достижения предела автоматический запуск следующей миссии блокируется с причиной до предусмотренного подтверждения осмотра.

Перед допуском следующей миссии станция проверяет наличие достаточного резерва локального хранилища для ожидаемых материалов. При недостатке места приложение показывает причину блокировки и доступный объём; числовой резерв рассчитывается после выбора БАС, состава материалов и накопителя.

### 25.12. Подтверждение опасных/аварийных действий оператором

В исключительном случае при подозрении на неисправность крышки приложение может запросить дополнительное подтверждение оператора перед её открытием. Это подтверждение не заменяет актуальный результат SafetyManager, достоверные датчики и локальные межблокировки и не может отменить DENY/UNKNOWN.

Уполномоченному удалённому оператору может быть доступна команда подтверждения выхода из аварийного состояния. Перед подтверждением приложение показывает предупреждение, установленную причину и результаты повторных проверок и требует явного действия оператора. Команда не обходит действующую аппаратную/локальную блокировку; инициатор, время, причина, предупреждение и результат записываются в аудит.

## 26. Первичная регистрация станции

Предварительная последовательность регистрации и выдачи Station ID:
1. В безопасном режиме первичной настройки станция создаёт индивидуальную пару ключей; закрытый ключ остаётся на станции и не передаётся через API.
2. Уполномоченный установщик физически подтверждает режим регистрации, а администратор проходит аутентификацию в доверенном сервисе.
3. Станция передаёт запрос регистрации/CSR, открытый ключ, одноразовый challenge и доступные аппаратные сведения.
4. Доверенный сервис регистрации проверяет подлинность устройства и полномочия регистратора, затем проверяет уникальность аппаратной и криптографической идентичности.
5. Реестр/EnrollmentAuthority назначает уникальный Station ID и выдаёт станции подтверждение регистрации и сертификат.
6. Станция проверяет ответ, сохраняет Station ID и сертификат, а реестр фиксирует связь ID с аппаратной и криптографической идентичностью.

Это укрупнённый контрактный сценарий, а не утверждённый протокол provisioning. Офлайн-регистрация, формат ID, PKI, аппаратное хранилище ключей и порядок восстановления описаны в [спецификации идентичности станции и криптографической защиты](24_STATION_IDENTITY_AND_CRYPTOGRAPHIC_SECURITY.md) и пока требуют согласования. Ручной ввод номера или сканирование QR-кода не являются достаточной аутентификацией.
