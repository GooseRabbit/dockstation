# Реестр программных модулей DockStation

**Статус:** рабочий реестр предварительной программной архитектуры.  
**Редакция:** 0.36  
**Дата актуализации:** 2026-11-13.
**Основание:** `docs/05_SOFTWARE_ARCHITECTURE.md`.

## 1. Назначение

Реестр показывает состав логических программных компонентов проекта, степень их проработки, реализации и проверки.

Он нужен для планирования работ и контроля полноты документации. Реестр сам по себе:

- не утверждает окончательную структуру исходного кода;
- не означает, что каждый компонент обязательно станет отдельным процессом, библиотекой или устройством;
- не выбирает язык программирования, ОС, контроллер или вычислительную платформу;
- не подтверждает реализацию или работоспособность компонента.

Границы и детализация компонентов могут уточняться после подготовки спецификаций и согласования интерфейсов.

## 2. Правила статусов

Статусы требований, реализации и проверки независимы друг от друга. Использовать определения из `docs/00_DOCUMENT_CONTROL.md`.

В настоящем реестре дополнительно применяется статус проработки спецификации:

| Статус спецификации | Значение |
|---|---|
| НЕ НАЧАТА | Спецификация ещё не подготовлена |
| ЧЕРНОВИК | Спецификация готовится |
| НА ПРОВЕРКЕ | Спецификация передана на проверку |
| СОГЛАСОВАНА | Владелец проекта согласовал спецификацию |
| ЗАБЛОКИРОВАНА | Нельзя продолжать без закрытия зависимости или открытого вопроса |

Статус «СОГЛАСОВАНА» относится только к конкретной спецификации и не означает, что реализация или испытания выполнены.

## 4. Сквозные технические элементы

Следующие элементы присутствуют в программной архитектуре, но пока не учитываются как самостоятельные функциональные менеджеры:

- `RuntimeEnvironment` — Linux-адаптер чтения версии ОС, версии ядра, архитектуры и сведений о сборке; проверяет доступность базовых источников системной диагностики. Первый срез реализован и проверен на host Linux x86_64; целевая сборка и проверка на Repka Pi 5 ещё не выполнены.
- `SystemDiagnostics` — Linux-адаптер uptime, оперативной памяти, файловой системы корневого раздела, температуры только явно обозначенного CPU/SoC/package-датчика и load average. Первый срез реализован и прошёл CTest в полном Linux CI; отдельный SSD не предполагается обязательным, целевая сборка и проверка на Repka Pi 5 ещё не выполнены.
- `NetworkDiagnostics` — Linux-адаптер чтения сетевых интерфейсов, локальных IPv4/IPv6-адресов и default-маршрутов; предоставляет явные DNS- и TCP-проверки по заданному адресу. Разбор маршрутов проверяет длины/содержимое адресных полей, неизвестное семейство DNS отклоняется. Код и host-проверка добавлены; тест прошёл в GitHub Actions в составе полного набора 10/10 CTest на Linux x86_64. Целевая проверка на Repka Pi 5 ещё не выполнена.
- `PlatformLogger` — системный журнал Linux-приложения: структурированные JSONL-записи, уровни, stderr/необязательный файл, ротация и маскирование чувствительных полей. Перед проверкой порога ротации файловый буфер сбрасывается, чтобы учитывать все предыдущие записи. Входные уровни/пути и ошибки файлового sink проверяются явно; чувствительные имена полей с пробелами также маскируются; тесты прошли в GitHub Actions в составе полного набора 10/10 CTest на Linux x86_64. Не заменяет доменный `EventLogger`.
- `CommandLineParser` — разбор аргументов запуска для параметров RuntimeConfig и явного `--config-file`; фиксирует, какие значения действительно заданы в CLI, чтобы применить их поверх файла. Отклоняет неизвестные/повторные/некорректные параметры и не меняет фиксированный loopback bind. При наличии файла откладывает межполевую проверку до объединения настроек.
- `RuntimeConfigFileLoader` — читает необязательный явно указанный `.conf` в строгом формате `key=value`, ограничивает размер 64 КиБ, проверяет ключи, дубликаты, типы и значения; различает NOT_FOUND, READ_ERROR и INVALID. Не выбирает системный путь по умолчанию и не читает секреты. Итоговый порядок: defaults → file → CLI; итоговая конфигурация проверяется до Logger.
- `RuntimeConfig` — типизированные настройки процесса Linux Gateway и валидатор диапазонов/совместимости. Безопасный loopback bind фиксирован как `127.0.0.1`, порт по умолчанию 8080. Добавлена `initialize_runtime_logger()`: сначала валидирует RuntimeConfig, затем инициализирует PlatformLogger. Файл `.conf` загружается только по явному `--config-file`; итоговые значения валидируются до Logger. CommandLineParser и RuntimeConfigFileLoader зарегистрированы в CTest; Linux-сборка и все 8/8 проверок CTest прошли в GitHub Actions с AddressSanitizer и UndefinedBehaviorSanitizer.
- `LinuxApplicationBootstrap` — точка входа `repka_gateway/main.cpp` и lifecycle-координатор `src/application/linux/application_bootstrap.hpp/.cpp`. Разбирает CLI, при наличии явно указанного `--config-file` загружает `.conf`, применяет только явно заданные CLI overrides, валидирует итоговый RuntimeConfig до инициализации Logger, устанавливает SIGINT/SIGTERM handlers с безопасным `sig_atomic_t`-флагом, проверяет базовые runtime-зависимости, собирает read-only SystemDiagnostics и NetworkDiagnostics, передаёт итоговую конфигурацию и флаг завершения зарегистрированной службе, затем восстанавливает обработчики и завершает Logger. Production-точка входа регистрирует LocalApiServer через ServiceRunner; при отсутствии ServiceRunner сохраняется bootstrap-only режим. Не управляет оборудованием и не запускает второй сервер. Код и CTest-проверка прошли в GitHub Actions; все 10/10 CTest зелёные на Linux x86_64. Bootstrap-only режим не запускает HTTP API.
- `LocalApiServer` и `ApiSerialization` — C++ read-only HTTP API, привязанный только к `127.0.0.1`; доступны только `GET /api/v1/health` и `GET /api/v1/system/diagnostics`. HTTP parser ограничивает размер и число заголовков, отклоняет request body/Transfer-Encoding, неподдерживаемые методы и неизвестные маршруты; ответы формируются из существующих Linux-сборщиков. DNS помечается `NOT_CONFIGURED`, SSH service — `UNAVAILABLE`, пока эти проверки не реализованы в C++ слое. Запуск/остановка связаны с ApplicationBootstrap/ServiceRunner. Последний полный host CI run 43608617035 прошёл: 13/13 CTest, 31/31 C++ host programs и 134 Python pytest; проверены install layout, systemd unit, запуск от непривилегированного пользователя, loopback API, QML package entry point и shell/network checks. Владелец вручную проверил Windows Operator ↔ C++ Gateway и systemd lifecycle в Ubuntu 24.04.5 LTS x86_64 VM; целевая ARM64/Repka Pi 5 и аппаратная интеграция остаются не проверены.
- Временный VM-вертикальный срез Operator → Python Gateway → TestRequestService → TestRequestAdapter → Operator — изолированная проверка программного взаимодействия. Маршрут доступен только при явном `--enable-test-adapter`, принимает исключительно `PING` и сообщает `physical_action_performed=false`. Это не считается production-реализацией `CommunicationService` и не меняет статус ESP32/аппаратной интеграции. C++ LocalApiServer реализует только локальный read-only диагностический API; он не заменяет обмен со станцией, БАС или внешним сервером.

## 5. Приоритет проработки

Текущие кандидаты на пофункциональную проработку:

1. `StationStateManager` — модель состояний и переходов станции.
2. `ConfigurationManager` — загрузка и проверка сохранённой конфигурации станции.
3. `DiagnosticsManager` — стартовая самодиагностика по проверенному снимку конфигурации и контракты отдельных проверок.

Спецификация StationStateManager и план его пофункциональной реализации согласованы. Спецификация ConfigurationManager (`docs/27`) и её план реализации (`docs/28`) остаются черновиками. Документы DiagnosticsManager (`docs/21` и `docs/22`) согласованы в части базовых контрактов решением DEC-058/059; реализация не начата. Функции используют проверенный снимок ConfigurationManager и не дублируют содержательную проверку конфигурации. Открытые аппаратные и режимные вопросы перечислены в docs/21.

Следующие модули не следует автоматически начинать в указанном порядке. Их очередность определяется зависимостями, рисками, открытыми решениями и готовностью интерфейсов.

## 6. Правила актуализации реестра

После каждой завершённой задачи:

1. Обновить только статусы компонентов, которых фактически коснулась задача.
2. Указать ссылку на созданную или актуализированную спецификацию.
3. Зафиксировать реализацию отдельно от готовности спецификации.
4. Отмечать проверку только при наличии фактического результата теста или протокола испытания.
5. Не отмечать компонент как принятый только на основании компиляции или отчёта ИИ.
6. При разделении или объединении компонентов сначала обновить архитектурную документацию и согласовать изменение.
7. Сохранять различие между логическим компонентом и его размещением на конкретном вычислительном устройстве.
