# Архитектура хранения и размещения данных DockStation

**Статус:** согласованная топология данных по DEC-072; конкретные серверные и эксплуатационные детали остаются открытыми.  
**Редакция:** 0.1.  
**Дата:** 2026-11-16.

## 1. Назначение и границы

Документ определяет согласованное распределение данных между Repka Pi 5, удалённым сервером и независимым резервным хранилищем. Он дополняет этап 6 мастер-плана и требования DEC-035, DEC-041, DEC-046, DEC-055, DEC-057 и DEC-068.

Документ утверждает топологию по DEC-072 и локальный SQLite backend по DEC-068. Он **не утверждает** PostgreSQL, конкретный объектный сервис, сроки хранения или место размещения независимых резервных копий. Детали серверной СУБД и серверного файлового хранилища остаются открытыми; SSD остаётся необязательным backend по DEC-057.

Основная цель — не смешивать данные с разными владельцами и режимами отказа. Станция должна сохранять локальную работоспособность и доказуемую историю своих операций при потере связи с сервером, но не должна становиться альтернативным источником истины для пользовательских аккаунтов и владения станциями.

## 2. Базовые принципы

1. **Для каждого домена есть один источник истины.** Локальная станция отвечает за фактические события и состояние своего оборудования. Центральный сервер отвечает за пользователей, OwnerSpace, владение станциями и полномочия доступа.
2. **Локальная фиксация предшествует опасному действию.** Намерение операции и operation_id должны быть устойчиво сохранены до отправки физически значимого запроса. Если подтверждённого commit нет, исполнитель не вызывается (DEC-046).
3. **Связанные записи фиксируются атомарно.** Событие, профильное изменение состояния, проверка дедупликации и продвижение cursor не должны оставлять частично записанный результат. Требования мастер-плана §5.3 обязательны независимо от выбранного backend.
4. **Большие бинарные файлы не помещаются в транзакционную БД.** Видео, изображения и экспортируемые архивы хранятся как файлы/объекты. БД содержит метаданные, контрольные суммы, статусы и ссылки на объекты.
5. **Синхронизация не является двусторонним слиянием всей базы.** Локальная станция публикует свои события и очередь передачи; сервер публикует полномочия, конфигурационные назначения и серверные задания. Конфликт не разрешается правилом «последняя запись победила» для состояния безопасности или физической операции.
6. **Отсутствие хранилища не маскируется.** Если операция требует постоянной записи, UNAVAILABLE, ошибка записи или неизвестный результат commit блокируют эту операцию. Диагностические функции, не требующие записи, могут продолжать работу.
7. **Резервная копия — отдельная копия в независимом домене отказа.** Второй каталог на том же накопителе или в том же сервере не считается достаточным резервированием.

### 3.1. Локальные структурированные данные Repka

Локальное постоянное хранилище должно покрывать только данные, необходимые для автономной работы станции, безопасного восстановления и надёжной передачи:

- актуальный snapshot и историю переходов SSM;
- намерения и lifecycle операций, включая незавершённые операции;
- принятые события, необходимые для дедупликации и аудита;
- реестр разрешённых локальных источников/подсистем и их ревизии;
- source cursor и подтверждённую идентичность текущей source session;
- маркеры начала/завершения восстановления;
- текущую проверенную конфигурацию станции и её ревизию;
- метаданные локальных файлов/записей камеры и устойчивую очередь передачи;
- статусы свободного места и ошибки хранения, если они нужны для принятия решения о допуске к следующему циклу.

Не требуется автоматически сохранять каждую высокочастотную пробу датчика в вечную историю. Частота, детализация, срок хранения телеметрии и агрегация должны определяться отдельно. До такого решения сохраняется согласованный статус/снимок и необходимая событийная история, а не бесконтрольный поток.

### 3.2. Файлы и видеоматериалы

Файловый backend отделяется от транзакционной БД и выбирается конфигурацией. SSD необязателен по DEC-057; это не означает, что Gateway должен бесконтрольно заполнять системный раздел. Для каждого профиля хранения должны быть заданы доступная ёмкость, порог резерва, допустимые типы данных и реакция на отсутствие/отказ.

Предлагаемый общий процесс завершения файла:

1. Создать временный файл в том же файловом хранилище, где будет конечный объект.
2. Записывать данные с контролем размера и ошибок.
3. Завершить запись, выполнить необходимые операции flush/sync и вычислить контрольную сумму.
4. Атомарно опубликовать завершённый файл в конечном пространстве имён средствами выбранной файловой системы.
5. Только после подтверждённой публикации зафиксировать в БД метаданные и готовность к отправке.

Прерванный временный файл не считается завершённым материалом. Повторный запуск должен обнаружить и безопасно обработать незавершённые записи. Точная семантика rename/fsync и поведение при отказе накопителя проверяются на целевой файловой системе.

Видеофайл не удаляется локально после простого начала или завершения HTTP-запроса. Удаление возможно только после подтверждения сервером принятого объекта, проверки его целостности и выполнения утверждённой политики локального хранения. Оригиналы на БАС не удаляются автоматически (требования docs/07).

### 3.3. Центральный сервер

Сервер — источник истины для:

- глобальных пользовательских учётных записей и их аутентификационных данных;
- OwnerSpace, членства пользователей и ролей;
- постоянного реестра Station ID и текущего владельца каждой станции;
- назначений прав, делегирования, выдачи/отзыва серверных сессий и подписанных офлайн-grants;
- централизованного аудита административных действий;
- каталога принятых материалов, их метаданных и статусов обработки;
- централизованных заданий и политик, которые сервер назначает станциям.

Repka не должна хранить копию серверной базы пользователей и самостоятельно решать, кому принадлежит станция. При прямом локальном доступе без сервера допустимы только полномочия, подписанные сервером и ограниченные конкретным Station ID, пользователем, действиями и сроком (DEC-055). Максимальный срок такого grant и перечень разрешённых офлайн-операций остаются открытыми.

Для серверной части логически требуется транзакционная реляционная БД из-за связей пользователь—OwnerSpace—станция—право. PostgreSQL можно оценивать как кандидата, но в этом документе он не утверждается: выбор сервера, схема развёртывания, отказоустойчивость и масштабирование — отдельная задача.

### 3.4. Независимое резервное хранение

Резервные копии сервера должны находиться за пределами его основного узла/тома и по возможности в отдельном домене доступа и отказа. Локальная копия на том же диске не защищает от отказа диска, шифровальщика, ошибки администратора или потери сервера.

Минимальные требования к будущей политике:

- шифрование резервных копий до передачи в отдельное хранилище;
- отдельные учётные данные и ограниченный доступ к резервному контуру;
- версионирование и защита от незаметной перезаписи/удаления;
- согласованность копии БД и связанных файловых объектов через manifest/checkpoint;
- контроль целостности по манифестам и контрольным суммам;
- установленная частота копирования и сроки хранения;
- регулярное испытание восстановления на отдельной среде;
- фиксация фактического RPO/RTO по результатам испытаний.

Конкретные сроки, географическое размещение, владелец ключей шифрования, целевые RPO/RTO и бюджет не определены. До их согласования нельзя обещать заданную длительность восстановления или отсутствие потери данных.

## 4. Оценка вариантов backend

| Вариант | Локальное состояние станции | Централизованные аккаунты и несколько станций | Оценка |
|---|---|---|---|
| SQLite | Хорошо подходит для одного локального процесса, небольшого структурированного хранилища и коротких атомарных транзакций | Не заменяет серверную БД | Утверждён локальным backend DEC-068; точную версию, файловую систему и накопитель необходимо проверить на Repka OS до target acceptance |
| PostgreSQL на самой Repka | Технически возможен, но добавляет отдельную службу, администрирование, обновление и обслуживание для одного узла | Может поддерживать серверный домен, если серверная нагрузка/доступность это оправдают | Не рекомендуется как первый локальный вариант без новых требований к конкурентной записи/нескольким локальным клиентам |
| Файлы JSON/YAML/отдельные файлы на каждую запись | Подходят для экспортов и простых конфигурационных файлов | Не заменяют транзакционный реестр отношений и доступа | Недостаточны как основное хранилище SSM: сложно обеспечить совместную фиксацию состояния, события, cursor и operation |
| PostgreSQL или другая управляемая реляционная БД на сервере | Не нужна на Repka для локального восстановления | Подходит для центрального multi-tenant реестра и транзакций прав | Кандидат серверного слоя; решение отложено до проектирования сервера |
| Объектное хранилище | Не заменяет локальную БД; может принимать крупные файлы по мере передачи | Подходит для видео/материалов и архивов | Отдельный интерфейс и backend; конкретный продукт/протокол не выбраны |

SQLite официально описывается как подходящий вариант локального хранения при небольшом объёме и невысокой конкуренции записи; одновременно допускается только один активный writer для одного DB-файла. Это соответствует текущей модели одного Gateway при условии сериализации записей. Профиль rollback journal DELETE + synchronous=EXTRA в DEC-068 ориентирован на более строгую durability-политику, но гарантии зависят от поведения файловой системы, ядра и самого накопителя. Host-тест завершения процесса не доказывает сохранность при внезапном снятии питания с Repka.

Ссылки на первичную документацию SQLite:
- [When To Use SQLite](https://www.sqlite.org/whentouse.html) — типовые сценарии, ограничения конкурентной записи и локальное применение.
- [PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) — различие EXTRA/FULL/NORMAL и влияние на durability.
- [Atomic Commit In SQLite](https://www.sqlite.org/atomiccommit.html) — механизм rollback journal и атомарности транзакций.

## 5. Обязательные сценарии взаимодействия слоёв

### 5.1. Физически значимая операция

1. Проверить права, конфигурацию, локальные safety-предусловия и доступность обязательного хранилища.
2. Сформировать operation_id и сохранить намерение операции.
3. Получить подтверждение устойчивой фиксации.
4. Только после этого передать запрос исполнителю/контроллеру.
5. Записать подтверждённые статусы/результаты и source cursor согласованной транзакцией.
6. При потере связи или неизвестном исходе не создавать повтор физического действия автоматически; после запуска требуется сверка состояния оборудования.

Эта последовательность не меняет DEC-046 и не даёт серверу права обходить локальные межблокировки.

### 5.2. Передача видео или файла

1. Закрыть и проверить локальный файл, зафиксировать его размер и контрольную сумму.
2. Создать устойчивое задание передачи в локальной БД.
3. Передать объект на сервер по идемпотентному идентификатору/ключу.
4. Сервер подтверждает объект только после того, как файл и его метаданные приняты и проверены.
5. Станция записывает подтверждение в очередь и удаляет локальную копию только по разрешённой политике хранения.

Потеря ответа сервера после фактического приёма не должна создавать дубли: повторная передача должна распознавать тот же идентификатор и содержимое.

### 5.3. Потеря Интернета

- Локальные SSM, журналы событий и очередь передачи продолжают работать в пределах доступного локального хранилища.
- Серверные аккаунты и изменения OwnerSpace не становятся локально редактируемыми.
- Офлайн-действия ограничиваются валидным подписанным grant и локальными safety-проверками.
- После восстановления связи станция отправляет накопленные события/материалы идемпотентно; сервер не переигрывает старые физические команды.

## 6. Отказы и ожидаемое поведение

| Отказ | Обязательное поведение |
|---|---|
| Локальная БД не открывается/повреждена | Persistence-зависимые операции блокируются; не создаются фиктивные успешные статусы; запускается документированный recovery path |
| Накопитель переполнен | Новые записи/материалы не подтверждаются; новый цикл блокируется, если не обеспечен согласованный резерв; причина видима оператору |
| SSD отсутствует или отключён | Независимые функции продолжаются; функции записи на этот backend показывают NOT_CONFIGURED или UNAVAILABLE по фактической причине |
| Сервер недоступен | Локальная станция сохраняет события и очередь; серверные права/владение не меняются локально |
| Объект загружен, но ответ потерян | Повтор использует тот же idempotency key и сверяет размер/хэш; не создаёт второй логический объект |
| Резервная копия повреждена | Она не считается пригодной; используется предыдущая проверенная версия, отказ регистрируется |
| Восстановление из резервной копии | Выполняется на изолированной среде/после согласованной остановки служб; после восстановления обязательны integrity checks и сверка фактического оборудования |

## 7. Открытые вопросы перед утверждением

1. Какой объём и максимальная длительность записи камеры ожидаются за один цикл; сколько циклов необходимо хранить локально до подтверждения сервера?
2. Какой внутренний накопитель фактически присутствует на Repka и каковы его ресурс/надёжность? Какой SSD и интерфейс рассматриваются как необязательный backend?
3. Где физически и организационно размещается центральный сервер: собственная инфраструктура, облако или смешанная схема?
4. Какой объектный backend доступен серверу и кто контролирует ключи шифрования материалов?
5. Каковы требования к срокам хранения телеметрии, журналов, видео, аудита и персональных данных?
6. Каковы целевые RPO/RTO, частота backup и срок хранения независимых копий?
7. Где находится резервное хранилище и кто имеет право запускать восстановление?
8. Каков максимальный срок действия офлайн-grant и какие операции разрешены без сервера?
9. Нужно ли предоставлять владельцу экспорт данных станции в переносимом формате и процедуру полного удаления/передачи станции?

Эти вопросы не блокируют проектирование интерфейсов, но должны быть закрыты до производственной политики хранения и серверной приёмки.

## 8. Следующий порядок работ

После утверждения DEC-068/DEC-072 дальнейшие шаги:

1. проверить SQLite version/features и фактические каталоги/права на целевой Repka OS;
2. schema v2 реализует source registry/session/cursor; schema v3 и `SqliteSubsystemStatusStore` дополнительно реализуют `SubsystemRegistrationReader`, `EventRepository` и `SubsystemStatusRepository` с одной транзакцией для Event, истории статусов, current pointer и source cursor;
3. **Выполнено на уровне Gateway composition root:** `GatewayPersistenceContext` владеет одной SQLite connection и обоими адаптерами; open/close и все вызовы stores сериализованы одним mutex. Production-путь — `/var/lib/dockstation/dockstation.sqlite3`; обе systemd-профили объявляют `StateDirectory=dockstation` с mode 0700. Context открывается до LocalApiServer и закрывается после его остановки; HTTP по-прежнему не предоставляет записи или provisioning. Host CI run 43852667632 подтвердил CTest 31/31 на x86_64 и ARM64, non-root startup, владельца файла БД `dockstation:dockstation` и режим 0600; Repka OS и power-loss acceptance остаются вне этой проверки.
4. **Host end-to-end ingress интегрирован:** ControllerLinkService → AuthenticatedEventTransportAdapter → RegistrySourceSessionVerifier/SourceSessionCoordinator → StationEventPipeline → SubsystemStatusEventProcessor → SQLite. Route SUBSYSTEM_STATUS_UPDATED активен только если явно заданы station_id/controller_source, а точная PSK identity и нужный subsystem уже зарегистрированы локально. Без настроек, SQLite или registration путь fail-closed; автоматической регистрации и HTTP CRUD нет.
5. добавить доверенный локальный provisioning workflow, проверить revoke/reconnect и повторную аутентификацию; расширить crash-recovery/backup-restore проверки и провести target Repka OS + power-loss acceptance.

Host TLS 1.3 PSK-DHE/PTY test использует production codec, ControllerLinkService, Event adapter и SQLite adapters: TelemetrySnapshot остаётся отдельно, DEGRADED event и последующий PASS сохраняются в history/current, cursor двигается только после commit, replayed sequence отклоняется до pipeline. Это не заменяет Mbed TLS interop и физическую Repka проверку. Gateway-only сборка с SQLite disabled не открывает БД и предоставляет только read-only diagnostics API.

## 9. Согласованная топология и оставшиеся технологические решения

Согласована **топология хранения по доменам**, а не одна база «для всего»:

- локальная транзакционная БД на Repka — текущее состояние станции, операции, события, курсоры, конфигурация и очередь передачи;
- отдельный локальный файловый backend — видео и крупные материалы;
- центральная реляционная БД сервера — аккаунты, OwnerSpace, права, владельцы Station ID и централизованный аудит;
- отдельное объектное хранилище сервера — принятые видео и материалы;
- независимое зашифрованное резервное хранилище — копии БД и файлов с проверкой восстановления.

Локальный SQLite backend с профилем DEC-068 утверждён владельцем. Его пригодность ещё должна быть подтверждена на точной версии Repka OS и реальном накопителе; host CI не заменяет target/power-loss acceptance. PostgreSQL можно отдельно оценить для центрального сервера; не следует устанавливать его на Repka только ради единообразия технологий.
