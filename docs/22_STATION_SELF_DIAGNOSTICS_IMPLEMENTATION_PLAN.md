# Пофункциональная реализация самодиагностики станции

**Связанная спецификация:** `docs/21_STATION_SELF_DIAGNOSTICS.md`.  
**Статус:** план согласован в части контрактов и общих правил; реализация не начата.  
**Редакция:** 0.4.  
**Дата:** 2026-11-12.

## 1. Принцип

Исполнитель не должен писать весь DiagnosticsManager или все службы оборудования сразу. Каждая задача должна реализовать одну конкретную функцию исходного кода, её тесты и минимальные необходимые типы/интерфейсы.

Сначала создаётся программная логика, работающая на обычном компьютере с fake/mock-службами. Реальные аппаратные адаптеры подключаются после выбора оборудования и платформы.

### 1.1. Состояние согласования

Владелец проекта 2026-11-12 согласовал базовые контракты спецификации docs/21: семь статусов, поля DiagnosticCheckResult, структуру SelfTestReport и статусы выполнения отчёта, матрицу DIAG-001…016, пассивный характер штатной стартовой диагностики, правила тайм-аутов/ошибок/ограниченных повторов, границы ответственности модулей, порядок выполнения и публикацию отчёта. Отдельно согласовано различать NOT_CONFIGURED, подтверждённое отсутствие ожидаемого устройства (FAIL) и отсутствие достоверных сведений из-за недоступности контроллера/канала (UNKNOWN).

Это согласование утверждает контракты, но не означает начала реализации DiagnosticsManager. Очерёдность реализации подчиняется мастер-плану docs/31 и его зависимостям. Предлагаемый ниже первый вертикальный срез — техническое предложение по последовательности SDA-задач, а не разрешение обойти более ранние этапы мастер-плана.

Открытые вопросы по конкретным устройствам, распределению проверок между узлами, BLE scan, диапазонам/свежести датчиков, критериям эксплуатационных режимов, формату/сроку хранения отчётов, точной параллельности и активным сервисным испытаниям остаются открытыми.

## 2. Общие правила для каждой задачи реализации

1. Работать в ветке, явно указанной владельцем для текущей задачи, и соблюдать `docs/AI_WORK_RULES.md`; самостоятельно не переключать ветки и не выполнять merge.
2. Перед началом обновить сведения о HEAD текущей рабочей ветки и получить актуальные файлы из неё.
3. Прочитать `docs/21_STATION_SELF_DIAGNOSTICS.md` и контракт текущей функции.
4. Реализовать только одну функцию из реестра ниже.
5. Не переписывать модуль целиком и не менять несвязанные файлы.
6. Не придумывать модели устройств, пороги, напряжения, токи и временные параметры.
7. Не вызывать реальное оборудование в unit-тестах.
8. Добавить позитивные, негативные и граничные тесты.
9. Показать diff и точные результаты запуска тестов.
10. Перед коммитом предоставить diff владельцу для просмотра; не выполнять merge без отдельного разрешения.

## 3. Реестр задач

| ID | Функция/задача | Что реализовать | Тесты |
|---|---|---|---|
| SDA-F00 | Типы DiagnosticStatus, DiagnosticCheckResult, SelfTestReport | Общие модели данных и допустимые статусы | Валидные/невалидные поля, неизвестный статус |
| SDA-F01 | validate_diagnostic_context(context) | Проверка диагностического контекста и наличия проверенного снимка ConfigurationManager | Снимок есть/отсутствует/не соответствует активной ревизии; контекст полон/неполон/противоречив |
| SDA-F02 | build_startup_diagnostic_plan(context) | Выбор применимых проверок | Оборудование установлено, не сконфигурировано, БАС отсутствует |
| SDA-F03 | validate_diagnostic_result(result) | Валидация результата одной проверки | Все статусы, отсутствующие поля, неверные данные |
| SDA-F04 | aggregate_self_test_results(results) | Сводка статусов без общего ready Boolean | PASS/FAIL/UNKNOWN/DEFERRED, частичный отчёт |
| SDA-F05 | execute_diagnostic_check(check_id, context) | Поиск и вызов зарегистрированной check-функции | Неизвестный ID, отсутствующая зависимость, исключение |
| SDA-F06 | check_runtime_health() | Проверка доступности критических программных задач | Нормальное состояние, зависшая/недоступная задача |
| SDA-F07 | check_configuration_manager_status() | Проверка доступности ConfigurationManager и наличия актуального проверенного снимка; без повторной проверки содержимого конфигурации | Менеджер доступен/недоступен; снимок VALID/отсутствует; ревизия совпадает/не совпадает |
| SDA-F08 | check_clock_service() | Проверка доступности монотонного времени и качества календарного времени | Нет monotonic clock, wall clock не синхронизирован |
| SDA-F09 | check_event_logger() | Проверка доступности службы журнала | Успешная запись, отказ записи, тайм-аут |
| SDA-F10 | check_local_storage() | Проверка доступа к локальному хранилищу; безопасный временный read/write тест, если он утверждён | Нет носителя, read-only, ошибка записи/чтения |
| SDA-F11 | check_power_manager_status() | Получение статуса PowerManager | Нет ответа, ошибка канала, отсутствующий канал измерения |
| SDA-F12 | check_safety_manager_status() | Проверка доступности SafetyManager и версии загруженных правил | Служба не отвечает, правила не загружены/версия неизвестна |
| SDA-F13 | check_ble_adapter_status() | Проверка BLE-адаптера и BLE-службы без подключения к БАС | Адаптер работает/отключён/отсутствует, служба не отвечает, БАС рядом нет |
| SDA-F14 | check_ble_scan_capability() | Отдельная проверка начала/завершения сканирования, если согласовано | Сканирование запущено/не запущено; список устройств пустой не является ошибкой |
| SDA-F15 | check_camera_pipeline_status() | Проверка доступности камеры и получения диагностического кадра | Нет камеры, нет кадра, ошибка передачи кадра |
| SDA-F16 | check_meteo_service_status() | Проверка доступности службы метеостанции | Служба доступна/нет ответа |
| SDA-F17 | check_sensor_channel_status(sensor_id) | Проверка одного настроенного канала датчика | PASS, STALE, INVALID, UNAVAILABLE, неизвестный канал |
| SDA-F18 | check_motor_service_status() | Проверка доступности контроллера и обратной связи без движения | Контроллер доступен/не отвечает/сообщает ошибку |
| SDA-F19 | check_wireless_power_service_status() | Проверка доступности зарядной службы без подачи энергии | Служба отвечает/не отвечает/сообщает ошибку |
| SDA-F20 | check_drone_integration_status() | Проверка бортовых интерфейсов при присутствующем БАС | БАС отсутствует → DEFERRED; сервис доступен/недоступен |
| SDA-F21 | publish_self_test_report(report) | Передача отчёта в EventLogger и SSM | Ошибка журнала, ошибка публикации, успешная публикация |
| SDA-F22 | run_startup_self_test(context) | Оркестрация готового набора функций | Полный запуск, частичный отказ, тайм-аут одной проверки |
| SDA-F23 | check_watchdog_status() | Проверка доступности/конфигурации watchdog по безопасному диагностическому статусу | Watchdog предусмотрен и доступен; отсутствует; статус неизвестен; проверка не вызывает тестовый сброс |

Порядок строк таблицы не является строгим порядком реализации: идентификаторы задач стабильны и не задают очередность сами по себе. `SDA-F23` — независимая проверка watchdog; её можно реализовать до или после оркестратора `SDA-F22`. Оркестратор должен включать только те check-функции, которые зарегистрированы и прошли свои тесты. Реальные проверки устройств SDA-F11…SDA-F20 можно реализовывать как интерфейсные функции поверх mock-служб до появления физического оборудования.

## 4. Предлагаемый первый вертикальный срез

Первым предлагается реализовать небольшую цепочку без аппаратной привязки:

1. SDA-F00 — типы результатов;
2. SDA-F03 — validate_diagnostic_result;
3. SDA-F04 — aggregate_self_test_results;
4. SDA-F13 — check_ble_adapter_status на интерфейсе fake BleService;
5. несколько unit-тестов Bluetooth-функции для PASS, FAIL, UNKNOWN и NOT_CONFIGURED.

После этого можно подключить SDA-F02 и SDA-F05, а позднее — реальную реализацию BleService для выбранной платформы.

В тестах SDA-F13 отсутствие обнаруженных поблизости BLE-устройств не должно превращаться в FAIL: функция проверяет адаптер/службу, а не наличие БАС.

SDA-F07 не загружает, не декодирует и не валидирует параметры самостоятельно. Она проверяет только доступность результата ConfigurationManager и наличие проверенного снимка ожидаемой ревизии. Содержательные проверки конфигурации относятся к CFG-F01…CFG-F07 из `docs/28_CONFIGURATION_MANAGER_IMPLEMENTATION_PLAN.md`.

## 6. Правила готовности одной функции

Функция считается готовой для следующего шага, только если:

1. реализует ровно свой контракт;
2. возвращает структурированный результат, а не неоднозначный Boolean;
3. отдельно обрабатывает отсутствие, отказ, неизвестность и неприменимость;
4. не имеет неоговорённых физических побочных эффектов;
5. покрыта позитивными и негативными тестами;
6. тесты фактически запущены;
7. diff просмотрен и принят владельцем проекта.
