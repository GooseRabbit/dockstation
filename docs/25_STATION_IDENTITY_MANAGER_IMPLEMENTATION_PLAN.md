# Пофункциональный план реализации StationIdentityManager

**Связанная спецификация:** `docs/24_STATION_IDENTITY_AND_CRYPTOGRAPHIC_SECURITY.md`.  
**Статус:** черновик; требует согласования владельца проекта и выбора платформы.  
**Редакция:** 0.1.  
**Дата:** 2026-11-03.

## 1. Назначение

План разбивает будущую реализацию StationIdentityManager на небольшие задачи уровня конкретных функций исходного кода. Он нужен, чтобы не поручать ИИ или разработчику реализацию всего механизма регистрации и криптографии одним большим заданием.

Каждая задача должна:
- реализовывать одну функцию или одну неделимую пару функций;
- иметь точный контракт входов, выходов и ошибок;
- использовать mock/fake-порты вместо реального сервера или аппаратуры в unit-тестах;
- показывать небольшой diff;
- не коммититься до проверки владельцем проекта.

План не утверждает язык программирования, PKI, тип secure element/TPM, криптографические библиотеки или транспорт.

## 2. Границы ответственности

### StationIdentityManager отвечает за

- постоянный Station ID;
- регистрацию станции и проверку уникальности;
- связь Station ID с аппаратной и криптографической идентичностью;
- жизненный цикл регистрации;
- применение результата регистрации;
- переходы станции в статусы ACTIVE, RECOVERY_REQUIRED и RETIRED;
- запуск процедур ротации/отзыва учётных данных устройства через соответствующие сервисы.

### StationIdentityManager не должен самостоятельно

- реализовывать криптографические алгоритмы;
- самостоятельно писать TLS, PKI или протоколы выдачи сертификатов;
- извлекать/экспортировать приватные ключи;
- заменять EncryptionManager или KeyStore;
- создавать пользовательские учётные записи и назначать роли;
- разрешать опасные физические действия;
- считать Station ID доказательством аутентификации.

Для криптографических операций использовать стандартные библиотеки и отдельные порты. Все закрытые ключи передаются только как непрозрачные ссылки/handles, но не как байтовые массивы.

## 3. Предварительные интерфейсы-зависимости

До реализации необходимо определить абстракции. Названия предварительные:

| Интерфейс | Назначение | Требуемое поведение |
|---|---|---|
| `StationRegistry` | Проверка и хранение записей станций | Уникальные ограничения по Station ID, серийному номеру и ключу |
| `StationIdentityRepository` | Локальное устойчивое хранение идентичности | Атомарная запись, проверка целостности, восстановление |
| `KeyStore` | Генерация и использование ключей | Неэкспортируемые закрытые ключи; возвращает opaque key reference |
| `EnrollmentAuthority` | Сервис регистрации/PKI | Проверка полномочий, выдача Station ID и device certificate |
| `TrustStore` | Доверенные корневые/промежуточные сертификаты | Проверка цепочки и назначения сертификата |
| `ProvisioningContextProvider` | Состояние физически активированного режима регистрации | Идентификатор сессии, срок действия и подтверждение физического действия |
| `AuditLogger` | Журнал регистрации и изменений идентичности | Без приватных ключей, паролей и токенов |
| `Clock` | Проверка временных ограничений | Различать календарное и монотонное время |

Интерфейсы не должны быть привязаны к конкретной БД, серверу или аппаратному ключевому хранилищу до выбора платформы.

## 4. Реестр задач уровня функций

| ID | Функция/задача | Назначение | Основные тесты | Зависимости |
|---|---|---|---|---|
| STI-F00 | Типы `StationIdentity`, `EnrollmentRequest`, `EnrollmentResponse`, `CredentialReference`, `EnrollmentStatus` | Объявить модели данных и статусы жизненного цикла | Валидные/невалидные поля, неизвестные статусы, отсутствие секретных полей в сериализуемой модели | Согласованная спецификация |
| STI-F01 | `validate_station_id_format(station_id)` | Проверить формат выбранного Station ID | Валидный ID, неверная длина/символы/версия/variant, пустое значение | STI-F00; формат UUID должен быть согласован |
| STI-F02 | `generate_station_id(random_source)` | Получить новый ID через криптографически стойкий источник случайности и стандартную библиотеку | Генерация валидных ID, источник случайности недоступен, повторная попытка, отсутствие простого PRNG | STI-F00; решение о UUIDv4 |
| STI-F03 | `validate_station_identity_record(record)` | Проверить согласованность Station ID, hardware_serial, key reference и статуса | Нет обязательного поля, несовпадение ID/статуса, повторяющиеся credential reference | STI-F00 |
| STI-F04 | `find_registration_conflicts(candidate, registry)` | Проверить занятость Station ID, serial и fingerprint публичного ключа | Нет конфликта; совпал один ключ; совпало несколько полей; реестр недоступен | StationRegistry mock |
| STI-F05 | `validate_provisioning_context(context)` | Проверить полномочия регистратора и действительность физически активированного режима регистрации | Нет физического подтверждения; истёкшая сессия; нет прав; валидный контекст | ProvisioningContextProvider, Clock |
| STI-F06 | `create_device_key_reference(key_store)` | Создать индивидуальный ключ и вернуть только непрозрачную ссылку | Успех; ошибка secure storage; приватный ключ не возвращается; нет общего ключа | KeyStore fake |
| STI-F07 | `build_enrollment_request(context, key_ref)` | Сформировать запрос регистрации/CSR и одноразовый challenge | Корректный запрос; повтор nonce; отсутствует ключ; в запросе нет приватных данных | STI-F05, STI-F06 |
| STI-F08 | `validate_enrollment_response(response, request, trust_store)` | Проверить цепочку доверия, challenge, Station ID и публичный ключ | Неверная подпись; истёкший сертификат; неверный nonce; ID/ключ не совпадает; валидный ответ | TrustStore fake |
| STI-F09 | `persist_station_identity(record, repository)` | Атомарно сохранить подтверждённую регистрацию | Успешная запись; отказ записи; частичная запись невозможна; повтор безопасен | STI-F03, Repository fake |
| STI-F10 | `complete_station_enrollment(request, response, context)` | Завершить жизненный цикл регистрации после полной проверки ответа | Полный успешный путь; провал каждой проверки; не публикуется ACTIVE до устойчивой записи | STI-F05, STI-F08, STI-F09 |
| STI-F11 | `verify_station_certificate(peer_certificate, station_record, trust_store)` | Проверить, что подключившееся устройство соответствует записи станции | Неизвестный/отозванный/истёкший сертификат; неверный Station ID; валидная цепочка | TrustStore |
| STI-F12 | `begin_credential_rotation(station_id, authorization)` | Начать плановую или аварийную ротацию ключа/сертификата | Нет полномочий; станция не ACTIVE; корректное начало; причина обязательна | StationRegistry, AuditLogger |
| STI-F13 | `apply_credential_rotation(rotation_response)` | Применить новый сертификат после проверки ответа | Подпись неверна; новый ключ не совпадает; сохранение не удалось; успешная ротация с историей | STI-F08, KeyStore, Repository |
| STI-F14 | `revoke_station_credential(station_id, credential_id, reason)` | Инициировать отзыв учётных данных станции | Неизвестная credential; нет полномочий; успешный отзыв; повторный запрос идемпотентен | EnrollmentAuthority, AuditLogger |
| STI-F15 | `retire_station(station_id, authorization, reason)` | Вывести станцию из эксплуатации без переиспользования ID | Нет прав; активная эксплуатационная сессия; успешное списание; повторный ID запрещён | StationRegistry, AuditLogger |
| STI-F16 | `validate_offline_enrollment_voucher(voucher, context)` | Проверить подпись/срок/область действия одноразового ваучера | Неверная подпись; истёк; уже использован; чужой парк/назначение; валидный ваучер | TrustStore, Clock, VoucherStore |
| STI-F17 | `synchronize_pending_enrollment(record)` | Синхронизировать офлайн-регистрацию с центральным реестром | Успех; дубликат; конфликт hardware identity; сервер недоступен; повторная синхронизация | STI-F04, StationRegistry |
| STI-F18 | `recover_station_identity(context, old_credential)` | Восстановить идентичность после замены контроллера/ключа по сервисной процедуре | Нет физического подтверждения; старый сертификат не отозван; успешная замена с сохранением истории | STI-F05, STI-F12…F14 |

Порядок реализации уточняется после согласования идентификатора, provisioning, аппаратной платформы и PKI. Список функций не является разрешением начинать все задачи последовательно без проверки владельцем проекта.

## 5. Рекомендуемый первый вертикальный срез

После согласования UUIDv4 и языка разработки предлагается начать с изолированного участка без реальной криптографии и аппаратуры:

1. STI-F00 — типы данных;
2. STI-F01 — validate_station_id_format;
3. STI-F02 — generate_station_id на стандартном криптографически стойком источнике случайности;
4. STI-F03 — validate_station_identity_record;
5. STI-F04 — find_registration_conflicts на fake StationRegistry.

В этом срезе нельзя создавать реальные сертификаты, запускать TLS-сервер или хранить реальные ключи. Цель — проверить модель идентификатора, запрет повторной регистрации и стабильность записи станции.

Следующий срез — интерфейс KeyStore и функция STI-F06 на fake-провайдере. Фактическое аппаратное хранилище будет подключено только после выбора контроллера.

## 6. Правила тестирования каждой функции

Для каждой задачи требуется:
- позитивный тест;
- негативные тесты;
- граничные значения;
- тест повтора/идемпотентности, где применимо;
- тест отказа внешней зависимости;
- проверка отсутствия утечки приватных данных;
- проверка порядка побочных эффектов;
- точная команда тестирования и фактический результат.

В unit-тестах использовать fake KeyStore/TrustStore/Registry/EnrollmentAuthority. Никакой тест не должен обращаться к реальному серверу PKI, реальному устройству или эксплуатационным ключам.

## 7. Что запрещено до выбора платформы и согласования криптографии

- писать собственную реализацию UUID, TLS, PKI, Argon2id или цифровой подписи;
- генерировать ключи с помощью обычного `random()` или фиксированного seed;
- помещать приватные ключи в SQLite/JSON/конфигурацию без отдельного утверждённого механизма защиты;
- хранить один общий ключ для всех станций;
- экспортировать приватный ключ через API;
- принимать сертификат только потому, что его предъявил локальный IP или USB;
- выполнять регистрацию по одному только знанию Station ID;
- отключать проверку сертификата ради успешного соединения;
- разрешать удалённой команде обходить SafetyManager;
- считать тест на fake KeyStore доказательством защиты реального оборудования.

## 9. Условия перехода к реализации

До первой задачи должны быть отдельно согласованы:
- формат Station ID и правила его жизненного цикла;
- онлайн- и офлайн-процедура provisioning;
- определение физической станции для целей восстановления после ремонта;
- интерфейс KeyStore и выбранная платформа;
- PKI, профиль сертификатов, срок действия и отзыв;
- используемая криптографическая библиотека;
- язык и структура программного проекта.

Тестовая функция, написанная на fake-объектах, проверяет поведение программной логики, но не подтверждает безопасность TPM/secure element, сертификатной инфраструктуры или физического оборудования.
