# Поэтапная реализация StationStateManager

**Статус:** рабочий план — требуется согласование владельца проекта.  
**Редакция:** 0.1.  
**Дата:** 2026-11-03.

## 1. Назначение

Этот документ превращает спецификацию StationStateManager в небольшие проверяемые задачи для Claude. Цель — не поручать модели написание большого файла или всего модуля за один раз. Каждая задача реализует одну функцию (либо одну неделимую пару функций), добавляет тесты и показывает небольшой diff.

Основной источник требований — docs/17_STATION_STATE_MANAGER.md. Если настоящий план расходится со спецификацией, приоритет у спецификации. Если спецификация расходится с согласованными решениями или остальной документацией, Claude должен остановиться и сообщить о противоречии.

## 2. Принципы работы Claude

1. Работать прямо в main по правилам docs/AI_WORK_RULES.md.
2. Перед каждой задачей обновить локальную копию из актуального main.
3. Сначала изучить точную функцию, её контракт и вызывающие/вызываемые компоненты.
4. В одной задаче реализовывать только одну функцию из списка ниже. Допускаются лишь минимальные типы/вспомогательные элементы, без которых функция не компилируется или не тестируется.
5. Не переписывать весь модуль, соседние функции и архитектурные документы.
6. Добавить тесты только для текущей функции и не ломать существующие тесты.
7. После изменения показать diff и список файлов. Не коммитить, пока diff не проверен.
8. Не подменять реальные аппаратные данные выдуманными значениями. Для тестов использовать явно обозначенные mocks/fakes.
9. Не выбирать язык, фреймворк, транспорт или платформу по собственной инициативе. Если для кода этот выбор уже сделан владельцем проекта, следовать существующей структуре.
10. Не заявлять о выполненных тестах без фактического запуска и точной команды.

## 3. Подготовка перед реализацией

До первой функции должны быть согласованы:

- docs/17_STATION_STATE_MANAGER.md;
- таблица допустимых переходов и событий, по крайней мере для первой вертикальной цепочки;
- event envelope и operation lifecycle;
- логические интерфейсы StateRepository, ActionDispatcher и Clock;
- язык, среда сборки и расположение кода — это отдельные решения владельца проекта.

Не начинать физические действия и драйверы. Первая реализация должна работать на обычном компьютере с имитаторами.

## 5. Рекомендуемый первый вертикальный срез

Чтобы не пытаться сразу реализовать весь цикл станции, начать с безопасного логического примера, не управляющего реальным оборудованием:

1. задать одно согласованное исходное состояние и небольшой утверждённый набор тестовых событий;
2. реализовать validate_event;
3. реализовать resolve_transition как чистую функцию;
4. проверить разрешённый, запрещённый и неизвестный переход;
5. затем добавить commit_transition с тестовым StateRepository;
6. только потом подключать события операций и функциональные менеджеры.

Конкретные состояния/события для среза должны быть взяты из утверждённой таблицы переходов, а не придуманы Claude.

## 6. Обязательные правила тестирования каждой функции

Для каждой новой функции Claude должен приложить:

- позитивные тесты;
- негативные тесты;
- граничные условия;
- тест повторного вызова, если функция может получить повтор;
- проверку отсутствия неоговорённых побочных эффектов;
- точную команду запуска теста и фактический вывод/результат.

Для чистой функции предпочтительны табличные тест-кейсы. Для функции с побочными эффектами использовать mock/fake-порты и проверять вызовы, аргументы и порядок взаимодействия.

## 7. Что запрещено в рамках этих задач

- реализовывать управление приводами и GPIO;
- вызывать реальное оборудование;
- создавать конкретные сетевые протоколы;
- придумывать значения тайм-аутов и количество повторов;
- менять список глобальных состояний без согласования;
- добавлять переходы, отсутствующие в утверждённой таблице;
- трактовать UNKNOWN как ALLOW;
- повторно запускать физическую операцию после тайм-аута без сверки;
- автоматически возобновлять опасную операцию после перезапуска;
- реализовывать SafetyManager внутри StationStateManager;
- объединять всю логику в одну большую функцию.

## 9. Критерий завершения одной задачи

Задача считается завершённой только когда:

1. реализована ровно указанная функция;
2. контракт функции соблюдён;
3. тесты добавлены и фактически выполнены;
4. diff просмотрен и не содержит несвязанных изменений;
5. ограничения и незакрытые зависимости перечислены;
6. владелец проекта принял результат.
