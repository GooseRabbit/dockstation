# Поэтапная реализация StationStateManager

**Статус:** СОГЛАСОВАНО владельцем проекта.  
**Редакция:** 0.4.  
**Дата:** 2026-11-05.

## 1. Назначение

Этот документ превращает спецификацию StationStateManager в небольшие проверяемые задачи реализации. Цель — не поручать одному исполнителю написание большого файла или всего модуля за один раз. Каждая задача реализует одну функцию (либо одну неделимую пару функций), добавляет тесты и показывает небольшой diff.

Основной источник требований — docs/17_STATION_STATE_MANAGER.md. Если настоящий план расходится со спецификацией, приоритет у спецификации. Если спецификация расходится с согласованными решениями или остальной документацией, разработчик должен остановиться и сообщить о противоречии.

## 2. Принципы работы исполнителя

1. Работать прямо в main по правилам docs/AI_WORK_RULES.md.
2. Перед каждой задачей обновить локальную копию из актуального main.
3. Сначала изучить точную функцию, её контракт и вызывающие/вызываемые компоненты.
4. В одной задаче реализовывать только одну функцию из списка ниже. Допускаются лишь минимальные типы/вспомогательные элементы, без которых функция не компилируется или не тестируется.
5. Не переписывать весь модуль, соседние функции и архитектурные документы.
6. Добавить тесты только для текущей функции и не ломать существующие тесты.
7. После изменения показать diff и список файлов. Не коммитить, пока diff не проверен.
8. Не подменять реальные аппаратные данные выдуманными значениями. Для тестов использовать явно обозначенные mocks/fakes.
9. Не выбирать язык, фреймворк, транспорт или платформу по собственной инициативе. Если для кода этот выбор уже сделан владельцем проекта, следовать существующей структуре.
10. Не заявлять о выполненных тестах без фактического запуска и точной команды.

## 3. Подготовка перед реализацией

До первой функции должны быть согласованы:

- согласованная первая вертикальная цепочка из `docs/17_STATION_STATE_MANAGER.md`: запуск, загрузка/проверка сохранённых параметров, стартовая диагностика через DiagnosticsManager, переход к ожиданию только после достоверно успешных критических проверок;
- event envelope и operation lifecycle из `docs/06_INTERFACES_AND_DATA_CONTRACTS.md`, включая необязательную причину отказа (reason_code и короткое reason_text);
- логические интерфейсы StateRepository, ActionDispatcher, Clock/Timer и ConfigurationPort/SettingsRepository;
- отчёт DiagnosticsManager и правила определения критических проверок;
- язык, среда сборки и расположение кода — отдельные решения владельца проекта. Предварительный ориентир аппаратной платформы — LIVE MINI KIT ESP32; язык не выбран, возможность перехода на Orange Pi требует отдельной оценки.

Не начинать физические действия и драйверы. Первая реализация должна работать на обычном компьютере с имитаторами.

**Фактический статус SSM-F01:** функция реализована в `src/core/event_validation.cpp`; тип события и политика объявлены в `src/core/event.hpp`, `src/core/event_validation.hpp`. Для неё добавлены 26 хостовых unit-тестов; проверки GCC, Clang, GCC без exceptions/RTTI и ASan/UBSan пройдены. Целевая сборка ESP32/Arduino и аппаратные испытания не выполнялись. Поля `std::string_view` не владеют памятью: исходные данные должны жить как минимум до завершения вызова `validate_event`; при последующей постановке события в очередь требуется отдельно обеспечить владение данными или гарантировать их срок жизни.

Порядок является рекомендуемым, а не разрешением реализовывать все функции без промежуточной проверки владельцем проекта. SSM-F11 может быть начата только после готовности необходимых зависимостей и набора правил переходов.

## 5. Согласованный первый вертикальный срез

Согласованная владельцем последовательность находится в разделе 8.1 docs/17_STATION_STATE_MANAGER.md. Согласование относится к этому первому срезу; остальные переходы автомата утверждаются отдельно.

Он включает три логических перехода, но состояния ЗАПУСК и САМОПРОВЕРКА содержат дополнительные обязательные действия:

1. ВЫКЛЮЧЕНА → ЗАПУСК по STARTUP_REQUESTED.
2. Внутри ЗАПУСК: инициализировать программные компоненты, загрузить сохранённые параметры/профиль, проверить версию, целостность и обязательные поля. При некорректной конфигурации не подставлять молча рабочие значения.
3. ЗАПУСК → САМОПРОВЕРКА по INITIALIZATION_COMPLETED только после успешной проверки конфигурации.
4. Внутри САМОПРОВЕРКА: запросить DiagnosticsManager выполнить стартовый план проверок через соответствующие службы и получить полный/частичный отчёт с причинами.
5. САМОПРОВЕРКА → ОЖИДАНИЕ по SELF_TEST_COMPLETED только при достоверно успешных результатах всех проверок, признанных критическими, и выполнении условий безопасного исходного состояния.
6. Если запуск обнаружил нештатное завершение или незавершённую физическую операцию, после запуска и диагностики требуется ВОССТАНОВЛЕНИЕ и сверка фактического оборудования; прямой переход к ОЖИДАНИЮ запрещён.

Начальная реализация не управляет оборудованием. Её цель — проверить типы событий, загрузку/валидацию конфигурации, обработку отчёта DiagnosticsManager, validate_event, resolve_transition, запрет неизвестных переходов и тестируемую фиксацию состояния. Неуспешная/неполная диагностика не трактуется как успех; конкретный выбор между ОГРАНИЧЕННЫМ РЕЖИМОМ и ОЖИДАНИЕМ ВМЕШАТЕЛЬСТВА задаётся утверждённой политикой отказов.

Рекомендуемый порядок внутри среза: согласовать профиль критических проверок и контракт конфигурации → объявить типы → реализовать валидатор события/конфигурации → реализовать resolve_transition как чистую функцию → протестировать разрешённые, запрещённые и неизвестные переходы → добавить фиксацию состояния с тестовым StateRepository.

Три перехода первого среза из раздела 8.1 docs/17_STATION_STATE_MANAGER.md согласованы и могут служить основанием для кода. Любые дополнительные переходы, включая отказные ветви, допускаются к реализации только после отдельного согласования.

В первой реализации используются имитаторы DiagnosticsManager, StateRepository, ActionDispatcher, Clock/Timer и ConfigurationPort. Реальные драйверы, приводы и зарядка в этот срез не входят.

## 6. Обязательные правила тестирования каждой функции

Для каждой новой функции исполнитель должен приложить:

- позитивные тесты;
- негативные тесты;
- граничные условия;
- тест повторного вызова, если функция может получить повтор;
- проверку отсутствия неоговорённых побочных эффектов;
- точную команду запуска теста и фактический вывод/результат.

Для чистой функции предпочтительны табличные тест-кейсы. Для функции с побочными эффектами использовать mock/fake-порты и проверять вызовы, аргументы и порядок взаимодействия.

## 7. Что запрещено в рамках этих задач

- реализовывать управление приводами и GPIO;
- вызывать реальное оборудование;
- создавать конкретные сетевые протоколы;
- придумывать значения тайм-аутов и количество повторов;
- менять список глобальных состояний без согласования;
- добавлять переходы, отсутствующие в утверждённой таблице;
- трактовать UNKNOWN как ALLOW;
- повторно запускать физическую операцию после тайм-аута без сверки;
- автоматически возобновлять опасную операцию после перезапуска;
- реализовывать SafetyManager внутри StationStateManager;
- объединять всю логику в одну большую функцию.

## 9. Критерий завершения одной задачи

Задача считается завершённой только когда:

1. реализована ровно указанная функция;
2. контракт функции соблюдён;
3. тесты добавлены и фактически выполнены;
4. diff просмотрен и не содержит несвязанных изменений;
5. ограничения и незакрытые зависимости перечислены;
6. владелец проекта принял результат.
